## As built
Decided by Zvi (2026-11-04: "if it doesn't contradict our plan, push it through"). Built to the card; where it did not match the code the deviation is here.
- **F44, the bound** (`fx/rates.ts`): a feed mid that moves more than `MAX_RATE_MOVE_BPS` (1,000 bp = 10%, exact: `|Δ|·10,000 > 1,000·old`) from the active rate is **refused**: nothing is published, the old rate stays (and runs out in 15 minutes, which refuses quotes: the safe failure of REQ-FX-004), one `fx_rate_deviation` case (severity high, one per active version and offered value) is opened outside the publishing transaction so it survives, and a `VALIDATION_FAILED` is thrown so the worker's job reports it in `errors` (no worker change: `refresh-rates.ts` already catches). The bound is a constant, not configuration (the card says "configured": it is one named constant to change; no new setting exists to read it from). The first rate ever, and any rate after a lapsed manual one, is compared with the last active row.
- **F44, manual expiry:** activating a manual rate sets `valid_until` to 24 hours (`MANUAL_RATE_MAX_MS`); `publishFromPort` publishes over a manual rate whose `valid_until` has passed (the feed takes over) and still returns `undefined` while it stands. **Not done:** "alert on an active manual rate older than N hours": with the cap there is no such state to alert on; the lapse itself is visible as quotes refused and the feed's next publish.
- **F51, the reserve** (`fx/service.ts`): `convert` moves the amount wallet → pending under `{key}:reserve` right after the transfer is submitted and before the vendor is asked; the settle journal pays out of pending; every void (reject, expired quote, the stale sweep) returns it once under `{key}:unreserve`. An outage leaves it reserved while the same key can still retry (the funds check is skipped on a retry whose reserve exists); the stale sweep returns it. In-flight conversions from before this change have no reserve: their retry reserves at that moment, after the purse check.
- **Fixes from review:** (1) a conversion whose `{key}:settle` journal already posted (the process died before the transfer settled) is **settled** with that journal by a retry (whatever the quote's age), by `void()` and by the stale sweep: it is never reserved again, asked of the vendor again, failed, or given back its reserve (a test crashes between the post and the settle, for a retry and for the sweep); (2) the deviation case dedupes on pair and active version (one open case per active rate; a feed that keeps offering wrong values updates its payload to the latest offer); (3) a manual rate with no `valid_until` (active before the cap existed) lapses 24 hours after `activated_at`, in `current()` (SQL) and in `publishFromPort`, so no desktop data fix is needed (tested with rows inserted that way).
- **Existing tests changed** (the card did not mention them): `fx/service.test.ts` — the tests that ran days on under "a manual rate never runs out" now have finance hold the 3.70 manual rate again at their start (`holdManual`), the manual-rate test checks 23 h works and 24 h + 1 ms is refused, and the 0.75% plan test expects the from side on the member's pending account (paid out of the reserve).
- **Files outside the card's list:** `apps/worker/src/fx/refresh-rates.test.ts` (a refused mid is reported), `contracts/openapi.yaml` (the `validUntil` description said a manual rate holds until superseded; description only, not a breaking change) with the regenerated `packages/sdk/src/schema.generated.ts`, and `docs/ops/autopilot-log.md`. `apps/worker/src/jobs.ts` (listed) needed no change.
- **Not done:** the funds check and the reserve are not a lock (T-0544): two simultaneous conversions can both pass the check.
