## As built
- **Routes** (flag `institutions.usBanking`; off is 404 `FEATURE_OFF` before anything else): `POST /institutions/{id}/us-banking` (institution admin, step-up,
  Idempotency-Key; body `{ holder, usEntity? }`; 201 `{ status, holder, sharesPlatformAccount, formUrl? }`) and `GET` (finance and admin; `{ status,
  holder, sharesPlatformAccount, moneyOpen, last4?, balance? }`, balance as `{ minor: string, currency }`). No MCP row: no agent scope.
- **`holder: institution`** creates the provider entity once and opens the hosted application for the requester's IP (the last `X-Forwarded-For` entry,
  which is the one the load balancer appended; absent, the call is refused). The entity is `usEntity` if given, else, for a US-market institution, the
  entity it applied as. An IL institution must name a US entity. **`holder: platform`** makes a sub-account under `usBankingPlatformEntityRef` (an
  `AppOptions` field, set up and approved by ops); without it the call is refused. With a pooled provider account the answer is `sharesPlatformAccount`
  and GET shows no number or balance. The holder is fixed: the other one is a 409.
- **Replay.** The same key and body answer the same result and create nothing; the same key with another body is 409; a new key while an application
  is open resumes it (the form again, no second entity, no new row). A new application after a rejection appends a `pending` row.
- **Status.** An insert-only log (`org.institution_us_banking_event`), the latest row by `seq` is current. It follows the provider two ways: GET polls
  `applicationStatus` while the application is open and records a change (the provider's answer wins over a stored event), and the T-0649 `application`
  handler is wired here (`onProviderApplication`): it maps the provider's id back to OUR institution through `ops.external_ref` (entity type
  `institution_us_banking`), and ignores an id it does not know and any platform institution.
- **KYB.** `us_banking` is a new capability in the KYB gate (open on `approved` and `approved_with_limits`). `moneyOpen` is true only when the
  provider approved AND the gate allows it. T-0652 and T-0653 call `kyb.require(id, 'us_banking')` and check the status; nothing else is opened here.
- **Persistent ledger (fulfils the T-0648 note).** `org.us_banking_key` and `PostgresKeyLedger` (implements the adapter's `KeyLedger`: first write wins,
  hash only) are in this card's migration and file. **They are not yet handed to the real adapter**: building the Crowded adapter into the
  registry (its token, base URL, `subAccountEmail`, `collectionCounterpartyRef`, `payer`) is the go-live wiring, and must pass
  `new PostgresKeyLedger(db)` as its `ledger`.
- **Files outside the card's list:** `apps/api/src/institutions/kyb-gate.ts` and `kyb-gate.test.ts` (the capability and its table), and `packages/sdk/src/schema.generated.ts`
