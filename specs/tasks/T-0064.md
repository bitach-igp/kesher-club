## Trace of what the authorisation path touches (2026-11-06, from `apps/api/src/cards/jit.ts` and the services it calls)
The card's premise, "INSERT for holds and nothing else, no UPDATE anywhere", does not match the code. A decision reads many tables and also writes beyond the hold. **The owner decides the grant list before this card is coded** (it is a security boundary).

Reads (SELECT): `cards.card`, `cards.card_token`, `ledger.account`, `ledger.journal`, `ledger.posting`, `ops.account_balance`, `ops.flag_state` (the agentic flag), `billing.membership`, `billing.plan_version` (also for the FX markup), `billing.entitlement_usage`, `ops.fx_rate`, `agent.pending_intent`. The deferred constraint trigger `ledger.assert_balanced` (`db/migrations/ledger/0001_init.sql:47-56`) re-reads `ledger.posting` when the hold commits; it is not SECURITY DEFINER, so it runs as `club_jit` and the `ledger.posting` SELECT covers it. A first draft of this section also listed `org.member`, `agent.grant`, `agent.client` and `ops.external_ref`; review found those are on listing and approval paths, not the authorisation path.

Writes the path performs today:
| Table | Statement | From |
|---|---|---|
| `ledger.journal`, `ledger.posting` | INSERT (the hold) | `PostgresLedger.postNoOverdraft` |
| `ops.account_balance` | INSERT … ON CONFLICT DO UPDATE (the balance cache, under the per-wallet lock, T-0544) | `post.ts` |
| `ledger.account` | INSERT when a member's `pending` account or a system account is missing | `AccountService.memberAccount`, `systemAccount` |
| `billing.entitlement_usage` | INSERT … ON CONFLICT DO UPDATE (a counter) | `EntitlementService.consume` |
| `billing.entitlement_consumption` | INSERT (idempotency record) | `EntitlementService.consume` |
| `agent.pending_intent` | INSERT, UPDATE (open, consume and release an agent purchase) | `IntentService` |

Proposed grant list (for the owner to approve or change): SELECT on every table in the reads list; INSERT on `ledger.journal` and `ledger.posting`; INSERT and UPDATE on `ops.account_balance`; INSERT and UPDATE on `billing.entitlement_usage`; INSERT on `billing.entitlement_consumption`; INSERT and UPDATE on `agent.pending_intent`; **INSERT on `ledger.account` only if the account-provisioning change below is NOT taken** (without it, a first authorisation for a member with no `pending` account, or a first conversion that needs a system account, fails with permission denied; with it, `club_jit` gets SELECT on `ledger.account` and no INSERT); USAGE on the identity sequence behind `ledger.posting.id` (`bigint generated always as identity`) and the one behind `ledger.journal` if it has one, because the insert's `RETURNING id` and the generated value need it (the migrations grant `usage, select on all sequences` to `club_app` per schema; `club_jit` has none). No DELETE anywhere, no UPDATE of `ledger.*`, nothing on `identity.*`, `audit.*`, `notify.*`, `legal.*`, `addons.*`, `ops.approval_request`, payouts or webhooks, and no write to flags. **Recommended change to the code, not a grant:** stop creating accounts on the authorisation path (provision a member's `pending` account and the system accounts when the card is issued, so JIT only reads `ledger.account`); that removes the one write that can add rows to the chart of accounts from the hot path.

Alternative if the owner wants JIT to hold fewer write grants: move entitlement consumption and the agent-intent updates out of the authorisation transaction (applied from the outbox after the decision). That is a larger change with its own replay and ordering questions and would be a separate card.

Two facts the migration author must keep in mind: `club_jit` runs with `statement_timeout = 200ms` and `lock_timeout = 50ms` (`db/roles.sql:34-35`), so an upsert that waits on a hot `ops.account_balance` or `billing.entitlement_usage` row longer than 50 ms fails and the decision declines TIMEOUT (by design: a decline is cheap); and the real-Postgres proof must run a decision through every write above, including a first authorisation for a member who has no `pending` account yet, before the grants are called enough.

## Decision (owner, 2026-11-06)
Zvi approved the recommendation on PR #246:
- Grants: the proposed list above (SELECT on the reads list; INSERT on `ledger.journal`, `ledger.posting`; INSERT and UPDATE on `ops.account_balance`, `billing.entitlement_usage`, `agent.pending_intent`; INSERT on `billing.entitlement_consumption`; USAGE on the identity sequences those inserts need). No INSERT on `ledger.account`, no DELETE anywhere, no UPDATE of `ledger.*`.
- Code: the authorisation path stops creating accounts. A member's `pending` account and the system accounts the path uses are provisioned before the first authorisation (when the card is issued), so `club_jit` only reads `ledger.account`. That change touches card issuing and `apps/api/src/cards/jit.ts`, which are outside this card's Files: it is a prerequisite card, to be sliced and merged before T-0064 is coded.
- The real-Postgres proof changes with it: a first authorisation for a member whose `pending` account was provisioned at issue approves, and an INSERT into `ledger.account` as `club_jit` is refused.
- The outbox alternative is not taken.
