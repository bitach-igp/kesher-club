# T-0035 [SETUP] The demo's shared clock reaches every API request
REQ: REQ-ADM-004 (enabling; found by T-0923) · Sprint: 11
Files: apps/api/src/server.ts, apps/api/src/server.test.ts, specs/tasks/T-0035.md, specs/tasks/README.md
Test first: the `server.test.ts` cases below. The demo stack runs the API, the worker's jobs and the panel on one shared clock (`createApp({ clock })`). Before this card, `dispatch` stamped each request with `input.now ?? new Date()`, and `createServer` never passes `now`. So every HTTP request ran on the wall clock while jobs ran on the panel's. The full run of all eighteen recordings (T-0923) showed it: once the earlier recordings advanced the panel clock five days, REC-11's quote read the rate as stale ("unavailable"), and REC-13's deposit `valueDate` (taken from the panel clock) was rejected as in the future.
- **Change.** `dispatch` defaults `now` to `app.services.clock.now()`, for REST routes and `/mcp` alike. A caller that pins `now` (every API test) still wins.
- **What `server.test.ts` pins:**
  - with an app clock five days ahead of the wall clock, a REST request and an MCP request through `createServer` see the app's time;
  - a `dispatch` call with `now` sees that time.
- Production is unchanged: there `clock` is the wall clock.
