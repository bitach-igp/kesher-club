# T-0024 [SETUP] Field-level PII sealing with a blind index
REQ: — (enabling; constitution art. 9, DDL rule 8; before T-0119, the first table that stores PII) · Sprint: 9
Files: apps/api/src/crypto/pii.ts, apps/api/src/crypto/pii.test.ts, apps/api/src/config.ts, apps/api/src/config.test.ts, specs/tasks/T-0024.md, specs/tasks/T-0119.md, specs/tasks/README.md
Test first: `createPiiCipher({ dataKey, indexKey })` seals a value as `version ‖ iv ‖ ciphertext ‖ tag` (AES-256-GCM, a fresh 12-byte iv each time) with the column's name as associated data: `open(seal(v, ctx), ctx)` returns `v`; the same value sealed twice gives different bytes; a ciphertext opened under another column's name, a flipped bit, a truncated buffer or an unknown version byte throws and never returns partial plaintext. `index(v, ctx)` is HMAC-SHA256 under a separate key with the column's name mixed in: equal for equal inputs, different across columns, and never equal to anything derived from the data key. The config adds `PII_DATA_KEY` and `PII_INDEX_KEY` as secrets that must each decode from base64 to exactly 32 bytes and must differ; a missing, short or reused key exits with `ConfigError` naming it and never printing it
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: key rotation (the version byte reserves it; a keyring is its own card), KMS-wrapped storage of the keys (the keys reach the process from Secrets Manager, which T-0003's KMS key already encrypts), any table (T-0119 is the first user). Stop and ask on conflict with the spec.
