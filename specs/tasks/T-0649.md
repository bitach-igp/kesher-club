## As built
- **Route.** `POST /webhooks/crowded` (operation `crowdedWebhook`, public, in the contract and `routes.ts`); the server strips a leading
  `/v1`, so `/v1/webhooks/crowded` is the same route. The webhook host's edge forwards `/webhooks/*` (`infra/terraform/envs/*/main.tf`),
  so this is the path to register with Crowded. The router's generic `/hooks/{provider}` is not under that pattern (it is a separate,
  existing question); a `crowded` binding there refuses everything, so a Crowded delivery can only enter through its own route.
- **Order.** Flag off: 404 `FEATURE_OFF`, nothing read. Then the signature over the raw bytes (`signature.ts`; no fallback to a
  re-serialised body): a failure is 401, one row in `ops.inbound_rejected` holding a reason, a length and a SHA-256, never the body and
  never an event id, so a forged delivery claims nothing. Then the batch (1 to 500 events, each with an `eventId` and `eventType`) is
  accepted whole or refused whole (400/422), and every event is stored as `(crowded, eventId)`; a repeat, inside the batch or across
  deliveries, is a no-op. The answer is `{ received, stored, duplicates }` straight away.
- **Rotation.** `crowdedWebhookSecrets` (an `AppOptions` field) is the current secret and, during a rotation, the previous one; each is tried.
  **Not yet read from config:** the process wiring that fills it from `CROWDED_WEBHOOK_SECRET` and a `…_PREVIOUS` (and the Terraform
  secrets) is part of the go-live with the adapter's registration; until then none is configured and every delivery is 401.
- **Processing** is not in the request: `CrowdedWebhook.process`, bound to the `crowded` provider on the router, is run by the worker's
  existing `webhook-replay` job (RUN-05). It takes from the event only which object it is about (a chapter id, and a payment id for an ACH),
  asks the provider for that object's current state through the port (`applicationStatus`, `achStatus`), and hands only that state to
  `crowdedHandlers.application` / `.ach`; `collected` is told which entity's collected payments changed, to read with
  `collectPayments`. Those handlers are for T-0650, T-0653 and T-0652 to supply (none is wired yet). An older event after a newer one
  re-reads the same current state. Unknown event types, wire events and platform events are stored and ignored. An id from the body that
  is not a plain id (`..`, `/`, `?`, `%`) is refused by the adapter's refs before any URL is built (tested, and `parseRef` now whitelists).
- **Files outside the card's list**, all small: `apps/api/src/app.ts` (shared plumbing: the options, the binding, the handler),
  `packages/sdk/src/schema.generated.ts` (regenerated), `packages/adapters/src/crowded/index.ts` (exports), `map.ts` and `map.test.ts` (the
  `parseRef` whitelist), `tools/crowded-webhooks.mjs` (the URL check accepted only `/v1/webhooks/crowded`). `handler.ts`, `verify.ts` and
  their tests are untouched: Crowded's batches and raw-byte signature do not fit the generic one-event router, so the receiver is its own file.
- **Hardening from the Opus review** (each tested): the server now keeps the body as the bytes that arrived (`HttpRequest.rawBytes`) and
  the signature is over them, so a delivery that is not valid UTF-8 verifies and a re-encoded one cannot; the generic JSON parse in `dispatch`
  is skipped for this route (`RAW_BODY`), so a body is judged by its signature before anything parses it (an unsigned non-JSON body is 401
  with a rejected row, not a 400); the 2 MB body limit counts bytes, not UTF-16 units; a leading byte-order mark is not part of the JSON; a NUL
  anywhere in an event (Postgres refuses it in text and jsonb on every retry, which would block the events behind it) or an event over 64 KB
  refuses the whole batch before anything is stored. `server.ts` and `http.ts` are shared plumbing, touched for this.
- **Known limits.** Storing a batch is one insert per event, not one transaction: a failure on event 3 leaves 1 and 2 stored and answers 500,
  and the provider's retry stores the rest, because a stored event is a no-op the second time. An unauthenticated caller can add a row to
  `ops.inbound_rejected` per request (a hash, a reason and a length, never the body); the webhook listener's provider-CIDR allowlist at the edge
  is what limits who can, and a rate limit is a follow-up. The handlers receive **Crowded's own chapter id**: T-0650, T-0652 and T-0653 must map
  it back to our institution through `ops.external_ref`, and ignore an id they do not find, before acting on it.
