Source: gap audit 2026-11-09, item 2; review finding F20 (never carded). `StepUpService` keeps `pending` and `issued` in `Map`s and signs with a per-process `randomBytes` secret; `PasskeyService` keeps `pendingRegistrations` and `pendingAuthentications` in `Map`s. Prod runs `desired_count` 2, so a ceremony started on one task and finished on the other fails, and a restart drops every step-up.
Test first: two `StepUpService` instances over one test database: `start` on A, `complete` on B succeeds; a token minted on A passes `requireStepUp` on B; the token still expires after `STEP_UP_TTL_MS` and a stale ceremony after 60 s; a ceremony is single-use (a second `complete` fails).
- Migration `identity.passkey_ceremony (ceremony_id, kind, session_id, party_id, options jsonb, issued_at, consumed_at)` and `identity.step_up_token (session_id primary key, token_hash, expires_at)`; forward-only, new constraints `NOT VALID` where they apply to existing rows, no existing table touched.
- Replace the four Maps with repository calls; the step-up token becomes a random value stored as a hash (drop the in-process HMAC secret), compared in constant time.
- Expired rows are swept by an existing daily job or deleted on read; no new job.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green, `pnpm db:lint` and a desktop handoff PASS; only listed files touched
