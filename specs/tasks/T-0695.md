# T-0695 [INS] A Crowded 409 DUPLICATE_REQUEST means "in flight": retry the same key, never read it as a conflict
REQ: REQ-INS-024, REQ-INS-022 · Sprint: later
Files: packages/adapters/src/crowded/institution-banking.ts, packages/adapters/src/crowded/fake-crowded.ts, packages/adapters/src/crowded/institution-banking.contract.test.ts, specs/tasks/T-0695.md, specs/tasks/README.md
Source: the 2026-11-10 comparison of the adapter with Crowded's published docs (docs/vendors/crowded/api-inventory.md section 5.5, postman-2sBYArTsS6.md). The adapter was written while the repeat behaviour was undocumented (question 14): it treats a 409 on a money call as "outcome unknown" and a 409 on a keyed create as our own `IDEMPOTENCY_CONFLICT` ("Crowded saw that key with another request"); the fake models "same body, same response; another body, 409". The docs say otherwise: a 409 `DUPLICATE_REQUEST` is a request with the same key still in flight, and the retry returns the payment the first produced; a reused book-payment key is the per-item error `DUPLICATE_PAYMENT`, not an HTTP 409.
Test first: with the fake answering the first call 409 `DUPLICATE_REQUEST` (in flight) and the same key again after a short wait with the payment the first call made, `sendAch` returns that payment (one payment at the fake, never two); a 409 that never clears after the bounded retries (3 tries, 1 s, 2 s, 4 s, clock injected so the test does not sleep) is `OUTCOME_UNKNOWN` as today, still telling the caller to read back before retrying and never to resend under a new key; a 409 on a keyed create (`createSubAccount`, `createPaymentPage`) retries the same key the same way and is never `IDEMPOTENCY_CONFLICT`; a per-item `errorCode: DUPLICATE_PAYMENT` on a payment or funding item is `OUTCOME_UNKNOWN` (the original may have been accepted), not `REJECTED` and not `VALIDATION_FAILED`; every other per-item `error` or `errorCode` and `status: Rejected` stay refusals; the fake's in-flight 409 is a control (a fixture), and a reused key with a different body stays what it is today, undocumented, with a comment pointing at question 27.
- The retry waits only on a 409 `DUPLICATE_REQUEST` and only with the SAME key; a network error or a 5xx is not retried here (the caller's own idempotent retry owns those).
