# T-0695 [INS] A Crowded 409 DUPLICATE_REQUEST on an ACH means "in flight": retry the same key before calling the outcome unknown
REQ: REQ-INS-024 · Sprint: later
Files: packages/adapters/src/crowded/institution-banking.ts, packages/adapters/src/crowded/fake-crowded.ts, packages/adapters/src/crowded/institution-banking.contract.test.ts, specs/tasks/T-0695.md, specs/tasks/README.md
Source: the 2026-11-10 comparison of the adapter with Crowded's published docs (docs/vendors/crowded/api-inventory.md section 5.5, postman-2sBYArTsS6.md). Documented: an ACH or wire payment create (`achCounterparty` is the one the adapter sends) answers 409 `DUPLICATE_REQUEST` while another request with the same `idempotencyKey` is in flight ("retry shortly"), and a retry, or a repeat after the first completed, returns the payment the first request produced. The adapter wrote its money-call path while this was undocumented (question 14): any 409 on a money call is `OUTCOME_UNKNOWN`, so a harmless in-flight overlap becomes a manual read-back.
Test first: with the fake answering the first `sendAch` call 409 `DUPLICATE_REQUEST` (in flight) and the same key again after a short wait with the payment the first call made, `sendAch` returns that payment (one payment at the fake, never two); a 409 that never clears after the bounded retries (3 tries, 1 s, 2 s, 4 s, the wait injected so the test does not sleep) is `OUTCOME_UNKNOWN` as today, still telling the caller to read back before retrying and never to resend under a new key; the retry waits only on a 409 `DUPLICATE_REQUEST` on the ACH create and only with the SAME key (a network error or a 5xx is not retried here); every other per-item `error`, `errorCode` and `status: Rejected` stays a refusal as today; the fake's in-flight 409 is a control (a fixture).
- Not changed, on purpose: the keyed creates (`createSubAccount`, `createPaymentPage`) keep mapping a 409 to `IDEMPOTENCY_CONFLICT` and the sub-account fund (book) call keeps its per-item refusal handling: the docs describe no 409 for those creates, and `DUPLICATE_PAYMENT` is documented only for `type: book` on `/payments`, which the adapter never sends. Whether to extend the same rule to them waits on Crowded's answer to question 27 (a reused key, different body) and on the fund call's undocumented response.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the real sandbox (the in-flight window cannot be provoked on demand); counterparty create and delete (not used by the adapter); a reused key with a different body (question 27); changing the shared port contract.

## As-built
- `moneyCall(fn, retryInFlight)` in `institution-banking.ts`: only the ACH create passes `retryInFlight`. On a 409 or `DUPLICATE_REQUEST` it waits 1 s, 2 s, 4 s (three retries after the first call, so at most four creates) and repeats the same call with the same wire key (`uuidFromKey("ach:<key>")`); a 409 still standing after the third wait is `OUTCOME_UNKNOWN` with the unchanged read-back-before-retrying guidance. A network error, a 5xx, a per-item `error`/`errorCode` and `status: Rejected` are not touched. The sub-account fund call and the keyed creates are unchanged.
- The wait is the adapter option `sleep?: (ms) => Promise<void>` (default a real timer), so no test sleeps.
- Fake: control `inFlightAchCalls = n` makes the next n ACH creates answer 409 `DUPLICATE_REQUEST`; the first of them makes the payment (the "other request"), and the call after the n answers that same payment. `count('payments')` added.
- Tests: in-flight twice then the original payment (one payment, one wire key, balance debited once); never clears (3 waits, four creates, one payment, same key); 503, 500 and a network error not retried; the book transfer's 409 not retried. The existing "a 409 on a payment is OUTCOME_UNKNOWN" test now injects `sleep` (without it the real 7 s of waits would run).
- Files: `specs/tasks/README.md` is listed but needed no change (the row already exists); nothing outside the Files line was touched.

## Follow-up (review nits, with a correction)
- The retry now fires only on a 409 that says DUPLICATE_REQUEST, in the `code` or at the start of the message. The reviewer suggested checking `code` alone; the live sandbox's 409 has no `code` field (`{"type":"ConflictException","message":"DUPLICATE_REQUEST: ..."}`, observed 2026-11-10 with six concurrent creates), so that would have stopped the retry in production. The fake now answers that exact shape, and a test shows another kind of 409 is not retried.
- The `sleep` option comment sits above `sleep` again, not above the webhook option.
