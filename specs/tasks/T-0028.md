Test first: with one `IL` and one `US` row of each kind due at once, the `IL` worker's sweep returns only the `IL` row, so it calls only the `IL` providers, and the `US` worker's only the `US` one. This covers the stale-load, resumable-payout, expired-hold and auto-reload reads, the pending inbound events and their backlog (token events and webhook replay), and the eSIM orders polled. Each job in `jobs.ts` declares its scope, and `jobs.test.ts` pins the table. A `market` job calls a market's providers about rows that carry that market. Each market's worker runs its own `market` jobs side by side under a `market:job` lock, and together the workers cover every row. This applies to the eSIM catalogue sync too, whose nightly run is recorded per market. A `club` job's work is not split by market: the club-rate refresh (one rate per pair, ADR-007), transaction monitoring (a pattern can span markets), the balance proof, and sweeps of tables with no market or of the ledger only (payment requests, agent intents, P2P send completion, stale conversions). Its lock is `club:job`, the same key in every worker, so two workers never run it at once. A lock only prevents overlap: a later tick may run a job again, which its idempotent body allows, and a nightly run happens once a day through `ops.job_run`. A P2P send between members of different markets is swept by the sender's market, whose API created the row; P2P sweeps touch only the ledger, so no provider is called for the other market.
