Test first: with one `IL` and one `US` row of each kind due at once, the `IL` worker's sweep touches only the `IL` row and calls only the `IL` providers, and the `US` worker's only the `US` one. This covers the stale-load, resumable-payout, expired-hold and auto-reload reads, the pending and failed inbound events (token events and webhook replay), and the eSIM orders polled. Each job in `jobs.ts` declares its scope. `market` jobs lock on `market:job` as today. `club` jobs lock on `club:job`, so exactly one worker in the club runs them. The `club` jobs are the club-rate refresh (one club rate per pair, ADR-007) and transaction monitoring (a pattern can span markets), plus the nightly jobs T-0023 adds. `jobs.test.ts` fails on a job without a scope. Two workers, one per market, against one PGlite schema run every `club` job once between them and every `market` job once each. A P2P send between members of different markets is swept by the sender's market, whose API created the row; P2P sweeps touch only the ledger, so no provider is called for the other market.
