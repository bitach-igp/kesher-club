# T-0932 [ADM] Plan versions: finance proposes, a second finance member approves, and only then is a version offered
REQ: REQ-ADM-006 · Sprint: 12
Files: apps/api/src/billing/plan-catalogue.ts, apps/api/src/billing/plan-catalogue.test.ts, apps/api/src/billing/plans.ts, apps/api/src/approvals/service.ts, contracts/openapi.yaml, packages/sdk/src/schema.generated.ts, db/migrations/billing/0003_plan_version_approval.sql, db/migrations/billing/atlas.sum, db/migrations/ledger/0025_plan_version_approval_kind.sql, db/migrations/ledger/atlas.sum, handoff/desktop/T-0932-plan-versions.md, specs/tasks/T-0932.md, specs/tasks/README.md; shared plumbing: apps/api/src/app.ts, apps/api/src/routes.ts
Test first: TST-ADM-006.
**Why.** The demo cannot seed a funder: `POST /memberships` needs a row in `billing.plan_version`, and nothing creates one.
- **Propose.** Finance proposes a version: plan code and name, market, price in the market's currency, term in months, entitlements, FX markup and a reason. It waits as `proposed`, the way price rules do (T-0928): proposer first, a different finance member second.
- **Offer.** On approval the version is offered from its effective date; on rejection it never is. `billing.plan_version` gains a state and the approval, with a migration and a desktop handoff.
- **Never edited.** A newer version supersedes an older one for new members. A member keeps the version they joined on (`PlanService` already pins it).
- **Endpoints.** List, propose, approve, reject (`/admin/plans`); support reads.
**Tests.**
- the 409 for the proposer, then B approves and a new membership quotes the price;
- a member on the earlier version keeps theirs;
- bad price, term or currency answer 422;
- a rejected version is never offered.

## As built
- **Migration numbers.** Billing had only `0001`, so the version columns land in `billing/0002_plan_version_approval.sql`
  (the card said `0003`); the approval kind is `ledger/0025` as listed. Existing versions read `active` through a
  constant default, and the new checks go on `NOT VALID`. `club_app` gains insert on `billing.plan` and
  `billing.plan_version` and update on the decision columns only (`state`, `approval_id`, `decided_at`), so a price,
  term, entitlement or markup still cannot change once written.
- **Offered.** `PlanService.current()` now reads only `active` versions, so a proposed or rejected one is never joined
  on. `createVersion` keeps creating active versions for seeds and tests and takes a `proposal` for the admin path.
  Each listed version says whether it is `offered`: the latest active version in force now.
- **Endpoints.** `GET`/`POST /admin/plans` and `POST /admin/plans/{code}/versions/{version}/approve|reject`. Support
  reads; finance proposes and decides; the proposer's second approval answers 409 through the approvals service,
  which now names `plan_version` among the finance-only two-person kinds. A new plan code creates the plan with the
  given name; an existing plan keeps its name. Activation is audited as `plan_version.activate`. Like price rules,
  these carry no Idempotency-Key, so `HEADER_OPS` is unchanged.
- **Price bounds.** Above zero and at most 100,000.00 in the market's currency (IL in ILS, US in USD); the prices
  themselves stay finance's to enter (decision 5).
