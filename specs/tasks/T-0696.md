# T-0696 [INS] A sub-account create whose outcome is unknown is looked up by name, not retried

Source: docs/vendors/crowded/README.md, "Sub-accounts, 2026-11-10": a repeat of `POST /chapters/{id}/subaccounts` with the same key and body answers 500 (429 while the quota is full), never the sub-account the first call made. The first call may have created it. Organization, chapter and collection creates already look the object up by name before they post (the header comment of institution-banking.ts); `createSubAccount` does not.
Test first: The sub-account create answers an unknown outcome (a network error or a 5xx after the fake created it), then `createSubAccount` is called again with the same key: on main it posts again and gets the fake's 500 (as the live sandbox does), so the member sees `PROVIDER_UNAVAILABLE` and the sub-account exists unreferenced; it must find the existing sub-account by name and return its ref.
- Before posting, look the sub-account up by its name (`Institution {institutionId}`) with `GET /chapters?search=<name>` and reuse an exact name match under this parent; claim it the way collections do (`claim:` note) so no other key can take it. After a post that ends unknown, repeat the lookup before reporting failure.
- The fake answers the live shape: a repeat of the same key answers 500, and the chapter list finds sub-accounts by `search`.
**Tests.** the unknown-outcome case above; a clean first create posts once; a name match claimed by another key is not reused (VALIDATION_FAILED, as collections do); a 429 quota answer is surfaced as such and does not loop.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched

## As-built
- `createSubAccount` (`institution-banking.ts`): inside the key ledger, `findSubAccount` lists `GET /chapters?search=Institution {institutionId}`, matches the exact name, then checks the parent. Live (sandbox, 2026-11-11): the list and search items carry no parent, `GET /chapters/{id}` carries `masterChapterId` (= the parent) and no `parentChapterId`, and only the create response has `parentChapterId`. So each exact-name candidate is fetched and its `masterChapterId` compared (a list item's `parentChapterId` or `masterChapterId` is accepted if one ever appears), then our `parent:` note as a fallback; a same-named chapter of another parent, or one whose parent cannot be told, is not reused. A match claimed (`claim:{parent}:{id}`) by another key is `VALIDATION_FAILED` and nothing is posted (a deliberate difference from collections, which skip and create another: a second same-named sub-account would be a duplicate). Found or created, it is claimed for this key.
- After a post that ends unknown (transport error, 5xx, 409) the lookup is repeated; a hit is returned, a miss (or a failing lookup) reports the original failure. A 4xx other than 409 is a refusal and is not looked up. A 429 becomes `PROVIDER_UNAVAILABLE` with a message naming the tenant quota; no retry, no second lookup (the quota is checked before anything is made).
- Fake: a repeated sub-account key answers 500 (any body); `subAccountQuota = n` answers 429 past n sub-accounts, before the key; the list never names a parent; `GET /chapters/{id}` added (carries `masterChapterId`, as live); `subAccountCount()`.
- Tests (contract file): unknown outcome by 503 and by network error, then the same key finds it (one sub-account, one post; ledger and a restarted adapter agree); post-then-lookup answers on the first call; a clean create posts once; the fake's live shape; claimed by another key; another parent's same-named chapter not reused (the live path: list without a parent, GET with `masterChapterId`); 429 once, no loop, then created when the quota is lifted. The unknown-outcome cases failed on main with `PROVIDER_UNAVAILABLE` (the repeat posted again and got the fake's 500).
- No gated sandbox test added: `sandbox.test.ts` is a read-only smoke test and a sub-account create leaves data behind in the sandbox with no delete route.
