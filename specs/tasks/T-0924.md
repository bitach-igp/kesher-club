Test first: TST-ADM-004. Nothing in the API creates an institution or makes anyone its staff: `org.institution` and `org.staff` were only ever written by tests, so neither the demo nor a pilot can stand up a yeshiva. Admins (staff token) create an institution (`POST /admin/institutions`, idempotent by key, audited `institution.create`) and assign a signed-up member to it (`POST /admin/institutions/{id}/staff`). The `staff` role applies at once. `finance` and `admin` move money or people, so they open an approval of the new kind `staff_grant` with the proposer as the first approver; a second, different admin approves it (`POST /admin/staff-grants/{id}/approve`) and only then does the `org.staff` row and the member's `org_finance` / `org_admin` role land, audited `institution.staff.grant` with both admins named. The proposer approving their own grant answers 409. A member is staff of one institution at a time (409). `POST /admin/institutions/{id}/staff/{partyId}/remove` deactivates the row and strips the `org_*` role, audited; every institution handler already checks an active `org.staff` row per request, so a removed member's next institution call answers 403 on the token they still hold. A role reaches the member's token at their next sign-in.

As built:
- **Idempotent create, UUIDv7 ids.** The key lives in a new insert-only `org.institution_onboarding` (key → institution), written in the same transaction as the institution and its audit entry, so a retry answers the same institution and a key reused with a different name or market answers 409.
- **Grants are scoped by key.** The `staff_grant` subject is `staff:{institution}:{party}:{role}:{key}`, so a retry answers the same grant and a re-grant after a removal opens a new one instead of finding the old approved request.
- **No silent moves.** The `org.staff` upsert updates a row only when it is at the same institution or inactive; an active row elsewhere answers 409, checked again inside the write.
- **Identity.** `IdentityRepository.setUserRoles` (in-memory and Postgres, with contract assertions) replaces the account's roles; the service keeps every non-`org_*` role.
