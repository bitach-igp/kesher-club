Found while slicing REC-14 (T-0922). `InviteService` (T-0602) has `accept` (invited → verified) and `activate` (verified → active), but no route reaches either, and nothing calls `activate`, so nobody on a roster ever becomes active and no allowance can pay anyone.
- `GET /invites/{token}` is public. It shows the institution's name, the roster name and whether the invite is open, expired or accepted. An unknown token answers 404.
- `POST /invites/{token}/accept` takes the member's bearer. The adult student accepts for themself: their party becomes the roster member's. Linking a funder stays with memberships (the seed's other open gap).
- An accepted member is active at once if they have approved KYC at T1 or above, which is what receiving money already needs; otherwise they become active when that approval lands.
- M04 (the app's invite screen) calls the real endpoints instead of the unbound extra.
- The demo seed has three personas accept the yeshiva's roster invites, so its roster has active members.

The tests cover:
- a T1 member's accept makes them active;
- a member without KYC is verified until their T1 approval, then active;
- an expired, used or unknown token answers 404;
- the funnel counts still add up.

Done when: listed tests pass; Spectral clean; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: funders and memberships (plans); invite emails beyond the existing fan-out. Stop and ask on conflict with the spec.

## As built
- "Roster name" is the roster row's own name (the student's), with its programme when the roster has one; rosters
  themselves carry no name. The preview answers 404 only for an unknown token: a used or superseded link says
  `accepted` or `expired`, and never names anyone new.
- Accept is a member call with an Idempotency-Key. The same member accepting again gets the same answer; anyone
  else finds the link gone (404). A member already on that institution's roster answers 409. `funder_party_id`
  stays empty: linking a funder is the memberships' job.
- Activation: `InviteService` asks KYC whether the party holds T1 or above; the kyc webhook calls
  `onIdentityApproved(partyId)` after every approved decision. `KycService.applyDecision` now returns the
  session's party and standing decision even on a replay, so a retried event still activates. The old
  `activate(memberId)` is gone: nothing called it, and its T2-plus-membership rule was never the card's.
- A committed roster import now fans its invites out (`importRosterHandler`'s `onCommitted`); a replay
  re-runs the idempotent fan-out. Before this nothing sent them.
- The link was `…/invite/{token}`, a path no app screen answers; it is now `…/invite?token=…`, which M04 reads.
- M04 shows the institution, the roster name and the programme. Signed out, Accept goes to sign-in and the root
  layout brings the member back to the invite (the T-1017 resume); signed in, the layout no longer bounces the
  invite screen to Home. A 404 on accept ends on the expired state.
- The seed reads each invite from the panel's new `notify/outbox` hook (`apps/simulators/src/host.ts`), the
  only way an HTTP-only seed sees a message; the panel exists in development only. The roster now names `noa`,
  `maya` and `eli`, so its import key moved to `seed-yeshiva-roster-2`.
