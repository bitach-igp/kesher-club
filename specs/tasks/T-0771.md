Problem: adding a vendor means editing the registry's `if` chain and every consumer that asks "is it Crowded" (`CrowdedWebhook` is mounted unconditionally at `/webhooks/crowded`, the funding provider key space `ops.external_ref` uses is the registry's provider string, `FUNDING_PROVIDER = 'funding'` is a webhook route name).
Proposed design: a binding carries typed capabilities, not a name to compare: `{ webhook?: { path: string; secrets: readonly string[] }, mirrorsLedger?: boolean, subAccounts?: boolean, ... }` on `RegistryBinding`; consumers ask `registry.bindingFor('funding', market)?.webhook` and `registry.capability('funding', 'subAccounts')`. Config parsing stays per vendor (a `ProviderConfig` table keyed by vendor name, which already exists at `apps/api/src/config.ts:56-81`), but the decision of what to mount and which secrets a receiver uses reads the binding. Ports keep their identity; `isMemberSubAccountPort` / `isFundingCreditPort` type guards are the existing precedent.
