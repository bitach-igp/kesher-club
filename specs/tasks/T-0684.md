## As-built
- `partner-recon` runs at 05:30 Israel time, scope `market` (the funding vendor is bound per market), recorded per market in `ops.job_run` (`IL:partner-recon`), once per Israel day; a failure records nothing, logs `job_failed` and the next tick retries. The job resolves the funding port and provider name when it runs (`registry.bindingFor('funding', market)?.provider ?? 'simulator'`, the name the load and closure services write into `ops.external_ref`). A funding port with no `listSettled` fails the run (logged, retried) rather than reconciling nothing. The `recon/recon.ts` entry left `JOB_EXCLUSIONS`. The job returns counts only (`matched`, `breaks`, `withinDeadline`, the two dates); the breaks are the cases.
- Design decision 1, our side of the match. `ReconJob` matched on `ops.external_ref` entity_type `journal`, which nothing writes; the funding flow writes `transfer` (a load, by loadId) and `refund` (a refund transfer, by refundId). Without a change every charge would have been `missing_journal` and every ref `missing_partner`. `ReconJob` now also reads those two ref types, joins them to the `ops.transfer`'s journals (`ledger.journal.transfer_id`) and takes the net of the transfer's `partner_settlement` postings as the ledger amount (a charge positive, a refund negative, as `FundingStatementSource` signs them; a converted load posts partner_settlement in the instrument's currency, so currencies agree). A transfer netting to zero (a hold that was reversed) is not ours. No change in `apps/api/src/wallet/*`: the refs already carry what is needed. The `journal` ref shape is kept as it was (no production writer; the existing tests use it).
- Design decision 2, which day. Our side used to be every ref ever written, which a one-day statement would call `missing_partner` forever. Our funding rows are now those with a journal in the Israel business day of the statement; a statement row we know from another day is still compared (a charge settling either side of midnight is a match, not a pair of breaks). A row of ours that the vendor settles only the next day is a `missing_partner` that night, then matched when its statement day comes round (RUN-03: expect the provider's late record).
- Design decision 3, run date vs statement date. `ReconJob.run(provider, runDate)` used one date for the 06:00 deadline and the statement, which cannot be right for a 05:30 run (the statement of the day just starting is empty, and the deadline of yesterday has passed). `run` takes an optional third argument `statementDate` (default `runDate`, so existing callers are unchanged): the nightly job passes today as `runDate` and yesterday as `statementDate`. Case keys stay `recon:{provider}:{externalId}:{runDate}`.
- The deadline alert: a run that ends after 06:00 opens one `recon_break` case (`reason: deadline_missed`, key `recon:deadline:{provider}:{runDate}`), as the US banking recon does, so it appears in `/admin/alerts` and in `recon.break_oldest_h`.
- Cases are the existing `on conflict (dedupe_key) do nothing` insert: a rerun of the same night opens nothing. It does not reopen a case people resolved or dismissed (T-0680's reopen is for a key that stays the same; this key carries the run date, so a break that persists is a new case each night, as the existing test asserts). Collapsing a persisting break to one case needs an owner decision on the key and is not done.
- With the simulator bound to funding (flags off, or dev) the statement is the simulator's in-memory list and our side is whatever the same process loaded, so it reconciles to zero breaks; a simulator restarted while the database kept yesterday's loads would report them as `missing_partner`. It does nothing useful until Stripe funding is bound; then it reads the real balance transactions, which no test has called.
- Review changes. (1) Migration `ledger/0030` adds a partial index `journal_transfer_id_idx` on `ledger.journal (transfer_id)`; the nightly query had nothing to find a transfer's journals by. It is a plain `CREATE INDEX` with `squawk-ignore require-concurrent-index-creation`: Atlas runs a file in one transaction, where CONCURRENTLY is not allowed, and this is pre-launch with no live journal traffic (the file says what to do on a live table). The `atlas` CLI was not available, so `atlas.sum` was recomputed by hand with Atlas's algorithm (per-file cumulative sha256 of name and content; total is sha256 over each name and its base64 hash); the same code reproduces every existing line of the old file. `pnpm db:lint` is green. Handoff `handoff/desktop/T-0684-journal-transfer-index.md` asks for the real Postgres 16 apply and a plan check. (2) The funding query first picks candidate refs (funding transfers only: `ops.transfer.kind` load or refund, so a payout `transfer` ref under a coinciding provider name is never ours; with a journal in the statement window, or named by the statement) and aggregates only those, not all history. A test seeds a payout transfer and journal. (3) The deadline case's `externalId: 'platform'` shows in `/admin/alerts` as `simulator · platform · deadline_missed` (text only) and counts in `recon.break_oldest_h` with no USD amount; a test line covers the gauge.
