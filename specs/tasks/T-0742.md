# T-0742 [WAL] A return after release opens a case instead of being dropped or throwing, and leaves the wallet alone
REQ: REQ-WAL-003 (after T-0703; split from T-0705 on 2026-11-12) · Sprint: later (ADR-018, proposed)
Files: apps/api/src/wallet/loads.ts, apps/api/src/wallet/loads.test.ts, specs/tasks/T-0742.md, specs/tasks/README.md
Source: verified 2026-11-12 at 90fe882. The old T-0705 said "`applyVendorState` calls `fail()` on a settled transfer, which the state machine refuses". That is true for `applyWebhook` (the Stripe path), but the Crowded path T-0703 built is different: `applyVendorLoad` returns early (`if (transfer.state === 'settled' && vendor.status === 'failed') return transfer;`) and the comment points at this card, so today a return after release is silently ignored: no case, no alert.
Assumption: A5 (a return after release is a platform loss: a case for people, no blind debit; who bears it is README question 34, unanswered). A decision for the owner does not block this card: it only records and alerts.
Test first: TST-WAL-003. A settled hosted load whose payment the vendor now reads `failed` with `failureCode` `RETURNED` opens ONE `ops.case` of kind `load_returned_after_release` (severity high, dedupe key `load-returned:{transferId}`, payload: transferId, loadId, amount, the member party id, failureCode), posts no journal, changes no transfer state and leaves the wallet balance as it is; the same event twice, or the same read by a later webhook, opens no second case (the upsert reopens a resolved one the way `openUnknownLoadCase` does); a return BEFORE release still reverses the hold once (unchanged); a settled load the vendor reads `failed` for a non-return reason (`REFUNDED`, `CANCELLED`) opens the same kind of case with that code; the Stripe `applyWebhook` path keeps its current behaviour exactly (every existing test passes unchanged): the case is opened only when the funding binding is not Stripe, so no new throw or case appears for a binding that never had the hole.
