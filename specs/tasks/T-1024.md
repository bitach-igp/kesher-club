What was found:
- There is no `PROVIDER_BILLING`. Billing is bound by `PROVIDER_FUNDING === 'stripe'` (T-0041), together with funding, from one `StripeOverride` carried on `overrides.funding`. So "every PROVIDER_BILLING value" is one input, `PROVIDER_FUNDING`; the tests also set a stray `PROVIDER_BILLING` to prove it changes nothing.
- No runtime consumer selects the Stripe webhook secret by provider name. The adapters take ONE secret (the first) at construction; `acceptPreviousSecrets` wraps `parseWebhook` to accept the older ones during a rotation. `app.ts` mounts no Stripe receiver at all (T-0780 owns that), so there is nothing in `app.ts` to move here.
- The secrets cannot be read FROM the binding to build the adapter: the binding is created after the adapter, from the same override. The first secret therefore still comes from the override.
Moved (safe, identical for every config):
1. The `PROVIDER_FUNDING === 'stripe'` block in `marketplaceOverrides` becomes one private `stripeOverride(config, transport)` returning `undefined` when Stripe is not chosen (the slice-2 shape: the choice is read in one place). Same keys, same throw text, same references (`webhookSecrets` is the config's own array), same `fetch` key only when a transport is given.
2. The funding and billing bindings now declare `webhook: { secrets }` (the full list, current first, in config order), via an optional argument of `bindBoth`; `acceptPreviousSecrets` for funding and for billing reads the list back from its binding instead of from the override. The accepted-secret set is unchanged. `listAdminBindings` picks `provider` and `mode`. CORRECTION (T-1025): the sentence this replaces said the secrets never leave the process, and that was false: the simulators panel route `GET /ports/{capability}` returned the whole binding, so a Stripe or Crowded binding put its revealed secrets in the response. Found in this card's review; fixed by T-1025 (the route answers `provider` and `mode` only, and the lists are frozen).
