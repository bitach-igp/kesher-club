# T-1025 [SETUP] The simulators panel stops serialising a binding whole; the shared webhook-secret lists are frozen
REQ: — (security fix, found in the T-1024 review) · Sprint: later (scoped 2026-11-24)
STATUS: BUILT (PR open).
Files: apps/simulators/src/server.ts, apps/api/src/registry.ts, apps/api/src/registry.test.ts, specs/tasks/T-1024.md, specs/tasks/T-1025.md, specs/tasks/README.md (the route is tested from `registry.test.ts`, which already builds real Stripe and Crowded registries; the simulators package cannot import the API)
Source: T-1024 review. T-0771 slice 1 and T-1024 put `webhook: { secrets }` (revealed strings) on the Stripe and Crowded bindings, and `GET /ports/{capability}` in `apps/simulators/src/server.ts` returned `registry.bindingFor(capability, 'IL')` whole. A host built with Stripe or Crowded configured therefore answered the panel with live webhook secrets. T-1024 said the secrets never leave the process; that was false.
Done:
1. The route answers `binding: { provider, mode }` or `null`, nothing else of the binding. Nothing reads another field: the panel page, `apps/demo` and the admin app use the route only for hooks (`POST /ports/.../hooks/...`), and `host.test.ts` reads `mode`.
2. The secret list is a frozen copy (`Object.freeze` on the mapped array, and on the `webhook` object) for Crowded (slice 1 path) and Stripe (`bindBoth`), shared by both markets and the verifier. No consumer can push, assign or sort it, so the accepted set cannot change after boot. `crowdedWebhookSecrets` still returns a fresh mutable copy and `acceptPreviousSecrets` only destructures, so both behave as before (the slice 1 and slice 3 tables pass unchanged).
Test first (`registry.test.ts`, describe "the panel never serialises a binding whole ..."): written red against the old code. A Stripe-configured host (`funding`, `billing`) and a Crowded-configured host (`institution-banking`): the body of `GET /ports/{capability}` is stringified whole and contains no secret string, no `"secrets"`, no `webhook` on the binding, only `provider` and `mode`; a precondition proves the binding does carry the secrets. A freeze test: the list and the `webhook` object are frozen in both markets, push, assign, pop and sort throw, the list is unchanged, `crowdedWebhookSecrets` is unchanged, and a later change to the caller's array does not reach the binding. A duplicate case: a `[A, B, B]` config yields `[A, B, B]` on every binding (Stripe and Crowded) and from `crowdedWebhookSecrets`, which kills a de-duplicating mutant.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched; every mutant killed or explained. 9 mutants run, 9 killed: route returns the whole binding; route adds `webhook`; Crowded list unfrozen; Stripe list unfrozen; Crowded `webhook` object unfrozen; `bindBoth` `webhook` object unfrozen; de-duplicate Crowded; de-duplicate Stripe; drop the last Crowded secret.
Out of scope: removing `webhook.secrets` from the `Binding` type or hiding it behind a method; a response redaction layer for other routes (none serialises a binding); the Stripe receiver (T-0780).
