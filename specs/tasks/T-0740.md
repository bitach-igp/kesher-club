# T-0740 [WAL] A hosted load needs the member's funding account: details, then ensureAccount, then the refs in ops.external_ref; a refused member cannot load
REQ: REQ-WAL-002 (after T-0698, T-0699, T-0738) · Sprint: later (ADR-018, proposed; split from T-0705 on 2026-11-12)
Files: apps/api/src/wallet/loads.ts, apps/api/src/wallet/loads.test.ts, specs/tasks/T-0740.md, specs/tasks/README.md
Source: `LoadService.request()` and `pull()` at 90fe882. `pull()` calls `createLoad({ customerId: input.payerPartyId, ... })`, but `CrowdedFunding` needs `customerId` to be the payer's contact ref (`c:<id>`, `contactOf` defaults to the identity, `funding.ts`), and nothing makes the contact or the wallet account: `ensureAccount` is called nowhere in `apps/` except a test helper (`apps/api/src/webhooks/crowded.test.ts:269`). `ensureAccount` needs `firstName`, `lastName`, `email`, an E.164 `mobile` and optionally `dateOfBirth` (`packages/ports/src/funding-account.ts`); the repo holds only the sealed phone (`identity.user_account.phone_sealed`) and a first name with the last initial (`identity.member_display_name`), so the details come from T-0738.
Assumption: A1 (contact plus wallet account per member, the vendor ids only in `ops.external_ref`, entity types `funding_contact` and `funding_account` keyed by the party, as T-0698 says), A2 (the vendor is the KYC authority: a rejected contact or a frozen account refuses the load).
Test first: TST-WAL-002. A hosted load for a member with no stored details is 422 `VALIDATION_FAILED` with `extra { detailsRequired: true }` before any vendor call and no transfer; with details, `request()` calls `ensureAccount` once with the idempotency key `funding-account:{partyId}` (stable per party, so a retry is the same account) and writes `funding_contact` and `funding_account` rows (`on conflict do nothing`, provider = the funding binding's provider name), and the second hosted load for that member makes no `ensureAccount` call (the rows are read first); a status `rejected`, `archived`, `frozen` or `closed` is `FEATURE_OFF` naming the status (no name, mobile or vendor text), nothing created, and the gate runs before `begin`; a `DUPLICATE_MOBILE` or `PARTY_CONFLICT` answer is 409 `IDEMPOTENCY_CONFLICT` with a fixed message and a `load_account_conflict` case (dedupe `funding-account:{partyId}`) for people; a `PROVIDER_UNAVAILABLE` is the same code and nothing is created; `pull()` passes `customerId` = the payer's `funding_contact` ref for a hosted load and the party id for every other method (Stripe loads unchanged); a hosted load for a member other than the payer is refused (`FORBIDDEN`) until the funder contact card exists (the payer would need a contact, not an account, ADR-018 A3); the account rows are never read back into a response.
- New optional deps on `LoadService`: `fundingAccounts?: FundingAccountPort` (not `accounts`: `Deps.accounts` is the ledger's AccountService) and `details?: { read(partyId): Promise<{ firstName; lastName; email; mobile; dateOfBirth? } | undefined> }` (T-0738's reader). Neither passed: the hosted path answers `FEATURE_OFF` and every other method is unchanged. `app.ts` passes them in T-0709.
- No personal data in a log line, an error or a case payload.
