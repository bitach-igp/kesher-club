Verified: `heldSince` (`jit.ts:318-325`) is one `sum(-p.amount_minor)` over `ledger.journal j join ledger.posting p` for `kind = 'auth_hold'`, `j.metadata->>'cardId' = $1`, `p.account_id = $2`, `j.effective_at >= $3`. It runs twice in sequence, `await`ed one after the other: the daily limit at `:189` (from `startOfUtcDay`) and the monthly at `:193` (from `startOfUtcMonth`), each only when its limit is set in the authorisation's currency. The velocity count (`:202-205`, `count(*) ... where kind = 'auth_hold' and metadata->>'cardId' = $1 and effective_at > now - 60 s`) is a third scan, already run with the membership read in a `Promise.all`. No migration indexes `metadata->>'cardId'` (grep of `db/migrations`), so each is a filtered read of `auth_hold` journals.
Design: one statement `select coalesce(sum(-p.amount_minor), 0)::text as month_held, coalesce(sum(-p.amount_minor) filter (where j.effective_at >= $4), 0)::text as day_held ... where j.effective_at >= $3` with `$3` the month start (the UTC day start is never before the month start) and `$4` the day start; run only when at least one limit applies; the two comparisons then use `day_held` and `month_held`, daily first, both answering `LIMIT_EXCEEDED`, so the decline code and its order are unchanged. Read-only: no lock, no write, no new index. The velocity query is NOT folded in: it counts journals across all of the card's purses (no `account_id` filter) while `heldSince` is per pending account, so merging would change a result. If measurement (`docs/ops/jit-load-test.md` method) shows it is worth it, run the held-sum read inside the existing velocity-and-membership `Promise.all`; the card does that only if the budget test below stays green.
