Design:
- `appearance.model.ts`: `APPEARANCE_OPTIONS` = `system`, `light`, `dark` with `CopyKey` labels (`appearance.system`, `appearance.light`, `appearance.dark`; a helper under `system`: follows the phone). State `{ status, theme: 'system' | 'light' | 'dark', saving, notice?, error? }`. `load()` reads `preferences.get()`. `choose(value)` applies at once (the store changes before the call), calls `preferences.set({ theme: value })` (the object form T-1020 introduces), keeps the server's answer, and on refusal rolls back to the previous value with `appearance.saveFailed`. Re-choosing the current value or choosing while `saving` is a no-op (as in currency).
- The mapping lives in one exported pure function `overrideOf(theme): ThemeMode | undefined`: `system` maps to `undefined` (so `ThemeOverrideContext` falls through to `useColorScheme()`), `light` and `dark` map to themselves.
- The override must reach every screen from one place, so the stored choice cannot live inside the Appearance screen's own model. `_layout.tsx` owns one shared `appearance` store (created beside the other seams), seeded after sign-in by `preferences.get()`, and the Appearance model writes through it: `createAppearanceModel({ preferences, shared })` where `shared.store` is that store. `_layout.tsx` wraps the tree in `<ThemeOverrideProvider value={overrideOf(theme)}>` ABOVE everything that calls `useTheme()` (above `TabBar`, the `Slot` and the sign-in screens), and `RootLayoutView` takes the store as a dep so tests render it without Expo.
- Before first paint: DECIDED IN THIS CARD. Signed-out screens (sign-in, OTP, passkey) have no account, hence no preference: they follow the system. After sign-in the preference is loaded once; the layout shows a held, system-themed neutral frame (the existing loading skeleton on the canvas colour of the SYSTEM mode, no content) until `preferences.get()` resolves or fails, with a 1.5 second cap, then renders the app in the stored mode; on failure or timeout it renders in `system`. END STATE when `get()` resolves AFTER the cap: SWITCH ONCE. The store is still written when the late answer arrives and the mode switches a single time (no flicker back); otherwise the member would stay on system until they opened the Appearance screen. A `get()` that never resolves leaves the app on `system` for good and the Appearance screen's own load retries. This avoids the one-frame flash of the wrong mode on launch without blocking the app on a slow API. The held frame must be covered by a layout test with a never-resolving `get` (the app renders after the cap, in system mode, and stays there), with a `get` that resolves after the cap (the mode switches exactly once to the stored value) and with a resolving `get` (no frame in the wrong mode).
- SEEDING: `signedIn` is recomputed on each render with no subscription, so the shared store is seeded from a `useEffect` keyed on `signedIn` going true (it calls `preferences.get()` once per sign-in and writes the store) and RESET to `system` in the same effect when `signedIn` goes false. Sign-out resets the shared store to `system`, so the next member on the device never sees the previous member's mode.
