Source: the #418 and #419 reviews. Today the metrics exist and nothing watches them, and an abandoned removal has no way back.
Behaviour:
1. Alarms (page unless noted; each description names the alert and RUN-10):
   - `staff.deprovision_refused` with reason `unknown_org` or `scim_unauthorized`: ANY occurrence pages (config drift between WorkOS and `orgIdp.orgs` silently drops real removals, T-1118 closes the cause).
   - `staff.drift_refused{reason=guard_half}` and the audit row `institution.staff.drift_refused`: a ticket the first day, a page when the same institution repeats for a second day (a standing refusal means a real removal is waiting behind the guard). The audit row is read by the runbook, not alarmed (no metric exists for it).
   - `staff.drift_finish_abandoned` greater than 0: pages. An abandoned removal leaves a LIVE member session with no institution access, and today no tool re-drives it.
   - Decide, and say in the PR, whether `staff.deprovision_lag_s` over 900 also pages (the 15-minute promise of REQ-AUTH-008); the card default is a ticket.
2. Re-drive. A staff-only, audited way to clear an abandoned marker or re-run `finish` for one removal (institution id and the removal's event key), through the existing admin surface or a worker-side function the runbook names; it writes an audit row, never edits a ledger row, never revokes a session newer than the removal (the shared `finish` rule). If it needs a route, that is a contract change: split it into its own card and keep a documented service-call procedure here.
3. Runbook RUN-10 in the club-runbook format (owner role, severity, alert names, first five minutes, resolution path, member message, verify), indexed in `docs/runbooks/README.md`. It names the exact audit actions and metric names to read, the re-drive step, and that no step edits the database by hand.
4. The alarms contract test and `alarms.tftest.hcl` hard-code alarm counts (the stale-job count is 28 after #419, and per-metric counts elsewhere): update them to the true new numbers, with a comment, never loosen an assertion to a range.
Test first: (1) `alarms-contract.test.ts` fails before the rows are added (each new "Alerts that page" row has an alarm whose description names RUN-10) and passes after; (2) `terraform test` (`tests/alarms.tftest.hcl`) with the new counts; (3) a re-drive test: an abandoned removal is re-driven once, the marker is cleared with an audit row, a second call changes nothing, and a session issued after the removal survives.
