Source: gap audit 2026-11-09, item 10; after T-0691 and T-0694. Re-scoped 2026-11-10 after the design check: the port already has `FederatedIdPPort.revoke(provider, refreshToken, idempotencyKey)` (OIDC adapter, simulator and contract suite exist, T-0117), so no port work is needed (there is no `revokeAppleToken`); there is no member-deletion flow, so the hook goes into `ClosureService` (T-0504), the account closure that sets the status `closed`; and the stored token comes from T-0694.
Test first: closing a member with an Apple link calls `federatedIdp.revoke('apple', token, 'closure:{partyId}:apple-revoke')` once with the unsealed refresh token, then erases the token row; a revoke failure does not block the closure, opens one `ops.case` (dedupe `apple-revoke:{partyId}`) and the token is erased either way (the operator needs no token; a retry would, which the card accepts); a member with only a Google link or only a passkey triggers no revoke; closing twice revokes once (the token row is gone and the adapter's idempotency store backs it).
