# T-0694 [AUTH] A member's Apple or Google link is stored, with the Apple refresh token sealed
REQ: REQ-AUTH-004, REQ-AUTH-005 · Sprint: later
Files: db/migrations/identity/0006_federated_token.sql, db/migrations/identity/atlas.sum, handoff/desktop/ (one request), apps/api/src/auth/social-links.ts, apps/api/src/auth/social-links.test.ts, apps/api/src/auth/repository.ts, apps/api/src/auth/pg-repository.ts, apps/api/src/auth/repository.contract.ts, specs/tasks/T-0694.md, specs/tasks/README.md
Source: T-0692's design check, 2026-11-10. T-0691 signs a member in through an `ops.external_ref` row (entity_type `member`, provider `apple` or `google`, external_id the IdP subject) but nothing writes that row, and nothing keeps the Apple refresh token that T-0692 must revoke on deletion. `FederatedIdPPort.exchangeCode` can return a `refreshToken`; no caller persists it.
Test first: `SocialLinks.link(partyId, provider, { subject, refreshToken? })` writes the `ops.external_ref` link and, for Apple, the refresh token sealed with `PiiCipher` (AES-256-GCM, the column name as associated data) in a new `identity.federated_token (party_id, provider, refresh_token_sealed bytea not null, created_at, primary key (party_id, provider))`; a second link for the same member and provider is refused (409 `IDEMPOTENCY_CONFLICT`), a subject already linked to another member is refused; the stored token is never plaintext (read the column raw), never logged, and a member with only a Google link has no token row; reading the token back (`takeForRevoke`) decrypts it only for the revoker.
- Forward-only migration, new table only (club-ddl: uuid, timestamptz, `club_app` grants limited to this table); a desktop handoff per `handoff/README.md`.
- A service function only: no route. The settings screen and its route (step-up required, since it adds a sign-in method) are a later card.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace`, `pnpm db:lint` green; desktop handoff PASS; only listed files touched
Out of scope: the link route and screen; unlink (needs DELETE on `ops.external_ref` for `club_app`, which the grant in ledger/0001 withholds: an explicit owner decision on widening that grant, or a different unlink design, goes with the settings-route card); Google refresh tokens; revoking (T-0692).

## As-built
- `SocialLinks` (`apps/api/src/auth/social-links.ts`, service only, no route, not wired into `app.ts`): `link(partyId, provider, { subject, refreshToken? })`, `takeForRevoke` and `eraseToken`. `takeForRevoke` unseals and returns the token and does not delete; `eraseToken` deletes only the token row (the link stays), so T-0692 reads, revokes, then erases, and each is tested alone. The token is sealed with `PiiCipher` under the column name `identity.federated_token.refresh_token_sealed`; only Apple keeps a token (a token passed for Google is dropped), and an Apple link without a token is allowed (no row).
- Refused with `DomainError` `IDEMPOTENCY_CONFLICT` (409): a second link for the member and provider (even with the same subject) and a subject another member holds; messages name the provider only. Bad input is `VALIDATION_FAILED`, an unknown member `NOT_FOUND`. Nothing is logged by the service.
- Repository (both implementations, plus a contract case): `linkFederated` (one transaction: the `ops.external_ref` insert with `on conflict do nothing`, then the token insert; returns `linked | member_already_linked | subject_taken`), `findFederatedSubject`, `findFederatedToken`, `deleteFederatedToken`. The repository only ever sees the sealed bytes.
- Migration `identity/0006_federated_token.sql`: `identity.federated_token (party_id uuid, provider text check apple|google, refresh_token_sealed bytea not null, created_at timestamptz, primary key (party_id, provider))`; `club_app` gets select, insert, delete on it. No FK to `user_account`, as for the other identity tables. `atlas.sum` was recomputed by script (atlas is not installed here): the script first reproduced the existing five lines and the total exactly. Desktop request `handoff/desktop/T-0694-federated-token.md`.
- Not decided here: the step-up check on adding a sign-in method belongs to the later route card; the service trusts its caller. The cipher keys are the existing PII keys. Not covered: real Postgres apply and the `club_app` grants (the desktop request).
- Unlink was dropped from this card: `club_app` has select, insert and update but no delete on schema `ops` (ledger/0001), so deleting the `ops.external_ref` link would fail in production while PGlite (unrestricted) hides it. T-0692 needs only `takeForRevoke` and `eraseToken`, which touch `identity.federated_token` where delete is granted.
