What the code does today (two consumers in `buildServices`):
1. `app.ts:209`, `subAccountChapters(o.db, o.registry.bindingFor('funding', o.market)?.provider ?? 'simulator')`. The string is NOT compared to anything. It is the `provider` column the member sub-account lookup filters `ops.external_ref` on (`funding_subaccount` rows, `s:<chapter>`), i.e. the data key the funding workflows write those refs under (`LoadService` and `ClosureService` get the same `bindingFor('funding', market)?.provider ?? 'simulator'` at `:260` and `:293`). Per value: PROVIDER_FUNDING `sim` binds `simulator` (mode `sim`), `stripe` binds `stripe` (mode `sandbox`); `createRegistry` never binds `live` (it refuses a `live` base mode) and no other code binds funding, so the other (provider, mode) pairs only arise from a hand-built registry, where the value is that binding's `provider` for any mode and either market. The `?? 'simulator'` fallback is unreachable through a real `ProviderRegistry`: `createApp` resolves `funding` (which throws when unbound) before it matters.
2. `app.ts:295`, `if (bindingFor('billing', o.market)?.mode === 'sim') webhooks.bind('simulator', { verifier: simulatorVerifier, ... })`. This reads the BILLING binding (the card text of T-0771 said funding) and its MODE, not a provider name: PROVIDER_FUNDING `sim` mounts `POST /v1/hooks/simulator` (200 with `x-sim-signature: sim`, 401 without), `stripe` (billing is bound to Stripe in sandbox) leaves it unmounted (404 NOT_FOUND). Any hand-built billing binding mounts it exactly when its mode is `sim`, whatever the provider and the market.
Why nothing moved (each needs an owner decision, or changes behaviour, or is dead code):
- Item 1 cannot become a capability. A flag such as `subAccounts` says whether a provider has sub-accounts; the lookup needs WHICH provider wrote the refs, and only the provider string says that. Replacing the argument with anything else changes the key space `ops.external_ref` is read under (a new `refProvider` field would be the same string under another name). Gating the lookup on a flag would also change behaviour: today the simulator's refs (`provider = 'simulator'`) are looked up too, so a `subAccounts`-less simulator binding would stop recognising its own sub-account chapters. Whether the simulator should be a sub-account provider, and which field names the ref key space, is the owner's call, together with the key-space question the T-0771 problem statement raises (`FUNDING_PROVIDER`, `ops.external_ref`).
- Item 2 is already a mode check, which is not name branching: `mode === 'sim'` is what `simulatorFlagViolations` and `ProvisioningService.verifier` read too. A `simulated` / `mirrorsLedger` flag would duplicate `mode`, and the only producers of `mode: 'sim'` are `SimulatorHost` (`apps/simulators`, outside this card), so a flag set "where bindings are built" in `apps/api/src/registry.ts` could not cover them. Deriving it inside `ProviderRegistry.bind` is a rename of `mode === 'sim'`. Left until slice 5 (mount receivers from `binding.webhook.path`) decides how simulator and vendor receivers are declared.
- No field was added to `Binding` (and nothing secret could be: bindings stay safe to serialise, T-1025).
