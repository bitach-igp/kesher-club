Every adapter already passes its contract suite against its fake; this card adds a sandbox contract run behind an env gate (skipped in CI, run by the deploy smoke job with sandbox keys) and the Terraform secret containers it needs (`twilio-*`, `postmark-*`, `expo-access-token`). Webhook secrets for the dual-key rotation window (two comma-separated values) are accepted.

Out of scope: live keys; the flag flips (`billing.stripe` and the rest stay as `config/flags.json` says); ADR-006 vendors. Stop and ask on conflict with the spec.
As built:
- Choices (rows of `PROVIDER_PORTS`, default `sim`): `PROVIDER_FUNDING=sim|stripe` (binds `funding` and `billing` together), `PROVIDER_NOTIFY_SMS=sim|twilio`, `PROVIDER_NOTIFY_EMAIL=sim|postmark`, `PROVIDER_NOTIFY_PUSH=sim|expo`. Each set is all-there-or-refused, like T-0042's, and a partial set is refused even while the port stays on `sim`.
- Sets: stripe `STRIPE_API_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PLAN_PRODUCTS`; twilio `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_SMS`, `TWILIO_TEMPLATES`; postmark `POSTMARK_SERVER_TOKEN`, `POSTMARK_FROM`, `POSTMARK_TEMPLATES`; expo `EXPO_ACCESS_TOKEN`, `EXPO_TEMPLATES`. The adapters cannot send without a template map, and no catalogue of notification copy exists in the repo, so the maps are config (JSON, template name to `{en, he}`; Expo `{title, body}`), validated at boot: both locales present, names plain own keys. `STRIPE_PLAN_PRODUCTS` is our plan code to `prod_...` id (the billing adapter's `planProducts`).
- `STRIPE_API_KEY` must be a test-mode key (`sk_test_`/`rk_test_`); a live key is refused until the production guard (T-0043). `STRIPE_WEBHOOK_SECRET` takes one or two comma-separated secrets (`secretPair`); one pair serves both the funding and the billing adapter (one container, as Terraform already had).
- Rotation window: the Stripe adapters take a single signing secret, so `createRegistry` wraps their `parseWebhook`: a delivery that verifies against the previous secret is re-signed with the current one and handed on, which keeps the adapter's own checks, de-duplication and amount cross-check. A delivery that verifies against neither goes to the adapter untouched and fails as before (`BAD_SIGNATURE`).
- Notify: `NotifyChannelRouter` (registry.ts) is bound as `notify` when any channel is chosen: sms, email and push go to their vendor, every other channel (WhatsApp included, `notify.whatsapp` is off and has no choice yet) to the notify simulator. A delivery lookup asks each adapter in turn and takes the first that knows the id; it holds no state. With nothing chosen `notify` is still the simulator itself.
- `createRegistry` binds in sandbox mode in both markets whatever the URL (going live is T-0043); `ProviderSummary` gains `funding`, `notify-sms`, `notify-email`, `notify-push`.
- Terraform (staging and prod): variables `provider_funding`, `provider_notify_sms`, `provider_notify_email`, `provider_notify_push` (default `sim`, validated) feed `PROVIDER_*`; new containers `stripe-plan-products`, `twilio-account-sid`, `-auth-token`, `-from-sms`, `-templates`, `postmark-server-token`, `-from`, `-templates`, `expo-access-token`, `-templates`; `adapter_secrets` maps each set, `provider_secrets` includes only the chosen ones, jit is forced to `sim` for all four. The unconditional `STRIPE_API_KEY` / `STRIPE_WEBHOOK_SECRET` mappings on api and worker are removed: with the new `STRIPE_PLAN_PRODUCTS` they would be a half-set credential and refuse boot on `sim`. Nothing read those two variables before.
- Sandbox runs: `packages/adapters/src/sandbox.contract.test.ts`, off unless `SANDBOX_CONTRACTS=1` and the vendor's sandbox variables are set (`SANDBOX_TWILIO_ACCOUNT_SID/_AUTH_TOKEN/_FROM/_TO`, `SANDBOX_POSTMARK_SERVER_TOKEN/_FROM/_ALIAS/_TO`, `SANDBOX_EXPO_PUSH_TOKEN` (+ `_ACCESS_TOKEN`), `STRIPE_SANDBOX_SECRET_KEY`, `STRIPE_SANDBOX_BILLING_WEBHOOK_SECRET`); CI sets none, so it is skipped there. Twilio, Postmark and Expo run the full `notifyContract`; Stripe is a three-test smoke (customer idempotency and SetupIntent, unknown PaymentIntent, forged webhook), not its contract suites, which need a vendor-signed webhook on demand and a payment method attached to a customer.
- Tests outside the Files line that had to change: `apps/worker/src/main.test.ts` and `apps/api/src/institutions/us-banking.e2e.test.ts` expected the start-up `providers` log to hold five ports; it holds nine. `apps/api/src/infra-contract.test.ts` is generic over `PROVIDER_PORTS` and passes unchanged. `docs/setup/secrets.md` lists the new containers.
Not done / not verified:

- `terraform fmt`, `validate` and `test` were not run: no `terraform` binary in the build environment. The edits copy the T-0042 layout and satisfy `infra-contract.test.ts`.
- `config/catalogue.json` was not touched: the worker's strict schema for it would refuse extra keys, and the template and plan maps went to config keys instead.
- Funding and billing webhook receivers for Stripe are not mounted; the adapters only gain their signing secrets.
- A single `STRIPE_WEBHOOK_SECRET` serves both Stripe ports. If funding and billing get separate Stripe endpoints (separate signing secrets), a second key is a small follow-up.
- Notification copy itself (the template bodies, Postmark aliases) is not written; an operator supplies it in the three `*-templates` containers.
