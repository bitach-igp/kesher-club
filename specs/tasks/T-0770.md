Decision of 2026-11-23 (session coordinator, within the card's intent; no migration, no backfill, old rows stay): DUAL-READ for the two markers whose old rows could exist in a live environment. `membership_lost_key` (`billing.stripe` has `defaultProd: true`, so a lost race can write one in any environment that sells memberships) and the payout `payee` link (`payouts.nium` is off by default, but a staging that turned it on would hold rows): the writer writes ONLY `ops.workflow_marker`; the reader checks the new marker first and falls back to the old `ops.external_ref` row (the exact old query), so a retry of an old lost key never reaches the vendor and an old payout keeps its payee in the list, the worker's input and `settle`. The sub-account purpose and owner markers switch cleanly with no fallback: `wallet.subAccounts` and `wallet.enabled` default off in `config/flags.json`, the credit port is not wired in composition, and `docs/ops/deploy-readiness.md` found no environment bootable; a pre-change `funding_subaccount_purpose` or `_owner` row is not read.
