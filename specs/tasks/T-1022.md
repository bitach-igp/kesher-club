Design:
- THE CONSOLE keeps the member's access and refresh tokens in httpOnly cookies on the server (`apps/console/src/session.ts`: `ACCESS_COOKIE`, `REFRESH_COOKIE`). `app/layout.tsx` is already a per-request server component (`dynamic = 'force-dynamic'`, reads `headers()`). It reads the preference DURING THE REQUEST (`GET /me/preferences` with the access cookie; `apps/console/src/api.ts` has no preferences method today, so ADD `preferences()` and `setTheme(theme)` to `memberApi(baseUrl, accessToken)`, which already carries the member bearer, reusing the proxy's refreshed token the way the other pages do) and renders the attribute on the `<html>` element directly: NO inline script, NO `localStorage`, NO client-side correction, so there is no flash. A pure `htmlThemeAttr(theme): { 'data-theme'?: 'light' | 'dark' }` in `src/theme.ts` does the mapping: `dark` gives `data-theme="dark"`, `light` gives `data-theme="light"`, `system` (and signed-out, and any API failure) gives NO attribute so the media query follows the system.
- EXPLICIT `data-theme="light"` IS REQUIRED FOR LIGHT. Omitting the attribute is not the same: it lets a dark system apply the `prefers-color-scheme: dark` rule. This is the main case to test.
- `apps/console/src/layout.test.ts` is a SOURCE-TEXT regex test: it asserts `/<html lang=\{locale\} dir=\{dirOf\(locale\)\}>/` and forbids colour literals in `layout.tsx`. The spread breaks that regex, so the regex is UPDATED DELIBERATELY in this card to `/<html lang=\{locale\} dir=\{dirOf\(locale\)\} \{\.\.\.htmlThemeAttr\(theme\)\}>/`, and the no-colour-literal assertion stays as it is (the helper holds attribute names, not colours).
- Use the conditional spread for the attribute (`exactOptionalPropertyTypes` is on): `<html lang={…} dir={…} {...htmlThemeAttr(theme)}>`.
- The control: a small Appearance page (System / Light / Dark) in the console, a server action in `actions.ts` that PATCHes `/me/preferences` with `{ theme }` and revalidates, linked from the console nav for signed-in staff. Strings in `apps/console/src/i18n.ts` in English and Hebrew (the console localises by `accept-language`); `i18n.test.ts` compares the key sets and flags a Hebrew string equal to its English one, so it is unaffected as long as every new Hebrew string is translated (add to its `SAME_ON_PURPOSE` list, and to Files, only if one is not).
- `apps/web` STAYS SYSTEM-ONLY: it is `output: 'export'` (static), has no session and no per-request render, so it cannot read an account preference. DO NOT add a toggle, an attribute or a script there; it follows `prefers-color-scheme` through the token CSS as it does today. Before changing ANY layout, check `apps/web/src/static-audit.ts` (it audits inline event handlers and external resources, not `<html>` attributes, verified 2026-11-23) and run it over the console build output if the console is audited too; the web app is untouched, so its audit cannot move.
- FINDING (the plan said "console and admin ... keep the token pair in httpOnly cookies"): the ADMIN app is not a member session. `apps/admin/src/auth/session.ts` holds an IAM Identity Center ID token (`kesher_admin_session`: subject, email, roles, amr); an admin has no member bearer and no `identity.member_preference` row, so there is nothing for the server to read at request time. DEFAULT CHOSEN 2026-11-23, reversible before build: admin STAYS SYSTEM-ONLY like `apps/web` (it already reskins through the token CSS from T-1019 and follows the system; no admin code changes in this card, `apps/admin` untouched). The alternative, a device-level httpOnly `kesher_admin_theme` cookie set by a small form and rendered on `<html>` by `app/layout.tsx`, is NOT the account preference (it is per browser, not per account) and needs the owner's say; if chosen, it is its own card, not folded in here.
Test first: TST-UX-003. `apps/console/src/theme.test.ts`: `htmlThemeAttr('dark')` is `{ 'data-theme': 'dark' }`; `htmlThemeAttr('light')` is `{ 'data-theme': 'light' }` (NOT empty); `htmlThemeAttr('system')` is `{}`; `undefined`, an unknown string and a failed lookup all give `{}` (the server never throws on a bad preference, it renders system); the lookup is skipped for a signed-out landing (no cookie, no API call); a refused or slow `GET /me/preferences` renders without blocking beyond the console's existing request timeout. The layout is an async server component that reads `next/headers`, so there is NO renderToString test of it (the console has none). The literal `TST-UX-003` appears in `theme.test.ts`.
