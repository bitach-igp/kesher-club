Test first: three queued messages and two publishers run concurrently on one database: every message is delivered to the sink exactly once; a sink that throws leaves the message pending with an attempt count and it is retried next tick; the job logs `{published, failed}` through `job_ran`.

## As-built
- `OutboxPublisher.publishBatch` claims its rows with `for update skip locked` in one transaction (`order by id limit n`), publishes each to the sink, and sets `published_at` in the same transaction; a second publisher skips locked rows and takes the next. A sink that throws leaves the row unpublished, adds one to `attempts` and stores the error's class name in `last_error_class` (never the message or payload); the next tick claims it again. Delivery stays at-least-once (a crash after the sink call and before commit redelivers), so sinks keep their own idempotency key (`OutboundEventsService` uses `outbox:{id}`).
- Migration `ledger/0031` adds `ops.outbox.attempts integer not null default 0` and `last_error_class text`. `ops.outbox` is not a ledger table and `club_app` already has update on it. The migration is a plain `ALTER TABLE ADD COLUMN` with a constant default (metadata-only). `atlas` is not installed in the cloud, so `atlas.sum` was recomputed with a script that reproduces Atlas' algorithm (per file: running sha256 over name then bytes; total: sha256 over name and the base64 of each file hash); it first reproduced the existing 31 lines and the old total exactly. The desktop request `handoff/desktop/T-0687-outbox-attempts.md` applies it to a real Postgres and runs a real concurrent-claim check (one session holds two rows, a second takes the others).
- `OutboxSink.publish(message, tx?)` now receives the claim transaction and `OutboundEventsService` writes `notify.outbound_message` through it. Without that, a sink that queries the database while the claim transaction is open waits forever on a single-connection driver (PGlite; it surfaced as outbound.test.ts timing out), and on a pool it would write on a second connection outside the claim. A sink that ignores `tx` still works.
- Job `outbox-publish`, scope `club` (one runner across workers; the outbox has no market column), every 10 s (`OUTBOX_PUBLISH_CYCLE_MS`), `money = false` in the alarms table (a stale drain opens a ticket; it moves notifications, not money). The sink is `app.services.outbound` (`OutboundEventsService`), the only `OutboxSink` that exists; it ignores messages that are not institution events and sends the rest through the events port, which is the simulator in tests, so it runs harmlessly. No flag was added.
- The scheduler's `job_ran` line now copies numeric `vendorReads`, `published` and `failed` from a run's result, so the drain logs `{published, failed}`; nothing else in a result is logged.
- PGlite runs one connection, so two concurrent `publishBatch` calls are serialised by the driver and the test proves exactly-once delivery with a slow sink, not true row-level parallelism; the `skip locked` behaviour itself is proved on a real Postgres by the desktop request. A failing message stays at the head of the id order, so more than `limit` permanently failing rows would starve later ones; `attempts` makes that visible and a dead-letter rule is left to T-0688 (replay).
- The worker job count is 26 and the stale-job alarm count is 26.
- Per-message savepoint (review): each message runs between `savepoint outbox_msg` and `release savepoint outbox_msg`; on a throw the publisher runs `rollback to savepoint outbox_msg` before it records `attempts` and `last_error_class`. Without it a SQL error inside the sink (through `tx`) leaves the transaction aborted (25P02), the bookkeeping update throws, the whole batch rolls back and the bad row repeats every cycle; and a sink that wrote through `tx` before throwing would leave that write behind. Two tests cover both (a bad insert on `tx`, and a write then a throw); both fail without the savepoint (PGlite does return "current transaction is aborted"). The handoff step 9 repeats the abort-then-recover on real Postgres; it is piped on stdin because one `psql -c` stops at its first error.
- Follow-up, not in this card: an alert on `attempts >= N` (or the oldest unpublished age) so a stuck message pages someone.
