Test first: Terraform creates empty containers under `kesher/<env>/…` (`infra/terraform/README.md` step 5: 'load each with put-secret-value') but nothing says what a valid value is or generates one. `tools/secrets` generates and loads, for one environment: `jwt-signing-key` (the format `config.ts` accepts), `pii-data-key` and `pii-index-key` (32 bytes, different from each other: config refuses equal keys), `staff-jwks`, `admin-api-signing-key`; it refuses to overwrite a non-empty secret without `--rotate`, never prints or logs a value, and checks each value against the same schema the process uses before storing it. `docs/setup/secrets.md` lists every container with its source (vendor dashboard or generated), who may read it, and the rotation procedure for the JWT key (publish the new kid, keep the old for the access-token lifetime), the PII data key (re-seal job, since fields are sealed with a blind index, T-0024: a rotation card is opened when first needed), webhook secrets (two values for the overlap window) and the database passwords (T-0044 task). The webhook provider IP ranges (`webhook_provider_cidrs`) and their source are listed there too.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; CI's terraform job green when `infra/` changed; only listed files touched
Out of scope: rotating the PII data key (requires a re-seal job, its own card); vendor-issued secrets. Stop and ask on conflict with the spec.
As built:
- `tools/secrets` generates `jwt-signing-key` (ES256 JWK), `pii-data-key` and `pii-index-key` (32 bytes, distinct), `admin-api-signing-key` with its public half `staff-jwks` (one key pair, kid `kesher-<env>-admin-1`) and the four `db-*-password` secrets. It checks each value with the same rules as the process config, loads it with `put-secret-value` reading it from stdin (`file:///dev/stdin`), keeps a secret that already has a value unless `--rotate`, stops on a missing container or any other AWS error, and prints names and outcomes only.
- `apps/api/src/secrets-tool.test.ts` loads generated values through `loadApiConfig` and `loadWorkerConfig`, so a schema change the tool does not follow fails CI.
- `docs/setup/secrets.md`: every container with its source and reader, the webhook CIDR rule, and a rotation procedure per secret. Honest limits recorded there: the API has one JWT signing key (no overlap), and PII key rotation needs a re-seal job that does not exist.
- The three `db-*` secrets other than `db-app-password` are created by T-0044 (PR #233); until it merges, `--only` leaves them out.
- The tool was exercised against a fake AWS CLI; no AWS account was touched. A first real run belongs to T-0060.
