Test first: TST-WAL-003. The port shape is `creditWallet(input: { loadId: string; accountRef: string; amount: Money }, idempotencyKey: string): Promise<{ status: 'credited' | 'pending' | 'refused'; reasonCode?: string }>` on `FundingCreditPort`, a separate interface in the `FundingStatementPort` style, found on the `funding` binding by `isFundingCreditPort(port)` (all methods exist, as `isMirrorPort` does). Contract block (runs only when the factory passes `credit: { ... controls }`): a settled load credited once answers `credited`; the same key twice answers `credited` and the control shows ONE credit for the load; a different key for a load already credited answers `credited` and makes no second credit (the credit is per load, the key only makes a replay safe); an amount other than the load's, or a currency other than USD, is `VALIDATION_FAILED` with nothing credited; a load that is not settled at the vendor (processing, requires_action, failed, returned) answers `refused` with `reasonCode: 'NOT_SUCCEEDED'` and nothing moved; an unknown `loadId` is `UNKNOWN_LOAD`; an `accountRef` the vendor does not know is `refused` with `reasonCode: 'NOT_FOUND'`; the control `failNext('INSUFFICIENT_FUNDS')` makes the next credit `refused` with that code and a LATER call with a NEW key credits (a refusal is final for its key, as the vendor's is, T-0718); the control `pendNext()` makes the next call answer `pending` and the SAME key later answers `credited` with one credit; the control `outageNext()` is `PROVIDER_UNAVAILABLE` (nothing moved, safe to resend). Simulator test: `new FundingSimulator(clock, { credit: true })` passes that block and `new FundingSimulator()` has no `creditWallet` (so `isFundingCreditPort` is false and every existing simulator, Stripe-adapter and loads test is unchanged).
- `reasonCode` is a short closed string chosen by the port, never vendor text: `NOT_SUCCEEDED`, `NOT_FOUND`, `INSUFFICIENT_FUNDS`, `ACCOUNT_UNAVAILABLE`, `PAYMENT_FAILED`. It is a `string` in the type so an adapter can add one; the caller (T-0705) only logs and cases it.
- Only `loadId`, `accountRef`, amount and key cross the port. No member name, mobile or memo text; the adapter makes its own memo (T-0741).
- Unknown outcome: an adapter that cannot tell whether the vendor moved the money answers `pending` (never a new key), and the caller retries with the same key. There is no new error code.
