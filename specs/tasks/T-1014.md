# T-1014 [AGT] Authorization server, part 1: discovery, JWKS and the authorization request

Test first: TST-AGT-010 (request rows). Per ADR-009, behind `mcp.enabled`:
- `GET /.well-known/oauth-authorization-server` (RFC 8414): issuer, endpoints, S256 only, `authorization_code` and `refresh_token`, `client_id_metadata_document_supported`, the scopes of REQ-AGT-005.
- `GET /oauth/jwks`: the signing key's public half.
- `GET /oauth/authorize`:
  - checks the client through the CIMD registry (T-1003), and that `redirect_uri` exactly matches the document;
  - requires `response_type=code`, an S256 `code_challenge`, `resource` set to the MCP URL, known scopes and a `state`;
  - stores the request for 10 minutes in `agent.authorization_request` and answers 302 to the member app's consent URL with the request id;
  - a bad request whose redirect URI is trusted goes back to the client with an RFC 6749 error and the state; otherwise 422 VALIDATION_FAILED at Kesher.
- Migration `agent/0002` holds `agent.authorization_request` and `agent.refresh_token` (T-1016 writes the second).

The tests cover:
- the metadata names S256 only;
- a good request redirects to the consent URL and stores what was asked;
- a redirect URI not in the document answers 422 and never redirects;
- `plain` PKCE, a missing `resource` or another resource, and an unknown scope each redirect back with `invalid_request` or `invalid_scope` and the state;
- a client document on a private address is refused;
- with `mcp.enabled` off, 404.

Done when: listed tests pass; Spectral clean; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace`, `pnpm db:lint` green; the migration applied on Postgres 16 through the desktop handoff; only listed files touched
Out of scope: consent (T-1015), tokens (T-1016), the app screen (T-1017). Stop and ask on conflict with ADR-009.

As built:
- **The service.** `apps/api/src/oauth/authorize.ts` holds `AuthorizeService` and the three handlers; `metadata.ts` builds the RFC 8414 document.
  - All three routes are public in `routes.ts` (the member arrives without a token) and answer 404 while `mcp.enabled` is off.
  - They sit at the root, and the contract gives each a path-level root server. `/v1/oauth/authorize` reaches them too, since dispatch strips the prefix.
- **The order of checks.** First the client: the SSRF-guarded registry (T-1003) refuses http, private hosts, redirects and oversized documents. Then the exact redirect URI. Faults in either answer 422 VALIDATION_FAILED at Kesher and never redirect.
- **Errors sent back to the client.** After those checks pass, faults go to the client's redirect URI with the state, in this order:
  - a missing or overlong state (sent back without one);
  - `response_type`, answered with `unsupported_response_type`;
  - S256 PKCE, `invalid_request`;
  - `resource`, `invalid_target` per RFC 8707 rather than the card's `invalid_request`;
  - the scopes, `invalid_scope`.
- **A stored request** keeps the client, redirect URI, deduplicated scopes, state, PKCE challenge and resource for 10 minutes, then sends the browser to `{consentUrl}/{id}`.
- **Configuration.**
  - The consent URL comes from `MEMBER_APP_URL` (`/connect` appended) in `main.ts`, or else the app's `kesher://connect` link.
  - The resource defaults to `{issuer}/mcp`.
  - `createApp` takes `oauth` and `cimd` (DNS and fetch) so tests run without the network.
- **Signing.** The JWKS is the member token service's key: one issuer, separate audiences (ADR-009).
- **Migration `agent/0002`** also creates `agent.refresh_token` for T-1016. The real Postgres apply is in `handoff/desktop/T-1014-atlas-apply.md`.
