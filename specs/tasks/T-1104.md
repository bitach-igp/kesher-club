# T-T-1104 [PAY] Invite someone to receive: a send to a phone number with no account starts an invite and moves no money until they have joined
REQ: REQ-PAY-001 (enabling; phase 1 gap analysis `docs/ops/phase-1-gap-analysis.md`, founder notes 2026-11-25) · Sprint: phase 1
Files: apps/api/src/p2p/recipients.ts, apps/api/src/p2p/recipient-invite.ts, apps/api/src/p2p/recipient-invite.test.ts, db/migrations/ledger/NNNN_recipient_invite.sql (+ atlas.sum), apps/api/src/routes.ts, contracts/openapi.yaml, packages/sdk (generated), apps/mobile/app/pay/**, apps/mobile/src/i18n.ts, handoff/desktop/T-1104-recipient-invite.md, specs/tasks/T-1104.md, specs/tasks/README.md
Test first: Today a phone that is not a verified member answers an indistinguishable 404 (T-0530) so nobody can probe who is a member, and the sender is stuck. Test first: the sender explicitly chooses 'invite them' (the 404 stays the default, so probing stays closed); the invite records the sender, a hash of the phone, an amount hint and the category the sender names, expires in 14 days (like REQ-PAY-004) and sends one text through the notify port (a rate limit per sender per day); NO money moves, no hold and no journal exist until the invitee has joined and passed T1, then the sender is told and the send is the ordinary send (limits, new-pair hold, idempotency unchanged); an invite to an existing member behaves as a normal send. This avoids holding customer money for someone with no account, which ADR-018 says we may not do. The phone is stored hashed and sealed, never logged.

Out of scope: Holding funds for a person who has no account (counsel; ADR-018); request links (T-1109).
Crowded cross-reference (2026-11-25, docs only, no vendor call): Crowded has an email-invite route for a sub-account owner, but it creates a treasurer with full account access and the owner self-onboards; it does not hold money for a person who has not joined, and Crowded banks entities only. The 'no money moves until joined' rule here stands. A hosted-page payment needs a contact with a mobile number and an intent without one gets a placeholder mobile that cannot receive SMS (api-inventory section 7).

As built:
- **Three routes, all dark.** `POST /p2p/recipient-invites` (`createRecipientInvite`), `GET /p2p/recipient-invites` (`listRecipientInvites`) and `POST /p2p/recipient-invites/{id}/claim` (`claimRecipientInvite`). Each needs the bearer, a sender outside the 24-hour recovery hold, and both `p2p.enabled` and the new flag `phase1.recipientInvite` (off in production, not a money flag); with either off they answer 404 `FEATURE_OFF`. None moves money, so none takes a step-up or an Idempotency-Key (the sender and the phone name the invite; claiming is idempotent by invite). The handlers live in `recipient-invite.ts` (composed in `app.ts`); `handlers.ts` is untouched.
- **The 404 is unchanged.** `POST /p2p/recipients/resolve` and the send answer exactly as before; `recipients.ts` only gained the shared `normalisePhone` (same input, same refusal). The invite is a separate, explicit sender action.
- **What an invite stores** (`ops.recipient_invite`, ledger migration 0035): the sender, the phone's blind index (HMAC-SHA256 under the T-0024 index key, column context `ops.recipient_invite.phone`), a sealed copy of the phone, an optional amount hint (`Money`, bigint minor plus currency, never in the text), the sender's category from a closed set, and 14 days. The sealed copy is needed twice: for the one text, and to check later whether a number that was already a member now qualifies. It is cleared (set null) when the invite ends (`claimed` or `expired`). The phone is never returned, logged or stored in plain; the category is a closed list, so the sender's words never reach a text or an instruction.
- **Categories.** `soldier, lone_soldier, yeshiva_student, seminary_student, university_student, rabbi, volunteer, program_participant, other`. T-1101 (PR #428) defines the same set for the profile and is not merged, so the list is spelled locally with a TODO to unify. The column carries a CHECK on the same list.
- **One text.** Exactly one SMS through the notify port, template `p2p.invite`, keyed `invite:{id}:sms`, no data (no sender name, note, category or amount; Hebrew for a `+972` number). A repeat by the same sender returns the live invite with 200 and the same key, so no second text; if the first text failed (`PROVIDER_UNAVAILABLE`, answered 503) the invite stays and asking again sends it once.
- **Rate limit.** `INVITES_PER_DAY = 10` new invites per sender in any 24 hours, counted from the table (so it holds across API processes) and judged under `pg_advisory_xact_lock(hashtextextended('recipient-invite:' || sender, 0))`. Repeating an open invite is not counted; the 11th answers 429 `RATE_LIMITED`.
- **State machine.** `open -> claimable -> claimed`, and `open | claimable -> expired`. A status column the app may change (column-level `update` grant on `status, recipient_party_id, phone_sealed, updated_at` only: who, which phone and the hint can never change; no delete) plus `ops.recipient_invite_event`, insert-only, unique per `(invite_id, to_status)`, so a state is entered once and a race has one winner. Every transition is a conditional update plus its history row in one transaction. A unique partial index keeps one live invite per sender and phone; a live invite past its 14 days is ended before a new one for the same number is made.
- **Join.** The KYC webhook (`app.ts`, after the roster hook) calls `onIdentityApproved(party)`: a verified, T1-approved member's phone finds every open, unexpired invite for it, makes each `claimable`, and tells the sender once (`p2p.invite_claimable`, keyed `invite:{id}:claimable`, so a replayed event or a retried text never double-sends). An account without T1, someone else's approval, and an approval after the 14 days change nothing.
- **Claim.** `claim` answers `{ invite, recipient: { partyId, displayName?, canReceive } }` and moves nothing; the sender then sends with `POST /transfers` to that `partyId`, whose limits, ₪500 new-pair hold and Idempotency-Key are unchanged (the test sends ₪600 and gets `pending_hold`, and a replay of the key is the same transfer). Another sender, or an unknown id, gets the same 404; an open invite and an expired one answer 409 `IDEMPOTENCY_CONFLICT`; the same sender claiming again, or three claims at once, get the same answer and one history row.
- **A number that is already a member.** The create response is the same as for anyone (201, `open`, the same body shape, the same text), because create never looks the number up. It becomes `claimable` when the sender next lists or claims (a lazy check that opens only that sender's sealed phones, at most 200), and the sender is told the same way. This adds no new probe: `resolve` already tells any member whether a number is a member, 30 a minute, and this route is capped at 10 new invites a day. Decision for the owner: if even that is too much, add an invitee-side accept step before `claimable` (not built).
- **Money.** No journal, hold or transfer is created or referenced by an invite; the test counts journals and transfers before and after.
- **Contract and app.** Spectral clean, SDK regenerated, `routes.ts` equals the operations; no new Problem codes. Mobile: a typed phone that answers "not a member" can show "Invite them to join" when the screen is given an `inviteRecipient` dependency; `usePayModel` does not pass one yet because `PayApi` and the client live in `apps/mobile/src/api.ts`, which is not on this card's Files line, so the button stays hidden until a follow-up wires `POST /p2p/recipient-invites` there. English and Hebrew copy mirrored, no product name in it.
- **Not built.** The worker does not sweep `expireDue` (expiry is applied on every list, claim and create, and `expireDue(now)` exists for a sweep); no cancel route; a per-phone cap across senders (a stranger's number can be texted once per inviting sender, each limited to 10 a day).
- **Desktop.** `handoff/desktop/T-1104-recipient-invite.md` applies the migration to real Postgres 16, checks the constraints and grants as `club_app`, and runs two simultaneous invites (with the lock, and without it to show the unique index) and a claim race under READ COMMITTED. Unverified until it runs. `atlas` was not installed here: `atlas.sum` was written with Atlas's hash (a running SHA-256 over each file's name and bytes, then a hash over the name and hash pairs), reproduced and first checked against the existing ledger and identity sums, which it matches byte for byte.
