## As built
- **Mapper** (`stripe/funding.ts`): an ACH `requires_payment_method` with a `last_payment_error` is `failed` (the failure code is the decline code, else the code). A card intent in that state stays `requires_action`: Stripe puts a declined card attempt there too and the client can confirm the same intent again, so failing it would drop a payment collected later. Without an error it is a fresh intent (`requires_action`). The "or after the intent was `processing`" half of the card is not built: the mapper sees one object and has no prior status, and Stripe records the return in `last_payment_error`, so the error is the signal.
- **Fake** (`stripe/fake-stripe.ts`): `settlePaymentIntent(id, 'returned')` returns a debit to `requires_payment_method` with `last_payment_error` (decline code `insufficient_funds`), as Stripe does; `'failed'` stays `canceled`; `'reset'` is `requires_payment_method` with no error. `last_payment_error` now comes from the intent's own state.
- **Release** (`wallet/loads.ts`): `LoadService.release` asks the port for the load before moving money; a `failed` load goes through `fail` (the pending journal is reversed once, key `{holdKey}:reversal`) and the transfer is `failed`. A port error (outage) leaves the hold where it is and the job retries next cycle.
- **Release vs. return race.** Journal and transfer row are separate transactions, so a return can land at several points. `fail` decides on the row as it is **now** (not on the caller's read, which may predate a hold that has since posted): while the money is held (`pending_hold`, or `pending` once a release has begun) it reverses the hold journal and any release journal, each found by its key (`{hold}:reversal`, `{release}:reversal`). If the row turns out to have moved on to keep the money (`settled`, `cancelled`: the release won), it undoes those reversals (`:undo`); while the row is still held it undoes nothing, so a transient error and a retry finish the same work. `release` re-reads the row and refuses (`IDEMPOTENCY_CONFLICT`) when it is no longer `pending_hold` or when the hold was already reversed, so a release is not posted behind a return; and it reverses its own journal (`{release}:reversal`, the same idempotent key `fail` uses) when either of its two state changes finds the load failed. Each reversal posts at most once (its key and `reverses_id` are unique).
  - **Windows that remain** (one transaction for journal and state is the systemic fix, review F09/F13, its own card): (a) a return fails the load in the instants between `release`'s re-read and its journal post, and the process dies before `release` compensates, leaving a release journal on a failed row that nothing repairs; (b) a stale `fail` runs against a load that is just settling and the process dies between its reversals and the undo. Both need a crash inside a window of a few statements.
  - **Decided by Zvi (2026-11-04): push it through** on the choices recorded here (release unless the vendor says `failed`, below) with these windows accepted.
- **Deviation from the card (stop-and-ask not possible, decision recorded here).** The card says release "only when `succeeded`". That would break TST-WAL-003, which releases a Monday ACH on Thursday while the vendor still says `on_hold` (the ACH hold-days product: the bank's hold days govern, not a vendor confirmation). I release unless the vendor says `failed`. If the owner wants "only when `succeeded`", that is a product change to REQ-WAL-003 and needs its own card.
- **Sweep** (`loads.ts` `stale`): `pending_hold` loads are included, ordered after `submitted` ones so held loads cannot starve them under the limit. Each cycle the worker therefore asks the vendor about every held load past the stale window (up to the limit); a `succeeded`/`on_hold` answer leaves them held, a `failed` answer fails them and reverses the hold.
- **Release job** (`release-holds.ts`): counts `released` only when the transfer reached `settled`.
