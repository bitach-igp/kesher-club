## As built
- **Mapper** (`stripe/funding.ts`): `requires_payment_method` with a `last_payment_error` is `failed` (the failure code is the decline code, else the code); without an error it stays `requires_action` (a fresh intent). The "or after the intent was `processing`" half of the card is not built: the mapper sees one object and has no prior status, and Stripe records the return in `last_payment_error`, so the error is the signal.
- **Fake** (`stripe/fake-stripe.ts`): `settlePaymentIntent(id, 'returned')` returns a debit to `requires_payment_method` with `last_payment_error` (decline code `insufficient_funds`), as Stripe does; `'failed'` stays `canceled`; `'reset'` is `requires_payment_method` with no error. `last_payment_error` now comes from the intent's own state.
- **Release** (`wallet/loads.ts`): `LoadService.release` asks the port for the load before moving money; a `failed` load goes through `fail` (the pending journal is reversed once, key `{holdKey}:reversal`) and the transfer is `failed`. A port error (outage) leaves the hold where it is and the job retries next cycle.
- **Deviation from the card (stop-and-ask not possible, decision recorded here).** The card says release "only when `succeeded`". That would break TST-WAL-003, which releases a Monday ACH on Thursday while the vendor still says `on_hold` (the ACH hold-days product: the bank's hold days govern, not a vendor confirmation). I release unless the vendor says `failed`. If the owner wants "only when `succeeded`", that is a product change to REQ-WAL-003 and needs its own card.
- **Sweep** (`loads.ts` `stale`): `pending_hold` loads are included. Each cycle the worker therefore asks the vendor about every held load past the stale window (up to the limit); a `succeeded`/`on_hold` answer leaves them held, a `failed` answer fails them and reverses the hold.
- **Release job** (`release-holds.ts`): counts `released` only when the transfer reached `settled`.
- **File outside the card's list:** `apps/worker/src/wallet/load-workflow.test.ts`: the sweep's counts in two tests include the held ACH load an earlier test leaves behind.
