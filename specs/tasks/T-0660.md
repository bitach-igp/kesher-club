## As built
- **`apps/simulators/src/crowded-http.ts`** (new): `CrowdedHttpSimulator` serves a Crowded backend under `/crowded/api/v1`. Bearer auth is checked here (401 without it, except the public `GET /webhooks/event-types`); everything else is handed to `FakeCrowded.fetch` as it is, so the `data` envelope, `meta.pagination` paging, the documented errors and the 201-with-`Rejected` come through untouched. A body that is not JSON is Crowded's 400, never an exception. The webhook management endpoints the script uses are implemented here (`POST/GET /webhooks`, `GET/DELETE /webhooks/{id}`; a soft delete, a secret shown once on create, HTTPS only except loopback `localhost`/`127.0.0.1`); `fake-crowded.ts` is not touched.
 - **Webhooks out.** `queue` builds one entry per active, subscribed registration with the exact bytes to send; `attempt` signs those bytes (`sha256=` + HMAC-SHA256 under the registration's own secret, `node:crypto`) and POSTs the same `Uint8Array`, so what is signed is what is sent (`X-Webhook-Batch`, `-Batch-Count`, `-Attempt`, `User-Agent: Crowded-Webhooks/1.0`, the custom `Authorization` if one was registered). At least once: a non-2xx or an unreachable receiver leaves the entry pending and `flush()` tries again with the same bytes, up to `MAX_DELIVERY_ATTEMPTS` (10) tries, after which it is abandoned; `at_most_once` abandons on the first failure. Deleting a registration drops its queued deliveries (one already in flight may still complete). `redeliver(batchId)` sends a delivered batch again byte for byte (the duplicate). Switches: `outOfOrder` (batches wait; `flush` releases them newest first) and `badSignature` (signs with another key). The receiver's secret and the simulator's HMAC key are one thing: the secret the script registered (`CROWDED_WEBHOOK_SECRET`). The `sha256=fake` placeholder of `FakeCrowded.webhook()` and the port simulator's `sha256=sim` are never used: the batch's events are taken from the fake and re-signed here. A registration's URL is stored exactly as given (no `URL.toString()` normalising).
 - **Controls** (`decide`, `pay`, `settleAch`, `returnAch`, `deliver`, `redeliver`, `outOfOrder`, `badSignature`, plus `emit` for any event). `settleAch` takes an ACH pending, processing, sent and announces each step. **`returnAch` only returns a `sent` payment** (pending, processing, canceled and failed are refused): `FakeCrowded` has no returned control and `fake-crowded.ts` is not on the card, so the simulator answers every read of that payment as `returned` from then on and sends `finance.ach_payment.returned`. The fake's balances are not touched (a real return would credit the account back).
- **`server.ts`** (shared with the OIDC, assistant and port panels: say so in the PR): `PanelContext.crowded` and `createServer(host, { crowded })`; `handle()` mounts `/crowded` before the JSON parse (it reads its own body) and passes the bearer from `ctx.headers`; the panel page lists the controls as forms that post to `/crowded/control/<name>` (the form script uses `data-url` when there is one). The control hooks live there and not in `host.ts` (not on the card). Nothing changes when no Crowded simulator is passed.
 - **`tools/crowded-webhooks.mjs`**: `--simulator` accepts an `http://localhost[:port]` base URL, and an `http://localhost[:port]` receiver URL only when the base URL is localhost too, so a local receiver is never registered against a remote Crowded. For both schemes the receiver URL is the same shape: the host, then an optional `/v1`, then `/webhooks/crowded` (`localhost.evil.example`, `127.0.0.1`, other hosts and other schemes are refused). Every https case is unchanged.
- **`docs/vendors/crowded/README.md`**: "Run it locally" with the one command (`pnpm --filter @kesher/api exec vitest run src/institutions/us-banking.e2e.test.ts`) and what `--simulator` does. The secret there is `CROWDED_WEBHOOK_SECRET`, singular, as T-0659 noted.
 - **The end-to-end test** (`us-banking.e2e.test.ts`): the panel server and the API's own `createServer` each listen on a random port; the real script registers `http://localhost:<api port>/webhooks/crowded` against the simulator; the simulator's batches go over HTTP to `/webhooks/crowded`. The API is started from its config, as a deployment sets it: `loadApiConfig` with `PROVIDER_INSTITUTION_BANKING=crowded`, then `overridesFromConfig(config, db)` and `createRegistry` bind the port — **the config-built adapter, with the `PostgresVendorKeyLedger` the override builds, runs every flow** (no hand-built adapter is swapped in). The three adapter options the config has no key for yet (T-0659 "Not done": the sub-account contact, Kesher's collection counterparty, the payer's consent) ride on the override, which `registry.ts` now forwards (touched as shared plumbing, like T-0659's `package.json`); config keys for them are a later card. PGlite has one connection held by an open transaction, so the e2e routes every query through the currently open transaction: the key ledger joins `link()`'s transaction instead of waiting on it (production Postgres has a pool). Config is asserted (`providers`, the binding), and the platform's own entity is created through that adapter, which reads the bank over HTTP. Flows: (1) a platform institution is a sub-account, an institution on its own entity is `pending`, the simulator approves, the event is stored with a good signature and changes nothing until the worker's replay (`app.services.webhooks.replay`), then `approved`; `moneyOpen` and the quote/collect calls stay closed (FEATURE_OFF) until our KYB decision; (2) a US fee batch is collected, paid on the simulator, the batch delivered twice (`stored: 0, duplicates: 1`), a further event for the same payment replayed: one `payment` row, item paid once; (3) ACH funding with a second approver, the KC- reference in `addenda`, `settleAch` to `sent`, the bank credit posted by the deposit path links the request (`received`); a **sent** ACH returned by `returnAch` shows `returned` and opens one case however often it is told; (4) a wrong signature answers 401, lands in `ops.inbound_rejected` (reason `MISMATCH`, a hash, no body), claims no event id, and the retry with the right key is stored; no and malformed signatures are refused the same way. Out of order: two application events and the two ACH steps are delivered newest first through the `outOfOrder` + `flush` path (asserted on the simulator's delivery order) and leave the re-read state, one `ach_status` row.
- **Decisions where the brief and the card disagreed with the code:**
  - *https only.* `CrowdedClient` and the config require https and neither is on the card. The e2e keeps `CROWDED_BASE_URL=https://crowded.sim.invalid/crowded/api/v1` and a `fetch` that sends it to the simulator on loopback; nothing in the adapter or the config is weakened. The simulator accepts plain http only for a loopback receiver URL.
  - *The adapter in the registry (owner decision, Zvi).* The e2e runs T-0659's wiring end to end: `overridesFromConfig(config, db)` — including the `PostgresVendorKeyLedger` it builds — plus `fetch` pointed at the HTTP simulator, and the three adapter options the config has no key for yet (the sub-account contact, Kesher's collection counterparty, the payer's consent) on the override, which `registry.ts` now forwards (`CrowdedBankingOverride` gained those optional fields; `registry.ts` touched as shared plumbing, like T-0659's `package.json`). No adapter is built or swapped by hand. PGlite's single connection is handled in the test: queries go to the currently open transaction, so the Postgres ledger joins `link()`'s transaction instead of waiting on it.
  - *@kesher/adapters in `apps/simulators`* is a devDependency now (`package.json` and the lockfile, shared plumbing): `crowded-http.test.ts` imports the client, the fake and the verifier from the package, not by path. `crowded-http.ts` itself still imports nothing from the adapters (structural backend, `node:crypto` HMAC). `@kesher/simulators` exports only `index.ts` (not on the card), so the e2e still imports `CrowdedHttpSimulator` by relative path; a later card can add the export and an entry in `index.ts` that starts the simulator with Crowded mounted (today only tests construct it).
  - *"Approved only after our KYB" (owner decision, Zvi).* Read as the existing rule: the link's status follows the bank — it may already show `approved` — and `moneyOpen` (collections, funding) stays closed until the KYB decision passes.
  - *Crowded has no `settled`.* `sent` is the end of the bank's side; the deposit path posts the credit and links the request (the existing T-0653 behaviour, by amount among sent requests).
  - *Replay.* The receiver only stores; the e2e drives `webhooks.replay` itself, as the worker's job does.
