- `crowded-http.ts` serves `FakeCrowded` over HTTP under `/crowded/api/v1` with Crowded's shapes as documented in `docs/vendors/crowded/api-inventory.md` (the `data` envelope, paging, 201-with-Rejected, the webhook management endpoints the script uses). It signs and POSTs batched webhooks (`X-Webhook-Signature: sha256=` over the raw bytes) to the registered URL, at least once and optionally out of order (a control-panel switch).
- `server.ts` mounts it beside the other simulators; the control panel can decide an application, pay a collection and settle or return an ACH.
- `tools/crowded-webhooks.mjs` accepts an `http://localhost` base URL only when `--simulator` is passed, so the same script registers our receiver against the simulator.
- `us-banking.e2e.test.ts`: the API with `PROVIDER_INSTITUTION_BANKING=crowded` pointed at the HTTP simulator on a random port, then:
  1. link an institution (platform holder with sub-accounts, and institution holder); the simulator approves, the webhook arrives, status becomes approved only after our KYB too;
  2. bill a US fee, pay it on the simulator, the webhook marks it paid once (deliver the batch twice);
  3. fund the master account by ACH, the simulator settles it, the request links to the deposit; then a returned ACH opens a case;
  4. a delivery with a wrong signature is refused and logged in `ops.inbound_rejected`.
- Record in the vendor README how to run it locally (one command).
**Tests.** the four flows above; an out-of-order delivery leaves the state the re-read returned; the simulator's paging matches the adapter's iterator.
