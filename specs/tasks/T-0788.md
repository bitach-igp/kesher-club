Source: T-0787's Follow-up (the three open questions: only `resolved` clears; whether clearing proves the owner is fixed; the reopen variant). The owner delegated all three to the coordinator, who decided on 2026-11-23:
1. ONLY a `resolved` decision on a `subaccount_owner_failed` case clears the marker. `dismissed` does NOT: staff chose not to fix the owner, so credits to that party stay blocked.
2. NO live re-read of the owner's status before clearing. Resolving is staff's word that the owner is fixed. Why it is safe: if staff resolve while the owner is still failed at the vendor, the next credit gets a real refusal from the vendor, which opens a `load_credit_refused` case (the load fails safe, it is never credited wrongly). A live re-read is not possible today anyway: `MemberSubAccountPort.subAccount(ref)` returns status and balances only; `ownerStatus` comes back once, from `ensureSubAccount`. The future hardening is the new Crowded question 74 in `docs/vendors/crowded/README.md` (is there a GET that says the owner is no longer failed?), NOT BUILT.
3. A dismissed or resolved owner case with the marker still set REOPENS when a load is blocked by it (the reopen variant T-0763 left out). A deliberate small behaviour change, the same principle as T-0786: no more silent block with no open case.
Design:
1. `OpsCases.decide` (`admin/cases.ts`): inside the decision's own transaction, after the case update and before the audit line, a `resolved` decision on kind `subaccount_owner_failed` calls `clearMarker(tx, { kind: ownerKind(provider), subjectId: payload.partyId })`. Case decision and delete are ONE transaction (both in the ledger database, `ops.*`): a failure of the audit write or of the delete rolls back both, and the replay is refused (409, the case is decided) before it reaches the delete; a clear of an absent row returns false and is harmless. `OpsCases` takes the funding provider as a third, optional constructor argument (the marker's kind carries the provider; `createApp` passes the funding binding's provider, `'simulator'` by default); without it nothing is cleared. A payload with no usable `partyId` clears nothing and the decision still stands. The audit line gains `markerCleared: true|false` for this kind only. `clearMarker` has exactly one caller in non-test code.
2. The kind joins `OPS_CASE_KINDS` (the generic admin path filters on it, so the owner case was invisible to `get` and `decide` before: NOT_FOUND). Mirrored additively: `OpsCaseKind` in `contracts/openapi.yaml` (response property and the `kind` query filter), the regenerated SDK, the admin console's `OpsCaseKind` type and `KINDS` / `KIND_WORDS` (plain words for staff). oasdiff reports the new enum value on four responses as it did for `kyb_application` (T-0632): `contracts/oasdiff-ignore.txt` lists the same four lines with the same reason (the admin console is ours, ADR-013, and ships in the same change). No new operation, so `routes.ts` is unchanged.
3. `ownerBlock` (`load-credit.ts`) and the failed-owner write in `sub-accounts.ts` open the case through `reopenableCase` (`load-cases.ts`) instead of `openCase`: an `open` or `investigating` case is left alone (no duplicate, fields untouched), a `resolved` or `dismissed` one is reopened with the earlier decision kept in the payload under `reopened`. The dedupe key `subaccount-owner:{party}` is unchanged. Cost: staff who dismiss the case while the marker stands see it reopen on the next sweep cycle that blocks a load for that party; to stop that, resolve it (which clears the marker) or leave it open.
Test first: TST-WAL-003. `admin/owner-cases.test.ts` (PGlite, the HTTP decide route): the owner case is listed, readable and filterable; resolved deletes the marker and the audit line says so; dismissed keeps the marker; support gets 403 and nothing changes; a replayed resolve is 409 and does not clear a marker written later; resolving with no marker present succeeds; clearing party A under provider P leaves party B and A under another provider; resolving or dismissing any other case kind that names the party never touches the marker; a payload with no usable party id clears nothing; no provider configured clears nothing; atomic both ways (a failing audit write and a failing delete each leave the case open AND the marker). `loads.test.ts` (the owner describe): resolve through `OpsCases` then the sweep credits once under `{wf}:credit:1`, one journal, balance equals the load; dismiss keeps the marker, credits stay blocked, the next blocked sweep reopens the case with `reopened.was = dismissed` and a further sweep changes nothing (not duplicated); a case resolved without a clear reopens on the next blocked load; A's resolve does not unblock B. `sub-accounts.test.ts`: a failed owner whose case is already closed reopens it.
