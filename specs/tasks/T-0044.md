Test first: `db/README.md` says 'prod applies from CI with the `club_migrator` secret', but the RDS instance is in isolated subnets (a runner cannot reach it) and no Terraform resource, workflow or image does the apply: the only in-VPC task is the preview `db-tool` (psql only, no Atlas), and the `club_migrator` secret does not exist among the secret containers. Add a one-off Fargate task `migrate` per environment on an image holding the repo's `db/` directory, a PINNED Atlas binary (`migrate.mjs` pulls `arigaio/atlas:latest` today) and node. It (1) runs `roles.sql` as the RDS master user (managed master secret), (2) sets the passwords of `club_app`, `club_jit`, `club_readonly` and `club_migrator` from Secrets Manager (new containers `db-jit-password`, `db-migrator-password`, `db-readonly-password`), (3) runs `node db/migrate.mjs` as `club_migrator`. Idempotent, safe to run on every deploy, exits non-zero on any failure, never logs a password or a URL with one. Tests: `migrate.test.mjs` plans the three steps in order and refuses a missing secret; `terraform test` asserts the task runs in the private subnets with no public IP and its role can read only those secrets.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; CI's terraform job green when `infra/` changed; only listed files touched
Out of scope: running it from a workflow (T-0050); the contract-step policy (`db/README.md` stays the rule). Stop and ask on conflict with the spec.
As built:
- `db/prepare.mjs` is the task's entry (`node db/prepare.mjs`): `planPrepare` returns the three steps, `run` executes them and prints only `ok`/`FAIL` and the step name. Passwords reach psql through its environment (`\getenv`) and the migrator through `ATLAS_URL`; the tests assert no password is in any argument or statement. TLS follows the task's `PGSSLMODE` / `PGSSLROOTCERT` (Terraform passes `verify-full` and the RDS bundle), so a local database without TLS runs the same code.
- A gap found while writing it: `roles.sql` revokes `CONNECT` on the database from PUBLIC and grants it to nobody, and gives `club_migrator` no `CREATE`, so on a database that was not created by a superuser no service role could log in and no schema could be created. Step 2 grants both; `roles.sql` is unchanged.
- `tools/migrate/Dockerfile`: node 22.22.0, `postgresql-client`, the Atlas binary from the pinned `arigaio/atlas:1.3.8`, `db/` only, non-root. New ECR repository `kesher/migrate` (envs/shared) and a fourth `release.yml` matrix entry (an `include` list, since this Dockerfile is not under `apps/`).
- `modules/migrate-task`: log group (CMK), security group (Postgres and VPC HTTPS out, nothing in), execution role limited to the master secret and the four passwords, read-only root with a `/tmp` volume. Wired into staging and prod with three new secret containers (`db-jit-password`, `db-readonly-password`, `db-migrator-password`) and a `migrate_task` output for the deploy workflow. `terraform` is not installed in the cloud session, so `tests/migrate-task.tftest.hcl` and the root changes were checked by CI's terraform job only.
