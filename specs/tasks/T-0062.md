Test first: the consent screen in M03/M04 sign-up shows the current terms and privacy policy (by link to the web page and a short summary), requires an explicit tap per document, posts the consents, and a returning member who meets `consent_required` is sent to the same screen, then back to what they were doing. English and Hebrew mirrored, right-to-left layout and 200 % Dynamic Type (T-0013). The model is a plain object over `createStore`; tests drive the model, the view takes it.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; CI's terraform job green when `infra/` changed; only listed files touched
Out of scope: the legal API (T-0061); marketing pages. Stop and ask on conflict with the spec.
As built:
- Model: `apps/mobile/src/consent.ts` (`createConsentModel` over `createStore`, `routeIfPending`, `legalLink`, `safeReturnTo`); view: `apps/mobile/app/(auth)/consent.tsx`. `api.ts` gained a `LegalApi` (`documents`, `mine`, `record`) on `Api.legal` over the T-0061 operations.
- The screen shows the documents in force (public `GET /legal/documents`) that `GET /me/consents` lists as `pending`, each with a title, a short summary (the change summary for a material change, else the first 280 characters), a link to its web page and its own switch. Nothing starts on and there is no accept-all; the button opens when every switch is on. One `POST /me/consents` carries exactly the documents shown and the UI locale, then the app goes to `returnTo`. A network failure records nothing and keeps the taps for a retry; a 422 or 409 reads the documents again and clears the taps; 503 reads as unavailable.
- Where in the flow: right after the passkey is created (account creation), `signin.model.ts` asks `GET /me/consents` and, if anything is pending, replaces to `/(auth)/consent?returnTo=<home>`; home, and so KYC and every money step, come after. A returning member's sign-in goes through the same check. `guard()` in `_layout.tsx` lets a signed-in member stay on `(auth)/consent`. If the check itself fails, the consent screen is shown (it asks again).
- **The server-side `consent_required` gate is T-0066 and is not built**, behind an owner decision. The client therefore does not wait for a problem response and no error code was added (the set is closed): it finds a member who owes a consent from `pending`, at sign-in. A member already signed in when a new material version is published is asked at their next sign-in or from Settings; the 401/403-style gate will cover mid-session once T-0066 exists.
- Settings: a "Legal" row on Home's settings card opens `app/settings/legal.tsx` (+ `legal.model.ts`): read-only, each document in force with its in-force version, the accepted version and day, the full text on request, the web link, and a banner to review when a newer material version is pending.
- **Web link base is a placeholder.** `apps/mobile/src/config.ts` has no web URL and none is decided, so no domain is written anywhere. The link is built from `EXPO_PUBLIC_LEGAL_BASE_URL` (unset everywhere; https only) plus the placeholder path `/legal/<docKey>?lang=<locale>`. Outside development and test builds a missing or non-https base makes the consent screen refuse (`consent.error.unavailable`), so it fails closed rather than asking agreement to text the member cannot open. The path and the key's value are for the web card (T-0048) to settle.
- English and Hebrew copy mirrored (`consent.*`, `legal.*`; the i18n test passes). Layout uses the existing `Screen`, `Card`, `Toggle`, `Button` and `ListRow` components (start/end, no fixed heights, `allowFontScaling` on), so it follows T-0013's rules; no new component was added.
- Tests: `src/consent.test.ts`, `app/settings/legal.model.test.ts`, the sign-up cases in `app/(auth)/signin.model.test.ts`, and the guard case in `app/_layout.test.tsx`.
