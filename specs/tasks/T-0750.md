# T-0750 [WAL] MemberSubAccountPort: ensure a member's sub-account under the nonprofit, with its simulator and contract suite

Source: ADR-018 "Decision, 2026-11-18". DECISION recorded there: a NEW sibling port, not a new account kind on `FundingAccountPort` (T-0698). A sub-account is a chapter, so the result carries a chapter ref that every later call needs; the input has a purpose and an owner or an invitation; the errors differ (`QUOTA_EXCEEDED`, `PURPOSE_REQUIRED`). Same style as `FundingAccountPort`: a separate interface, implemented by the funding binding, found by a method-exists guard (`isMemberSubAccountPort`), so no registry capability, catalogue row or provider key. The nonprofit chapter is the ADAPTER's configuration (T-0751); it never crosses the port.
Assumption: documented only (README "Sub-accounts, 2026-11-10", api-inventory 4.4): a sub-account takes exactly one of an `owner` (first name, last name, mobile, email; date of birth optional) or an invitation `email`; an owner that fails does not fail the sub-account; it has its own deposit account; over the tier limit the API answers 429.
Test first: TST-WAL-002. `ensureSubAccount` twice with one party and one key returns the same refs; a second key for the same party returns the same refs (one sub-account per member and purpose, not per call); the same key with different input is `IDEMPOTENCY_CONFLICT` and returns no refs; an `owner` and an `inviteEmail` together, or neither, is `VALIDATION_FAILED`; an empty purpose is `PURPOSE_REQUIRED`; a non-E.164 mobile or an invalid email is `VALIDATION_FAILED`; the simulator's `ownerStatus` is `active` for an owner, `invited` for an invitation and `failed` for the fixture email `ownerfail@example.test` (the sub-account is still made and `open`); `frozen@example.test` gives status `frozen`; after `setQuota(n)` the create past `n` sub-accounts answers `QUOTA_EXCEEDED` BEFORE the key is looked at (as the live API does) and creates nothing, and a repeat of an earlier key still answers its own refs; `account(subAccountRef)` returns `balance`, `hold` and `available` as `Money` with `available = balance - hold`, USD only; an unknown ref is `UNKNOWN_ACCOUNT`; no error text, log line or `JSON.stringify(e)` contains the mobile, email or name passed in.
- Shape: `ensureSubAccount({ partyId, purpose, owner? : { firstName, lastName, email, mobile, dateOfBirth? }, inviteEmail? }, idempotencyKey) -> { subAccountRef, accountRef, status: 'open' | 'frozen' | 'closed', ownerStatus: 'active' | 'invited' | 'failed' }`; `subAccount(subAccountRef) -> { status, balance, hold, available }`. Refs are opaque; `accountRef` is `s:<chapterId>:<accountId>` at Crowded (T-0754), `subAccountRef` is `s:<chapterId>`. Errors: `MemberSubAccountError` with `VALIDATION_FAILED`, `PURPOSE_REQUIRED`, `QUOTA_EXCEEDED`, `UNKNOWN_ACCOUNT`, `IDEMPOTENCY_CONFLICT`, `PROVIDER_UNAVAILABLE`, fixed message text.
- The port never decides whether a purpose is exempt: it only refuses an empty one. That is T-0752's guard and counsel's list (T-0759).
