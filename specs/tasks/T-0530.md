Test first: TST-PAY-001 (screen rows). Found while recording REC-05 and REC-06: M15 says "Send ₪600.00 to db411990-e00d-…", the party id the member typed, because nothing resolves the recipient before the confirm.

`POST /p2p/recipients/resolve` takes a phone number or member id and answers:
- the recipient's id;
- a display name minimal enough not to identify a stranger: the first name and the last initial the recipient set (T-0531), "Avi E.";
- whether they can receive.

It answers nothing about a number that is not a member, and it is rate-limited per member against enumeration. The confirm sheet shows that name. The tests cover:
- a known phone resolves to "Avi E.";
- an unknown phone answers 404 with no hint;
- the 31st lookup in a minute answers RATE_LIMITED;
- the confirm sheet never renders a uuid.

Done when: listed tests pass; Spectral clean; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: contacts sync. The display-name rule is a privacy decision: stop and ask before widening it.

As built:
- **`POST /p2p/recipients/resolve`** sits behind the bearer and `p2p.enabled`. It takes exactly one of `phone` (international form; spaces, dashes and brackets are stripped) or `memberId`, and answers `{ partyId, displayName?, canReceive }`.
  - `displayName` is the name the recipient set (T-0531).
  - `canReceive` means T1 is approved and the account is not pending.
  - An unknown number and a closed account answer the same 404 with the same detail.
- **The rate limit.** 30 lookups a minute per member, over a sliding window, and a refused lookup counts too. The window is held in the API process, so with N processes a member gets up to 30 × N a minute. A shared counter would need a table of its own, which is a follow-up if enumeration ever shows in the logs.
- **The app:**
  - M13 now takes a phone number, resolved to the member before M14. The field reads "Phone number or member ID".
  - A picked contact resolves through the same lookup unless the screen passes a resolver of its own.
  - M15 resolves the member id on open and names "Bob E.", or "a Kesher member" while unresolved or unnamed. The sheet never shows the id.
  - A recipient who can't receive yet, or is gone, shows the existing banners.
- **Copy.** English and Hebrew are mirrored.
