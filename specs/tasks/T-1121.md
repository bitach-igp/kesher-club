# T-1121 [AUTH] SSO sign-in registers a device and emits `new_device_sign_in` (security, independent reviewer)
STATUS: open (scoped 2026-11-26 from the #422 review).
REQ: REQ-AUTH-008 (SECURITY: independent reviewer required, the author must not review it) · Sprint: later · dark/before `auth.orgSso` is turned on
Files: apps/api/src/institutions/staff-sso.ts, apps/api/src/institutions/staff-sso.test.ts, specs/tasks/T-1121.md, specs/tasks/README.md. Read `auth/passkeys.ts` and `auth/social.ts` for how they call `upsertDevice` and emit the event; reuse it, do not copy it.
Source: the independent review of #422 (T-0792), non-blocking finding (a): SSO sessions register no device and emit no `new_device_sign_in` event. Passkey and social sign-in do both, so a takeover of the IdP account signs in as staff with no new-device alert to the member.
Shape: on the exchange success path (where the token is issued, never at the callback and never on a refusal), call `upsertDevice` for the device id the state carries and emit `new_device_sign_in` exactly as the passkey path does. A failure of the device write must not leave a token issued without it: decide the order (device first, then token) and say why. The event carries no IdP claim (name, email, groups).
Test first: (1) a first SSO exchange on a new device writes the device row and emits one `new_device_sign_in`; (2) a second exchange on the same device emits none; (3) a refused exchange (wrong verifier, replayed code) writes no device and emits nothing; (4) the event body holds no IdP claim.
Done when: the listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched; about 80 lines.
