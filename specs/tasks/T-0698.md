# T-0698 [WAL] FundingAccountPort: ensure a member's contact and wallet account at the funding vendor, with KYC pass-through
REQ: REQ-WAL-002 (after T-0697) · Sprint: later (ADR-018, proposed)
Files: packages/ports/src/funding-account.ts (new), packages/ports/src/funding-account.contract.ts (new), packages/ports/src/funding-account.simulator.ts (new), packages/ports/src/funding-account.simulator.test.ts (new), packages/ports/src/index.ts (exports), specs/tasks/T-0698.md, specs/tasks/README.md
Source: ADR-018. If the vendor holds the member's wallet, the vendor must know the member first. This is a separate interface in the `FundingStatementPort` style, implemented by the same adapter instance and found through the `funding` binding, so no new registry capability, catalogue row or provider key is needed (the alternative, a new capability, is recorded in the ADR). It lives in `@kesher/ports`, where the module is WAL because it is the wallet's precondition; the Crowded implementation is an INS-folder adapter (T-0699).
Assumption: A1 (contact plus wallet account per member; the vendor's id kept in `ops.external_ref`, a vendor `externalId` unconfirmed), A2 (the vendor is the KYC authority for its accounts; our `KycPort` stays the app's tier gate).
Test first: TST-WAL-002. `ensureAccount` for one party and one key twice returns the same `contactRef` and `accountRef`; a second key for the same party returns the same refs (the account is per member, not per call); the status is `open` for a normal member, `rejected` for the fixture email `rejected@example.test` (the vendor refused the contact), `frozen` for `frozen@example.test`; two different parties with one mobile answer `DUPLICATE_MOBILE` for the second; a missing or non-E.164 mobile, an empty name or an invalid email is `VALIDATION_FAILED`; no error message or log line contains the mobile, email or date of birth passed in; `account(accountRef)` returns `balance`, `hold` and `available` as `Money` with `available = balance - hold`; an unknown ref is `UNKNOWN_ACCOUNT`; `chapter()` and `transactions()` agree with the balances the simulator's controls set (credit 100 cents: `balance` up 100 and one `credit` row), pages each row once, and take `from` inclusive and `to` exclusive.
- Shape: `ensureAccount({ partyId, firstName, lastName, email, mobile, dateOfBirth? }, idempotencyKey) -> { contactRef, accountRef, status: 'open' | 'rejected' | 'frozen' | 'closed' }`; `account(accountRef) -> { status, balance, hold, available }`; `chapter() -> { checking, held }` (the platform chapter's checking balance and the held collection funds, `Money`); `transactions({ accountRef, from, to })`, an async iterable of `{ transactionRef, kind: 'credit' | 'debit', amount, postedAt, description, collectPaymentId? }` (description is the vendor's text: untrusted, shown as text only). The last two are read by reconciliation (T-0708). Refs are opaque strings kept in `ops.external_ref` with entity types `funding_contact` and `funding_account`; the port keeps no lookup by party. Errors: `FundingAccountError` with `VALIDATION_FAILED`, `DUPLICATE_MOBILE`, `UNKNOWN_ACCOUNT`, `PROVIDER_UNAVAILABLE`.
- A `rejected` or `frozen` status is returned, not thrown: the caller (a later card) refuses the load with the status named.
- Never stores KYC images; the date of birth is passed through, never returned.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the Crowded adapter (T-0699); calling it from `LoadService` (T-0705 and T-0709 wire it); our own KYC tiers; a bank-side status the vendor adds later; closing an account.

## As-built
- `funding-account.ts`: `FundingAccountPort` (`ensureAccount`, `account`, `chapter`, `transactions`), `FundingAccountError` (`VALIDATION_FAILED`, `DUPLICATE_MOBILE`, `UNKNOWN_ACCOUNT`, `IDEMPOTENCY_CONFLICT`, `PARTY_CONFLICT`, `PROVIDER_UNAVAILABLE`; fixed message text, never the personal data) and `isFundingAccountPort(port)`, a new method-exists check on the `funding` binding's port (the repo has no equivalent guard for `FundingStatementPort`). No registry, catalogue or provider-key change.
- The result is a union: an account carries `contactRef` and `accountRef` with a status `open`, `frozen` or `closed` (the vendor's account states); a contact the vendor refused (Failed, `rejected`) or archived (`archived`) carries `contactRef` only, because Crowded creates no account for it. `account()` of such a ref is `UNKNOWN_ACCOUNT`. Only `open` is usable by a caller. An account still being provisioned is the adapter's to resolve (poll) before it returns, and `accountCreated: false` from the vendor is success.
- Identity at the vendor is the mobile within the chapter. `partyId` is only the idempotency subject; the contact create has no idempotency key and no external id, so the adapter (T-0699) owns the mobile-to-contact lookup (list the chapter's contacts by mobile before creating) and the caller owns the party-to-contact mapping in `ops.external_ref` (`funding_contact`, `funding_account`).
- Idempotency: a key is bound to a hash of its input (party and contact fields; hashes only, nothing in clear). The same key with different input is `IDEMPOTENCY_CONFLICT` and returns no refs. A new key for an existing party with the same data answers the same refs and the current status; with a different mobile, name, email or date of birth it is `PARTY_CONFLICT` (a member changing phone is an explicit update call, not in this card). A different party whose mobile already belongs to a contact is `DUPLICATE_MOBILE` (the caller shows the member a generic message), including a rejected contact's mobile. Validation runs before a key is bound, so a refused request claims no key.
- `chapter()` returns `checking` only. It is a separate account at the vendor (ADR-018 D5), not the sum of the wallets; the simulator's `setChecking` is independent of `credit`. `held` was dropped: it has no vendor source on the chapter or account reads and T-0708 will source it from the collect payments listing. `FundingTransaction` has no `collectPaymentId`: the vendor's wallet transaction rows carry none, so only a statement or reconciliation join can supply it.
- `funding-account.simulator.ts`: fixtures by email: `rejected@`, `archived@`, `frozen@`, `outage@example.test`. Controls: `credit`, `debit`, `setHold`, `setChecking`, `setStatus`.
- `funding-account.contract.ts` and `funding-account.simulator.test.ts`: 22 tests, including the outage fixture in the shared contract, a replay returning the current status, and a privacy test that scans message, stack, `JSON.stringify(e)` and `String(e)` plus console spies. The first version of the tests failed on main (no `funding-account` module); the review round's behaviour (key binding, no account for a rejected contact, `PARTY_CONFLICT`) is pinned by new contract cases.
- Assumptions about what Crowded accepts, not confirmed: mobile `^\+[1-9]\d{7,14}$`, a real `YYYY-MM-DD` date of birth, a non-empty name and a plain email. The vendor validates each contact item itself, so the adapter maps its own refusal to `VALIDATION_FAILED`. Balances and rows are USD only (ADR-018). `from` and `to` are ISO instants.
- `specs/tasks/README.md` already lists the card; no change.
