# T-0698 [WAL] FundingAccountPort: ensure a member's contact and wallet account at the funding vendor, with KYC pass-through
REQ: REQ-WAL-002 (after T-0697) · Sprint: later (ADR-018, proposed)
Files: packages/ports/src/funding-account.ts (new), packages/ports/src/funding-account.contract.ts (new), packages/ports/src/funding-account.simulator.ts (new), packages/ports/src/funding-account.simulator.test.ts (new), packages/ports/src/index.ts (exports), specs/tasks/T-0698.md, specs/tasks/README.md
Source: ADR-018. If the vendor holds the member's wallet, the vendor must know the member first. This is a separate interface in the `FundingStatementPort` style, implemented by the same adapter instance and found through the `funding` binding, so no new registry capability, catalogue row or provider key is needed (the alternative, a new capability, is recorded in the ADR). It lives in `@kesher/ports`, where the module is WAL because it is the wallet's precondition; the Crowded implementation is an INS-folder adapter (T-0699).
Assumption: A1 (contact plus wallet account per member; the vendor's id kept in `ops.external_ref`, a vendor `externalId` unconfirmed), A2 (the vendor is the KYC authority for its accounts; our `KycPort` stays the app's tier gate).
Test first: TST-WAL-002. `ensureAccount` for one party and one key twice returns the same `contactRef` and `accountRef`; a second key for the same party returns the same refs (the account is per member, not per call); the status is `open` for a normal member, `rejected` for the fixture email `rejected@example.test` (the vendor refused the contact), `frozen` for `frozen@example.test`; two different parties with one mobile answer `DUPLICATE_MOBILE` for the second; a missing or non-E.164 mobile, an empty name or an invalid email is `VALIDATION_FAILED`; no error message or log line contains the mobile, email or date of birth passed in; `account(accountRef)` returns `balance`, `hold` and `available` as `Money` with `available = balance - hold`; an unknown ref is `UNKNOWN_ACCOUNT`; `chapter()` and `transactions()` agree with the balances the simulator's controls set (credit 100 cents: `balance` up 100 and one `credit` row), pages each row once, and take `from` inclusive and `to` exclusive.
- Shape: `ensureAccount({ partyId, firstName, lastName, email, mobile, dateOfBirth? }, idempotencyKey) -> { contactRef, accountRef, status: 'open' | 'rejected' | 'frozen' | 'closed' }`; `account(accountRef) -> { status, balance, hold, available }`; `chapter() -> { checking, held }` (the platform chapter's checking balance and the held collection funds, `Money`); `transactions({ accountRef, from, to })`, an async iterable of `{ transactionRef, kind: 'credit' | 'debit', amount, postedAt, description, collectPaymentId? }` (description is the vendor's text: untrusted, shown as text only). The last two are read by reconciliation (T-0708). Refs are opaque strings kept in `ops.external_ref` with entity types `funding_contact` and `funding_account`; the port keeps no lookup by party. Errors: `FundingAccountError` with `VALIDATION_FAILED`, `DUPLICATE_MOBILE`, `UNKNOWN_ACCOUNT`, `PROVIDER_UNAVAILABLE`.
- A `rejected` or `frozen` status is returned, not thrown: the caller (a later card) refuses the load with the status named.
- Never stores KYC images; the date of birth is passed through, never returned.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the Crowded adapter (T-0699); calling it from `LoadService` (T-0705 and T-0709 wire it); our own KYC tiers; a bank-side status the vendor adds later; closing an account.

## As-built
- `funding-account.ts`: `FundingAccountPort` (`ensureAccount`, `account`, `chapter`, `transactions`), the status, input and view types, `FundingAccountError` (`VALIDATION_FAILED`, `DUPLICATE_MOBILE`, `UNKNOWN_ACCOUNT`, `PROVIDER_UNAVAILABLE`; fixed message text, never the personal data) and `isFundingAccountPort(port)`, the method-exists check a later card uses to find the capability on the `funding` binding (as `listSettled` is found). No registry, catalogue or provider-key change.
- `funding-account.simulator.ts`: stateful, in-memory. Fixture emails: `rejected@example.test` (status `rejected`), `frozen@example.test` (`frozen`), `outage@example.test` (`PROVIDER_UNAVAILABLE`). Controls: `credit`, `debit`, `setHold`, `setHeld`, `setStatus`. `chapter().checking` is the sum of the account balances; `held` is a control. Input is validated before the idempotency store, so a refused request claims no key. Once a key has answered, a replay skips the duplicate-mobile and outage checks and returns that party's account with its current status.
- `funding-account.contract.ts` (`fundingAccountContract`) and `funding-account.simulator.test.ts`: 17 tests covering every clause of the card, plus a console spy and message check that no mobile, email, name or date of birth appears in an error or a log line.
- Decisions: a `rejected` contact still gets refs (the vendor created the contact; the status is the refusal), so the caller can store them in `ops.external_ref` and refuse by status. The simulator's mobile is E.164 `+` and 8 to 15 digits (stricter than "starts with +", looser than a numbering plan). Currency is USD only for balances and rows (the funding rail is USD, ADR-018). `from` and `to` are ISO instants; an unparsable one is `VALIDATION_FAILED`. Crowded facts the adapter (T-0699) must honour: the contact is created with `POST /chapters/{id}/contacts`, the wallet account with `POST /chapters/{id}/accounts` (v4 `idempotencyKey`), contacts are unique by mobile within a chapter (the source of `DUPLICATE_MOBILE`), and there is no settable external id, so the party-to-contact mapping is only in `ops.external_ref`.
