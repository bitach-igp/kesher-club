# T-0071 [SETUP] AuditService.record is refused under club_app on a real Postgres: serialise the hash chain with an advisory lock, not a table lock
REQ: — (enabling; found in the T-0046 bootstrap; P0 for the first deploy) · Sprint: 16 deploy
Files: apps/api/src/audit/service.ts, apps/api/src/audit/service.test.ts, specs/tasks/T-0071.md, specs/tasks/README.md
Test first: `AuditService.record` runs `lock table audit.entry in share row exclusive mode` (service.ts:50). Postgres allows that mode only with UPDATE, DELETE or TRUNCATE on the table, and `audit.entry` grants `club_app` only `select, insert` (`db/migrations/audit/0001_init.sql:33`). So under the real service role every audited API action fails with `permission denied for table entry`: admin flag flips, approvals, institution onboarding and the rest. Tests never saw it because they run as the table owner. The failing test: on PGlite via `createTestDatabase().asRole('club_app', …)` record an entry (and two concurrent ones); today it throws. Fix without weakening tamper-evidence: do NOT grant update, delete or truncate on `audit.entry`. Serialise the chain with `select pg_advisory_xact_lock(<constant key>)` at the start of the transaction, before reading the last hash, so concurrent writers still append in `seq` order and the chain cannot fork. The key is one named constant. Tests: records under `club_app`; two concurrent records form one unbroken chain that `verify` accepts; the role still cannot update or delete a row. Also check every other `lock table` in the repo under its real role (a grep found only this one).
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: changing grants on `audit.entry`; moving the chain to another store. Stop and ask on conflict with the spec.
