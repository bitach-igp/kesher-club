# T-0697 [WAL] FundingPort can start a hosted load and answer a pending one with a payment-page action
REQ: REQ-WAL-002 · Sprint: later (ADR-018, proposed)
Files: packages/ports/src/funding.ts, packages/ports/src/funding.contract.ts, packages/ports/src/funding.simulator.ts, packages/ports/src/funding.simulator.test.ts, specs/tasks/T-0697.md, specs/tasks/README.md
Source: ADR-018 (Crowded as the member funding rail). `FundingPort` is a pull: `createLoad` takes a saved payment method and answers synchronously. A vendor whose payer pays on the vendor's page needs the port to say "pending, open this". `requires_action` and `clientSecret` already exist, but `clientSecret` is Stripe's payment-sheet secret and the status carries no place to put a page address.
Assumption: A8 (the port answers a pending load with an `action`; Stripe and the simulator unchanged for existing callers), A3 (the payer's IP and consent are required by the vendor's intent).
Test first: TST-WAL-002. A $100 load with `method: 'hosted'` and `hosted: { payerIp, userConsented: true }` returns `status: 'requires_action'` with `action: { type: 'payment_page', url }` and no `clientSecret`; the same key returns the same load and the same action (one load); a hosted load without `payerIp`, or with `userConsented` not `true`, is `VALIDATION_FAILED`; the simulator control `payHosted(loadId, 'card')` makes the load `succeeded` with `method: 'card'`, and `payHosted(loadId, 'ach')` makes it `processing`, then `settle(loadId)` makes it `on_hold` with `holdUntil` three business days on and `method: 'ach'`; `failHosted(loadId, 'DECLINED')` makes it `failed` with that `failureCode`; every existing contract test passes unchanged.
- `FundingMethod` gains `hosted` (the payer picks card or bank on the page). A `Load` read after payment carries the method actually used. `createLoad` input gains optional `hosted?: { payerIp: string; userConsented: true; successUrl?: string; failureUrl?: string }`; `Load` gains optional `action?: { type: 'payment_page'; url: string; expiresAt?: string }`. Nothing is removed or made required.
- The contract suite gains a hosted block behind an option (`hosted: true`, default false) so the Stripe contract test, which passes no option, runs unchanged. An adapter that does not support hosted answers `UNSUPPORTED_METHOD` (the Stripe adapter already does for any method it does not know).
- The simulator's page url is a documented non-routable address (`https://pay.simulator.invalid/{loadId}`); the url is never logged with a token in it.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the Crowded adapter (T-0700); the API field (T-0714); the app (T-0715); embedded tokens (the `action` type is open for a later `embed` kind once Crowded confirms); changing `LoadService`.

## As-built
- `funding.ts`: `FundingMethod` gains `hosted`; new `LoadAction` (`payment_page`, `url`, optional `expiresAt`) and `HostedLoadInput`; `Load.action?`; `createLoad` input `hosted?`. Nothing removed or made required.
- `funding.simulator.ts`: a hosted load answers `requires_action` with `https://pay.simulator.invalid/{loadId}` and no `clientSecret`; a missing `payerIp` or `userConsented !== true` is `VALIDATION_FAILED` (checked before the idempotency store, so a bad request never claims a key). Controls: `payHosted(loadId, 'card'|'ach')`, `failHosted(loadId, code)`, `settle(loadId)`. The card said `settle` makes a processing load `on_hold`; the header comment already mentioned `settle` but no such method existed, so it is new: processing goes to `on_hold` with `holdUntil` three business days on, and an `on_hold` load is released as `succeeded`. Controls throw `VALIDATION_FAILED` on a load in the wrong state.
- `funding.contract.ts`: option `hosted?: boolean` (default false). When true: the pending-action, one-load-per-key and consent tests; when false: the adapter answers `UNSUPPORTED_METHOD` for `hosted`. The Stripe contract test passes no option and so runs the `UNSUPPORTED_METHOD` case against the Stripe adapter unchanged (it passes).
- Tests: `funding.simulator.test.ts` (simulator contract with `hosted: true`, plus the control tests). The new tests failed on main (6 failures) before the code.
- `specs/tasks/README.md` already lists the card; no change.

### Review round 1
- `payerIp` must pass `isPublicIp` (new, `funding.ts`): an IPv4 or IPv6 literal that is not private, loopback, link-local, unspecified, CGNAT, multicast or reserved; IPv4-mapped (`::ffff:a.b.c.d`, also the hex form) and IPv4-compatible forms are judged by the IPv4 inside; IPv6 must be global unicast (`2000::/3`). Written inside `packages/ports` (modelled on `clientIp` in the API, nothing imported from apps). T-0700 should call the same helper.
- `successUrl` / `failureUrl` must pass `isHttpsUrl` (protocol exactly `https:`, a host, no credentials); `assertHttps(url, what)` throws `VALIDATION_FAILED` for adapters to reuse, also for the `action.url` they hand out. The port does not restrict redirect hosts: an allowlist of our own hosts is the adapter's job (T-0700). Both checks run in the simulator before the idempotency store.
- The simulator's action now carries `expiresAt` (clock plus one hour, ISO 8601 UTC); the contract asserts the format when present. T-0700 must persist `expiresAt` per load rather than recompute it, because the idempotent replay and `getLoad` must return equal loads.
- A webhook for a hosted load (`webhookFor(id, status, method?)`) now drops `action` and, for a paid load, carries the method used (card unless the hook says ach); `getLoad` afterwards agrees. A failed hosted load keeps method `hosted` (no method was used).
- Not modelled: a return or reversal after success. The port is pull-shaped and has no returned status; the Crowded `collect.payment.returned` event will need a `LoadStatus` or a simulator control in T-0700 or a later card.
