# T-0919 [ADM] Staff sign in to a local console through a simulator identity provider
REQ: REQ-AUTH-009 (after T-0031 and T-0918) · Sprint: 10
Files: apps/simulators/src/oidc.ts, apps/simulators/src/oidc.test.ts, apps/simulators/src/server.ts, apps/admin/src/config.ts, apps/admin/src/boot.test.ts, docs/setup/demo.md, specs/tasks/T-0919.md, specs/tasks/README.md; added when the end-to-end run found a 500: apps/api/src/app.ts (shared plumbing), apps/api/src/admin/handlers.test.ts; evidence: handoff/done/T-0919-idp-picker.png, handoff/done/T-0919-console-home.png
Test first: the console signs staff in only through Identity Center (`apps/admin/src/auth/oidc.ts`: discovery, authorization code, token, JWKS), so a local console cannot be opened without real SSO secrets. There is no bypass to add and none is wanted: the console keeps its full OIDC path, and the simulator panel gains a standards-shaped issuer at `/oidc` with `/.well-known/openid-configuration`, `/authorize`, `/token` and `/jwks`. It signs ES256 ID tokens with a key generated at start, for fixed staff personas with `roles` (`support`, `compliance`, `finance`, `admin`) and a second `admin` for two-person flips. `/authorize` shows a persona picker in place of a password form. `oidc.test.ts` drives the console's own `discover`, authorization-request and token-exchange helpers against it: the ID token verifies against `/jwks`, carries the nonce and the chosen roles, and a wrong `code_verifier` or a reused code answers `invalid_grant`. `config.ts` gains one rule for `ADMIN_OIDC_ISSUER` and `ADMIN_OIDC_JWKS_URL`: outside `ADMIN_ENVIRONMENT=local` each must be `https` and must not name `localhost`, `127.0.0.0/8` or `::1`; in `local`, `http` is allowed only for those loopback hosts. `boot.test.ts` pins three cases: `preview` with `http://localhost:4010/oidc` exits 1 with a `boot_failed` line naming `ADMIN_OIDC_ISSUER`; `local` with the same issuer boots; and `local` with `http://idp.example` also exits 1, so the simulator issuer cannot be pointed off the machine.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; with T-0031 running, `ADMIN_ENVIRONMENT=local ADMIN_DATA=api` console signs in as each persona (stated in the PR); only listed files touched
Out of scope: Identity Center itself, staff-token claims (ADR-013, unchanged), new console screens. Stop and ask on conflict with the spec.

As built:
- **Client authentication.** The console's `exchangeCode` authenticates with `client_secret_post`; it sends no PKCE `code_verifier`. The issuer accepts both:
  - a code requested with an S256 `code_challenge` must present the matching verifier;
  - any other code must present the client's secret (`kesher-admin-local` / `local-simulator-client`, documented as not a secret).
  - `oidc.test.ts` covers the console's own path, a wrong PKCE verifier (`invalid_grant`) and a wrong secret (`invalid_client`).
- **Staying on this machine.** The issuer answers only to a loopback `Host` and redirects only to loopback URLs, so it cannot be used as an identity provider anywhere else. The ID token's `aud` is the client id.
- **A 500 found end to end.** With T-0031 running and `ADMIN_ENVIRONMENT=local ADMIN_DATA=api`, the console home returned 500. The composition root handed the admin handlers `s.flags as FlagService`. In the demo, `s.flags` is the in-memory "all on" `StaticFlags`, so `GET /admin/flags` crashed. The admin handlers now always get the stored, two-person `FlagService`. A test in `apps/api/src/admin/handlers.test.ts` checks that the stored state is listed while evaluation stays on.
- **Verified in Chromium**, each persona in a fresh browser context: "Sign in with Identity Center", the persona picked on the simulator's page, then the console home "Today" with its queues from the API and Customer 360 finding Dana (seeded by T-0032) by id and by phone, masked. This held for Sam Support, Cleo Compliance, Finn Finance, Ada Admin and Abe Admin. Screenshots are in `handoff/done/T-0919-*.png`.
