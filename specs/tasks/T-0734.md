# T-0734 [INS] Crowded idempotency keys are UUID v4, as the live API requires; the fake refuses any other version
REQ: REQ-INS-024 · Sprint: fix (found against the live sandbox, 2026-11-11)
Files: packages/adapters/src/crowded/map.ts, packages/adapters/src/crowded/map.test.ts, packages/adapters/src/crowded/fake-crowded.ts, packages/adapters/src/crowded/institution-banking.contract.test.ts, packages/adapters/src/crowded/sandbox.test.ts, docs/vendors/crowded/README.md, specs/tasks/T-0718.md, specs/tasks/T-0719.md, specs/tasks/T-0734.md, specs/tasks/README.md
Source: the Crowded sandbox, 2026-11-11: `POST /chapters/{id}/payments` (ACH and book) and `POST /chapters/{id}/counterparties` answer `400 ValidationError "Idempotency key must be a valid UUID v4"` for a version-5 key and accept a version-4 key. `uuidFromKey` made a version 5, and the fake accepted any UUID shape, so no test saw it: every live ACH send would have failed.
Test first: `uuidFromKey` matches `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, is stable per key, and differs per key; a send, a sub-account create and a book transfer through the adapter reach the fake with a v4 key and succeed (this fails on main once the fake enforces v4); the fake answers 400 `ValidationError` "Idempotency key must be a valid UUID v4" for a version-5 key on a payment and a sub-account create.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the MirrorPort adapter (T-0719); creating sandbox data from the gated suite.

## As-built
- `uuidFromKey` (`map.ts`) keeps the namespaced SHA-1 and sets the version nibble to 4 (variant stays `10xx`): deterministic, same key same value, well distributed (122 hash bits remain).
- Callers (all in `institution-banking.ts`): `createSubAccount` (`sub:` prefix), `sendAch` (`ach:`), `bookTransfer` (`book:`, the sub-account fund call). No other caller; the adapter has no counterparty create, so none derives a key.
- The fake (`fake-crowded.ts`) checks a strict v4 body key with 400 `ValidationError` "Idempotency key must be a valid UUID v4" on every payment (before the rejected-fixture branch), on the sub-account create (after the quota check, which the live API ran first), and per item on the sub-account fund call (item `failed`, same message). The live order for sub-account and fund was inconclusive; the check changed no existing test. The fake has no counterparty create route, so there is nothing to enforce there.
- Persisted keys: the `KeyLedger` (`InMemoryKeyLedger`, `PostgresVendorKeyLedger` over `ops.vendor_idempotency`) stores OUR key (the workflow id) with a body hash and the result, never the derived UUID; the UUID is recomputed at send time. `ops.external_ref` stores Crowded ids, not keys. So the wire key of a request changes across this change: a request whose first attempt used the old v5 key and whose retry uses the new v4 key would reach Crowded as a different key and could double-send. Nothing is live (the live API refused every v5 key, so no ACH, sub-account or book call has succeeded with one), so no such request exists; state this again if the adapter is ever pointed at production before this merges.
- The gated sandbox suite (`sandbox.test.ts`) is unchanged except for a comment recording the v4 rule; it creates no data.
- Docs: the sandbox probe of 2026-11-11 is in `docs/vendors/crowded/README.md`; questions 39, 40 and 47 are marked answered; T-0718 and T-0719 each gain a line on the v4 key and on `paymentStatus: Rejected`.
