As built:
- Three operations: `GET /legal/documents` (public; the newest version already in force of each document, both languages, with its hash), `GET /me/consents` (what the member accepted, and what is pending with its reason `first` or `material_change`) and `POST /me/consents` (records acceptance of the listed versions against the token's device and the locale the member read it in). The service from T-0304 is now composed into the app (`legalHandlers(new LegalService(o.db))` in `app.ts`).
- Only a version in force can be accepted; an old, future, missing or unknown document, a duplicate, a bad locale or an empty list answers 422, and a request with one bad entry records none. Recording the same version again is a no-op that returns the first record, so the call takes no Idempotency-Key (the contract says why).
- **No IP is collected**, as the card asks. `legal.consent.ip` is `inet not null`, so `0.0.0.0` is stored and means "not collected"; T-0067 makes the column nullable.
- Split out, because each is a different size and decision: the two-person draft and publish routes (T-0065); the `consent_required` gate on money routes (T-0066: it needs a design choice, because every existing member has the "first" documents pending, so an unflagged gate would block everyone); the nullable `ip` column (T-0067, a migration and so a desktop apply).
- `GET /legal/documents` is not cached: the server sends `cache-control: no-store` on every response. Caching it at the edge belongs with the web site (T-0048).
