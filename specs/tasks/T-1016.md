# T-1016 [AGT] Authorization server, part 3: the token endpoint, with PKCE and rotating refresh tokens
REQ: REQ-AGT-011, REQ-AGT-002 (after T-1015) · Sprint: 13
Files: apps/api/src/oauth/token.ts, apps/api/src/oauth/token.test.ts, apps/api/src/server.ts, apps/api/src/app.ts, contracts/openapi.yaml, packages/sdk/src/schema.generated.ts, specs/tasks/T-1016.md, specs/tasks/README.md; shared plumbing: apps/api/src/routes.ts
Test first: TST-AGT-011. `POST /oauth/token` takes `application/x-www-form-urlencoded`, as OAuth requires; `server.ts` parses that content type alongside JSON. Behind `mcp.enabled`:
- `authorization_code`:
  - checks the code once, within 60 seconds, against the client, redirect URI and `code_verifier` (S256);
  - answers an access token (ES256, 10 minutes, `aud` set to the MCP URL, `sub`, `scope`, `grant_id`, `client_id`, `jti`) and a refresh token (opaque, hashed, 30 days).
- `refresh_token`: rotates; the old one stops working. Presenting an already-rotated one revokes the grant.
- Revoking a grant (T-1006) ends its refresh tokens.

The tests cover:
- a wrong verifier, a reused code and an expired code answer `invalid_grant`;
- the access token passes `McpTokenValidator` and is refused by the member API (and a member token by /mcp);
- refresh rotates;
- a replayed refresh token revokes the grant, and the next /mcp call is 401;
- a revoked grant's refresh answers `invalid_grant`.

Done when: listed tests pass; Spectral clean; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: token introspection and revocation endpoints (the grants screen revokes). Stop and ask on conflict with ADR-009.

As built:
- **`apps/api/src/oauth/token.ts`** holds `TokenEndpoint` and the `issueAgentToken` handler. The route is public (clients have no secret) and sits behind `mcp.enabled`.
- **Body and errors.** `server.ts` parses a form body for this route only, and every other route stays JSON-only. Errors are OAuth's JSON (`error`, `error_description`) with 400, not a problem document. The server already marks every response `no-store`.
- **The code exchange.**
  - The code leaves `approved` in the same statement that finds it, so it is single-use even under a race.
  - A wrong verifier, client or redirect URI still commits that state, so the code is burned rather than left for another try.
  - A reused code revokes the grant it made (OAuth 2.1 §4.1.3), mirroring the refresh replay rule.
  - Every mismatch answers the same `invalid_grant`, so the client learns nothing about which part was wrong.
- **Tokens.**
  - The access token is ES256 with `typ: at+jwt`, signed with the member token service's key. Its claims are `iss` (the issuer), `aud` (the MCP URL), `sub`, `scope`, `grant_id`, `client_id` and `jti`, valid 600 seconds; the validator allows 5 seconds of skew.
  - A refresh token is 32 random bytes, stored as SHA-256, in a family that keeps its first 30-day expiry through rotations.
- **Revocation.** A grant revoked from the grants screen needs no hook, because both exchanges check that the grant is active. `agent/grants.ts` is therefore out of the card's files.
