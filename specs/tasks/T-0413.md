# T-0413 [CRD] The accounts a card authorisation needs exist before the first authorisation
REQ: REQ-CRD-003 (enabling; owner decision 2026-11-06 on PR #246, so the authorisation role needs no INSERT on `ledger.account`) · Sprint: 16 deploy
Files: apps/api/src/ledger/accounts.ts, apps/api/src/ledger/accounts.test.ts, apps/api/src/cards/service.ts, apps/api/src/cards/service.test.ts, apps/api/src/cards/physical.ts, apps/api/src/cards/physical.test.ts, apps/api/src/cards/jit.ts, apps/api/src/cards/jit.test.ts, apps/api/src/app.ts (shared composition root: `CardService` now takes the `AccountService`), apps/worker/src/cards/issue-workflow.test.ts, apps/worker/src/cards/token-events.test.ts (they construct `CardService`), apps/demo/src/seed.ts (the demo's system accounts), specs/tasks/T-0413.md, specs/tasks/README.md
Test first: today the authorisation path creates accounts on demand: `AccountService.memberAccount` and `systemAccount` insert into `ledger.account` when the row is missing (`apps/api/src/ledger/accounts.ts`, `ensure`), and `jit.ts` calls them for the member's `pending` account (`row.pending_id ?? memberAccount(...)`) and, on a converted authorisation, for the system accounts `fx_position` and `fee_income`. The decision recorded on T-0064 is that `club_jit` has SELECT on `ledger.account` and no INSERT, so the path must only read. Add read-only `AccountService.findMemberAccount` / `findSystemAccount` (return the id, or throw `NOT_FOUND`); `jit.ts` uses them, so a missing account throws, the existing fail-closed catch declines `TIMEOUT`, and nothing is inserted. Every place a card row is created provisions the member's `pending` account in USD and ILS (idempotent) before the card is returned: `recordCard` in `cards/service.ts` (reached from `issueVirtual` and the worker's issue activity) and the direct `cards.card` insert in `cards/physical.ts` (a physical card would otherwise decline `TIMEOUT` on every authorisation). `CardService` takes the `AccountService` for this, so its constructor changes: `app.ts` passes it, and the worker tests that construct `CardService` follow. Wallets are not touched: they are created lazily at a member's first load, and a member with no wallet already declines (`jit.ts` reads it and declines when absent). The system accounts (`fx_position`, `fee_income`, both currencies) are provisioned by the production bootstrap (T-0046, not yet built: until it lands a production converted authorisation would decline, which is harmless while the card flags are off), by `apps/demo/src/seed.ts` (it provisions none today, and the lazy path used to cover it) and by the `beforeAll` of the converted tests in `jit.test.ts` (which relied on the lazy accounts). Tests: issuing a card creates both `pending` accounts and a second issue creates no duplicate; an authorisation for a provisioned card approves and leaves the `ledger.account` row count unchanged; an authorisation for a card whose `pending` account was deleted declines `TIMEOUT` and inserts nothing; a converted authorisation with the system accounts missing declines `TIMEOUT` and inserts nothing; a physical card issues with its `pending` accounts too; existing JIT, physical-card and worker issue tests stay green with their helpers provisioning what the path now expects.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the grants and the real-Postgres proof (T-0064); the production bootstrap itself (T-0046, which must list `fx_position` and `fee_income` in USD and ILS among the system accounts it creates); backfilling cards issued before this card (none exist outside the demo seed, which is re-run); provisioning wallets at sign-up (they stay lazy).
