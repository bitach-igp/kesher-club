Test first: today the authorisation path creates accounts on demand: `AccountService.memberAccount` and `systemAccount` insert into `ledger.account` when the row is missing (`apps/api/src/ledger/accounts.ts`, `ensure`), and `jit.ts` calls them for the member's `pending` account (`row.pending_id ?? memberAccount(...)`) and, on a converted authorisation, for the system accounts `fx_position` and `fee_income`. The decision recorded on T-0064 is that `club_jit` has SELECT on `ledger.account` and no INSERT, so the path must only read. Add read-only `AccountService.findMemberAccount` / `findSystemAccount` (return the id, or throw `NOT_FOUND`); `jit.ts` uses them, so a missing account throws, the existing fail-closed catch declines `TIMEOUT`, and nothing is inserted. Card issue (`cards/service.ts`) provisions the member's `pending` account in USD and ILS (idempotent) before the card is returned. The system accounts (`fx_position`, `fee_income`, both currencies) are provisioned by the production bootstrap (T-0046) and by the test and demo setup helpers. Tests: issuing a card creates both `pending` accounts and a second issue creates no duplicate; an authorisation for a provisioned card approves and leaves the `ledger.account` row count unchanged; an authorisation for a card whose `pending` account was deleted declines `TIMEOUT` and inserts nothing; a converted authorisation with the system accounts missing declines `TIMEOUT` and inserts nothing; existing JIT tests stay green with their helpers provisioning what the path now expects.
