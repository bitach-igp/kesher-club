# T-0413 [CRD] Accounts exist before the first authorisation: issuing provisions them, JIT only reads ledger.account

Test first: TST-CRD-001. Today the authorisation path creates accounts: `JitService.evaluate` falls back to `accounts.memberAccount(party, 'pending', currency)` when the lookup finds no pending purse (`apps/api/src/cards/jit.ts:169`), and `holdLegs` calls `accounts.systemAccount('fx_position' | 'fee_income', …)` for a converted hold (`jit.ts:293-295`); both go through `AccountService.ensure`, which INSERTs into `ledger.account` when the row is missing. The owner decided (T-0064, Decision) that `club_jit` gets no INSERT on `ledger.account`, so the accounts must exist first. Tests, written first:
1. Issuing a virtual card (`CardService.recordCard`, the step both the API trigger and the worker's issue workflow run) leaves the member with a `wallet` and a `pending` account in USD and ILS (`provisionMember`) and the card path's system accounts (`fx_position` and `fee_income` in USD and ILS) in place; issuing again, or replaying the workflow, adds no rows. Recording a physical card (`physical.ts`) does the same through `CardService`.
2. A spy or counting wrapper over the database shows a JIT decision issues no INSERT into `ledger.account`, for a plain hold and for a converted hold (T-0409), and for a replayed authorisation id.
3. A card whose member has no `pending` account in the authorisation currency (a row inserted directly, bypassing issue) declines `INSUFFICIENT_FUNDS` and writes nothing; a converted hold whose `fx_position` or `fee_income` account is missing declines `INSUFFICIENT_FUNDS` and writes nothing. No new decline reason: the port's set is closed.
4. The existing `jit.test.ts`, `jit.bench.test.ts`, `settlement.test.ts` and worker card tests still pass with their fixtures provisioned through issue.
Design: `AccountService` gains `provisionCardSystem()` (ensures the system accounts above, idempotent like `provisionMember`) and a read-only `findSystemAccount(type, currency): Promise<string | undefined>` that never inserts. `CardService` takes the `AccountService` (wired in `apps/api/src/app.ts`; the worker tests that construct `CardService` pass one) and calls both provisioning methods in `recordCard` before the card row is inserted, so a card never exists without its accounts. JIT reads the pending id from its existing one-round-trip lookup only and resolves system accounts with `findSystemAccount`; it keeps no reference to the methods that insert.
