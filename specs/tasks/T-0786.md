Source: The first scope of this card (merged as the previous text of this file) claimed that a credit refused `NOT_SUCCEEDED` and retried under the same key could later be answered `credited`, so a return before the journal would miss money the vendor holds, and proposed a `credit_resent` marker. PR #397 built it (closed unmerged; branch `cards/T-0786-credit-resent` keeps the code) and an independent review answered REQUEST_CHANGES. The reviewer's findings, verified on the simulator: (a) The premise cannot happen under the documented vendor contract. A refusal is final for its key: `packages/ports/src/funding.ts` ("A refusal is final for its key (the vendor's is), so a retry after a refusal needs a NEW key"); the Crowded adapter stores the refusal as final (`packages/adapters/src/crowded/credit.ts`, `close(refused('NOT_SUCCEEDED'))`, replayed forever); the simulator's `IdempotencyStore` does the same; `funding.contract.ts:255` and `funding.contract.test.ts:947-958` use `:credit:2` after an ACH hold. The old test only reached `credited` because `spy.mockResolvedValueOnce` bypasses the simulator's idempotency store; under an honest vendor all 23 sequences the `credit_resent` change added were false-positive cases (a case for money that never moved). So the old design is withdrawn. (b) The real problem, below, is the opposite one: the key never recovers.
Verified (the problem): in `creditStep` (`load-credit.ts`) a `refused` answer with `reasonCode: 'NOT_SUCCEEDED'` is stored as outcome `refused` by `recordCreditOutcome` and then returns `{ proceed: false, refused: false }`: `openCreditCase` is not called, so no `load_credit_refused` case exists (the comment says "the vendor's read flapping, not a refusal: retried with the same key, no case", the T-0761/T-0766 design). The next sweep reads `creditCase` (no case, `attempt = 0`), computes `attempt = 1` again and calls `creditWallet` with the SAME key `{wf}:credit:1`. An honest vendor replays its stored refusal for that key, so the answer is `NOT_SUCCEEDED` every cycle, forever. Measured on the simulator with an honest vendor (first answer per key stored and replayed; the load read `succeeded` by us, refused `NOT_SUCCEEDED` by the credit call): calls `[:credit:1, :credit:1, :credit:1, :credit:1]` over a request and three sweeps, transfer state `submitted`, 0 journals, 0 cases. The member's load never lands, nothing shows on the money queue, and no alert fires: it sticks silently. It also contradicts the port contract's own rule that a retry after a refusal needs a new key. (A real refusal, any other reason code, opens a case and takes `:credit:{n+1}` after people resolve it, which is right and is not changed.)
Decision and build (2026-11-23): the owner took the card's recommendation, option 2 (in code, option 3): after N = 3 consecutive case-less `NOT_SUCCEEDED` answers for the same key, ONE `load_credit_refused` case opens (reasonCode `NOT_SUCCEEDED`, the attempt n of that key); the key stays `{wf}:credit:{n}`; staff resolve it and the existing resolve path takes `:credit:{n+1}` exactly as for any real refusal. No automatic new key, no change to the key format or the attempt numbering, none to the real-refusal path or to pending/credited handling.
 Counter (derived from insert-only rows, no migration): a write-once marker per case-less answer in `ops.workflow_marker`, kind `credit_flap:{attempt}` (one kind per attempt, so a later key starts from zero), subject the transfer id, seq the occurrence 1..N, value the credit key. `recordCreditFlap` reads seqs 1..N with `getMarkers`, writes the FIRST ABSENT seq (first writer wins) and returns how many are on record; at N the credit step calls `refuse(...)`, which is the existing `openCreditCase`. Crash safety: a crash after the vendor's answer and before the marker write (or before the outcome write) loses nothing but time: the next cycle sends the same key, the honest vendor replays the same answer and it is counted then, so the case opens one cycle later. Racing sweeps: two sweeps may count one answer once (both write the same seq), they cannot open two cases because `reopenableCase` is `insert ... on conflict (dedupe_key) do update ... where status in ('resolved','dismissed')`, which inserts nothing for an open case. While a case is open the step returns before any vendor call (unchanged). A return before the journal reads the stored outcome `refused` and opens no case (unchanged).
 Tests, all in `loads.test.ts` (suite `NOT_SUCCEEDED with no case opens ONE case after the third answer`, using `honestCreditVendor` from `honest-credit-vendor.ts`: the first final answer per key is stored and replayed, `pending` and an outage are not stored; never `mockResolvedValueOnce`), plus the unit rows in the T-0766 suite:
 1. (flipped characterization) request + sweeps: calls stay `:credit:1`, the third answer opens exactly one case, no journal, transfer `submitted`, later sweeps open no second case and call no vendor.
 2. (control) a real refusal `ACCOUNT_UNAVAILABLE` opens one case at once, no flap marker, resolve takes `:credit:2`, one journal.
 3. (what a flap that clears can reach; with an honest vendor a later answer other than `NOT_SUCCEEDED` for the same key is impossible) two answers then the load is returned: no credit case, no returned case, the existing handling; counts of two transfers never add up; `pending` and an outage are not counted and the load then credits under the same key.
 4. resolving the case takes `:credit:2` and credits once with one journal; a second run of answers on `:credit:2` counts from zero and reopens the case at attempt 2.
 5. crash points: (5a) the flap-marker write lost, (5b) the vendor answer lost, (5c) two racing sweeps open one case, (5d) N-1 answers then a return opens no extra case; and unit tests of `recordCreditFlap` (1, 2, 3 then stays 3, attempts and transfers separate, first absent seq written, no overwrite) and of the credit step over a scripted db (T-0766 suite).
 Differential: `load-credit-flap.differential.test.ts` runs seeded random sequences (answers credited / pending / NOT_SUCCEEDED / real refusal / outage; crashes; resolves; returns; sweeps) and checks the invariants; its trace is also dumped with `T0786_DIFF_OUT` and was compared with the same file run on origin/main; the sequences that differ are listed in the PR body.
Decision to take (taken: see above), with the recommendation:
 (1) TAKE THE NEXT KEY after a case-less `NOT_SUCCEEDED`. The attempt number must then come from something other than the case payload (a case-less refusal has no payload): for example the highest `credit_began` seq for the transfer plus one when its stored outcome is `refused`. Fixes the stuck load by itself in one more sweep. Costs: changes the attempt numbering and key rule T-0766 kept out of scope; and a risk of DOUBLE CREDIT if the vendor's `NOT_SUCCEEDED` is a flap that later settles (the first key's refusal is final at the vendor, but a load that then reads `succeeded` is credited by the second key; the port contract says a different key for a load already credited answers `credited` and moves nothing more, so the vendor is the guard, and that guard is the thing the vendor question below must confirm). Also a return before the journal after attempt 2 began must read attempt 2 (`creditMayHaveMoved` follows the same attempt number).
 (2) OPEN A CASE after N consecutive case-less `NOT_SUCCEEDED` answers for the same key (N proposed 3, so a one-off flap resolves itself with no noise), keeping the same key; staff decide through the existing `load_credit_refused` case (resolve it and the retry takes the next key, as today for any real refusal). Costs: a load waits N sweep cycles before anyone knows; needs a counter, which is a derived read, not a new column (count the `credit_began` rows is not enough because the seq does not move, so either a new insert-only marker kind per answer, no migration, or reading `ops.transfer_event`); the existing `reasonCode` on the case is `NOT_SUCCEEDED`, and the `load_credit_refused` runbook (T-0746) must say what staff do with it (it is not a vendor refusal of the account).
 (3) BOTH: (2) first, so staff are told, and (1) as the action when they resolve the case (which is what the case already does). Costs of both, with the least new behaviour: (2) is the only new code path, (1) is the existing resolve-then-next-key path used as is.
 Recommendation: (3), which in code is (2) alone: after N case-less answers open the case, and let the existing resolve path take the next key. It tells staff, changes no key rule and no attempt numbering before a human has looked (so no automatic double credit), and uses the one path T-0705 already tests. Choose (1) only if the vendor says `NOT_SUCCEEDED` is never transient and an automatic new key is safe.
Open question for the vendor (docs/vendors/crowded/README.md, question 73, for the next meeting list): is `NOT_SUCCEEDED` ever a transient state, that is, can a load that a credit attempt found not `succeeded` read `succeeded` later and be credited under a NEW key; is a refusal replayed for the same key for the whole idempotency window (about 48 hours, to be confirmed); and what happens to a key after the window ends? Until it is answered the safe default is staff decide (option 2).
