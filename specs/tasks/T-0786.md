# T-0786 [WAL] A credit that was refused `NOT_SUCCEEDED` and later credited under the same key is read as "may have moved" by a return before the journal

STATUS: SCOPED, BUILD-READY. NEEDS AN INDEPENDENT REVIEWER (money-adjacent: it decides whether a case is opened for money the vendor may hold; the author must not review it). Files: apps/api/src/wallet/load-credit.ts, apps/api/src/wallet/loads.test.ts, specs/tasks/T-0786.md, specs/tasks/README.md
Source: T-0769 review (2026-11-23). The sequence, all in `load-credit.ts`: (1) `creditStep` writes `credit_began:{n}` and calls `creditWallet`; the vendor answers `refused` with `reasonCode: NOT_SUCCEEDED` (the vendor's read flapped). The line `if (result.status === 'refused' && result.reasonCode !== 'NOT_SUCCEEDED') return refuse(...)` opens no case, but the line before it has already stored `credit_outcome:{n} = refused` through `recordCreditOutcome`. (2) `creditCase` finds no case, so the next sweep computes the same `attempt = found.attempt + 1` and calls again with the SAME key `{wf}:credit:{n}` (by design, "retried with the same key, no case"). (3) The vendor now reads `succeeded` and answers `credited`; `recordCreditOutcome` is write-once (`putMarker` is `on conflict do nothing`, `club_app` has select and insert only), so the stored outcome stays `refused`. (4) A crash before the journal posts, then the vendor returns the load: `LoadService.fail` calls `creditMayHaveMoved`, which finds no open case, `began` true and `outcome === 'refused'`, returns `undefined`, and `openReturnedCase` is never called. The money the vendor credited to the member's wallet has no case and no journal. The comment on `creditMayHaveMoved` and on `recordCreditOutcome` ("conservative: it can only open a case, never hide one") is true for `pending` and for a missing outcome but not for this `refused`. The existing test `(a)` in `loads.test.ts` pins the single-call half (one `NOT_SUCCEEDED`, then a return: no case), which stays right; nothing covers a later credit under the same key. The provider is the same throughout (markers are keyed by the transfer id).
Design: the stored `refused` is only final when the attempt was never sent again. Add a write-once marker kind `credit_resent` (subject = transfer id, seq = attempt, value = the credit key) written by `creditStep` immediately before every vendor call for an attempt whose stored outcome is already `refused` with no open case (the retry after a case-less refusal), through a typed `recordCreditResent`. `creditAttemptState` returns `resent: boolean` and `creditMayHaveMoved` reads a `refused` outcome with `resent` true as "may have moved" (returns the vendor id; the return opens one `load_returned_after_release` case, stage `before_journal`, exactly as for `pending`). Why this and not the alternatives: (a) "treat `refused` as may-have-moved always" reverses test `(a)` and opens a case for every flap that never reached the vendor's credit, which is noise for people on a money queue; (b) "never reuse a key after a refusal" is what the vendor contract says for a real refusal (refusal final per key, T-0761, T-0705) and a case-opening refusal already takes the next key, but the attempt number is read from the case payload (`creditCase`), a case-less refusal has none, and making it advance means changing key format and attempt numbering, which T-0766 kept out of scope and which risks double credit across a deploy; (c) updating the stored outcome needs an UPDATE grant, which means a migration, out of scope. The new marker is insert-only, needs no migration (the kind is a string), and fails safe: a crash between the marker and the call reads as may-have-moved, the same as a missing outcome today. A resend that is answered `refused` again changes nothing more (the outcome stays `refused`, `resent` is true, so a later return opens a case: conservative, one case, the cost of a rare flap twice).
Test first: TST-WAL-003, in the T-0705 credit suites of `loads.test.ts` beside test `(a)`, using the same `build()` with the credit spy and the `dieOnPost` and `returned` controls. New (red on 816520d): (1) `NOT_SUCCEEDED`, then the same key answered `credited`, then the journal post throws, then a return: `credit_outcome:1` stays `refused`, the transfer is `failed`, and exactly one `load_returned_after_release` case exists with `stage: before_journal`; red on current code because no case opens. (2) The control: `NOT_SUCCEEDED` once and a return opens NO case (test `(a)` unchanged, green before and after). (3) `NOT_SUCCEEDED` twice then a return: one case. (4) A real refusal (a case opens, attempt 2 takes key `:credit:2`) behaves as today: a return while the case is open opens no returned case; after resolve, attempt 2 begun and credited then a crash and a return opens one. (5) Unit: `creditAttemptState` reads `resent` false with no row and true with the row; `recordCreditResent` twice stores one row; the sequence replayed (two sweeps) writes one `credit_resent` row and one credit key.
