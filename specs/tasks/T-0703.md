# T-0703 [WAL] Crowded payment events move a hosted load: re-read, then hold, credit or fail, replay-safe
REQ: REQ-WAL-002, REQ-WAL-003 (after T-0700) · Sprint: later (ADR-018, proposed)
Files: apps/api/src/webhooks/crowded.ts, apps/api/src/webhooks/crowded.test.ts, apps/api/src/wallet/loads.ts, apps/api/src/wallet/loads.test.ts, apps/api/src/app.ts (shared composition root: the `funding` handler), packages/adapters/src/crowded/funding.ts, packages/adapters/src/crowded/funding.contract.test.ts, specs/tasks/T-0703.md, specs/tasks/README.md
Source: ADR-018 and the snapshot ("Collect" event types, "Payment Event Data"). The receiver `/webhooks/crowded` (T-0649) already verifies the HMAC over the raw bytes, dedupes by `eventId` and stores the batch; its `process` re-reads the object and hands the current state to a handler. It is gated by `institutions.usBanking` and its `collected` handler is chapter-granular for institution fees. `FundingPort.parseWebhook` returns one event, which does not fit a batch, so the Crowded funding adapter does not use it.
Assumption: A4 (a bank-transfer `Succeeded` starts the hold, a card `Succeeded` credits), A5 (a return before release reverses the hold and fails the load; after release it is T-0705).
Test first: TST-WAL-003. A signed batch with `collect.payment.processing` then `collect.payment.succeeded` for an ACH payment of a member-chapter intent leaves the load `pending_hold` with one hold journal and `holdUntil` set; the same batch twice, and the two events in the other order, change nothing more (both re-read the same current state); `collect.payment.returned` while held fails the load and reverses the hold journal once; a `collect.payment.failed` event for a payment that the re-read shows `Succeeded` changes nothing (the compatibility event for ACH returns and cancels does not decide, the read does); a card `Succeeded` settles through the existing `settle` path (one journal, `{workflowId}:settle`); a payment whose amount differs from the transfer is refused with `VALIDATION_FAILED`, as `applyWebhook` does for Stripe; an event for a payment no load owns is stored and ignored; a bad signature answers 401 with one `ops.inbound_rejected` row and applies nothing.
- `CrowdedHandlers` gains `funding?(chapterId, paymentRef)`; `process` calls it for `collect.payment.*` events whose chapter is the platform member chapter (`memberChapterId`, injected by T-0709), and keeps calling `collected` for every other chapter. The handler calls a new `LoadService.applyVendorLoad(loadId, now)`: `getLoad`, then `applyVendorState` for the transfer found by `byVendorLoad`, the same path `applyWebhook` ends in.
- Gates: the route is open when `institutions.usBanking` or `wallet.enabled` is on. A member-chapter event while `wallet.enabled` is off is stored and left unprocessed (it throws `FEATURE_OFF`, so replay applies it once the flag is on); an institution event while `usBanking` is off behaves as today.
- The Crowded funding adapter's `parseWebhook` always answers `BAD_SIGNATURE` (fail secure): a Crowded delivery on `/hooks/funding` is refused and recorded, and only `/webhooks/crowded` accepts it. A test shows `/hooks/funding` refusing a validly signed Crowded batch.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the release step and a return after release (T-0705); the replay job itself (RUN-05, unchanged); event types other than `collect.payment.*` (collections, intents and refunds stay on the institution path); registering the webhook at Crowded (an ops step in `docs/vendors/crowded/README.md`, "Webhook registration"; the registration must list `collect.payment.*` explicitly, the docs say new event types are not added automatically).

Follow-ups carried from the T-0700 and T-0699 reviews (2026-11-12), to fold into this card or a small card:
- Map EVERY payment seen on an intent to its load (`load:payment:<paymentId>`), not only the standing one, so a webhook that names an earlier failed payment is not answered `UNKNOWN_LOAD`.
- Persist the first-seen success instant per load so `holdUntil` does not drift with the payment's `updatedAt`.
- Ledger get/put failures must surface as `PROVIDER_UNAVAILABLE`, not a raw `Error` (`packages/adapters/src/crowded/funding.ts` and the member-accounts adapter).
- `payerIp` is in the key-binding MAC, so a retry from a new IP is `VALIDATION_FAILED`: consider leaving the IP out of the binding.
- Concurrent distinct keys with colliding titles could alias one collection; that needs an atomic claim. Note for a ledger with real shared storage (the in-memory ledger cannot show it).
- `searchParams.delete` re-serialises the query string (cosmetic only).
- `isPublicIp` (port code from T-0697) treats `2002::/16` and `2001:db8::/32` as public: fix in a small card.

## As-built
- `apps/api/src/webhooks/crowded.ts`: `CrowdedHandlers.funding?(chapterId, paymentRef, intentRef?)` and `CrowdedWebhookDeps.memberChapterId`. For `collect.payment.*` of the member chapter `process` reads `data.paymentId` (or `data.id`) and `data.intentId` (Crowded's "Payment Event Data" carries both; the card named only the payment ref, the intent is an addition so a payment no read has seen yet still finds its load), builds `crowded:<chapter>:<id>` refs and calls `funding`; the body decides nothing. Other `collect.*` events of the member chapter are stored and ignored; every other chapter keeps the `collected` path. The route is open when `institutions.usBanking` or `wallet.enabled` is on. A member-chapter payment event with `wallet.enabled` off, and an institution event (application, ACH, collect) with `usBanking` off, throw `FEATURE_OFF` from `process`: stored, row left unprocessed with the error, applied by replay once the flag is on (the card said an institution event "behaves as today"; today the flag-off route answered 404 and stored nothing, and keeping the event is the safer reading once the route is open for the wallet). Events of types no handler owns are never flag-gated. Signature, dedupe by `eventId`, constant-time verification and the `ops.inbound_rejected` row are the T-0649 code, unchanged.
- `apps/api/src/app.ts` (shared composition root, said here as the card asks): `crowdedMemberChapterId` option (T-0709 will supply it from configuration) passed as `memberChapterId`, and the `funding` handler, which calls `loads.applyVendorLoad(intentRef ?? paymentRef, now)` and then any injected `crowdedHandlers.funding`. No route, OpenAPI, flag or registry change.
- `apps/api/src/wallet/loads.ts`: `LoadService.applyVendorLoad(loadId, now)`: `port.getLoad`, the transfer by `byVendorLoad` (else through `metadata.intentLoadId`, so a payment-named read finds the transfer linked under the intent id), then the same amount check and `applyVendorState` as `applyWebhook` (now both go through `applyToTransfer`). `UNKNOWN_LOAD` from the port, or no transfer, is ignored (`undefined`); other errors rethrow so replay retries. The journal metadata names the id the transfer is linked under. A credited (`settled`) load the vendor now says failed is left alone: a return after release is T-0705.
- `packages/adapters/src/crowded/funding.ts`: `parseWebhook` answers `BAD_SIGNATURE` always; `/hooks/funding` refuses a validly signed Crowded batch (tested). Follow-ups applied: (1) every payment seen on an intent is mapped (`load:payment:<ref>` for each, not only the standing one) and `metadata.intentLoadId` was added; a payment never seen on any read is still `UNKNOWN_LOAD` with no request (the event's `intentId` covers that case in the receiver). (2) The first-seen success instant of a bank transfer is kept per payment (`load:succeeded:<payment>`), so `holdUntil` no longer moves with Crowded's `updatedAt` (tested with a drifting `updatedAt` and a second adapter on the same ledger). (3) The ledger is wrapped so any get or put failure is `PROVIDER_UNAVAILABLE` with fixed text (tested). (4) `payerIp` is validated (public address) but no longer in the key-binding MAC: a retry of a key from another network is the same load; the success and failure urls still bind.
- Follow-ups NOT done here (outside the card's files), for a small card: the same ledger-failure wrapping in `member-accounts.ts` and `institution-banking.ts`; the atomic claim for concurrent distinct keys with colliding titles (needs a ledger with real shared storage); `searchParams.delete` re-serialising the query string (cosmetic); `isPublicIp` treating `2002::/16` and `2001:db8::/32` as public (`packages/ports/src/funding.ts`).
- Not built, by design: the hosted `createLoad` call from `LoadService.pull` (it does not pass `hosted` yet, so the tests make the transfer with `begin`/`submit`/`link` around the adapter), the registry binding and `memberChapterId` configuration (T-0709), the release job for a held Crowded load and a return after release (T-0705), registering `collect.payment.*` at Crowded (ops step). Tests: `crowded.test.ts` (member-chapter describe, 14 cases: hold once and replay-safe in both orders, intent-less payment, return while held, `failed` event over a `Succeeded` read, card settle once, payment-only event, amount mismatch, unowned payment, bad signature, `/hooks/funding`, flag off then replay, wallet-only route, both flags off, routing), `loads.test.ts` (`applyVendorLoad`, 3 cases), `funding.contract.test.ts` (6 new cases).
