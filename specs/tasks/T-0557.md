# T-0557 [ESIM] Add-on orders: the loser of a same-key create gives its credit back
REQ: REQ-ESIM-001, REQ-WAL-001 · Sprint: fix (medium, follow-up of T-0548 review F13/F15)
Files: apps/api/src/addons/orders.ts, apps/api/src/addons/orders.test.ts, specs/tasks/T-0557.md, specs/tasks/README.md
Source: T-0548 Out of scope. In `AddonOrderService.create` the credit is applied (`credit.apply(..., id, ...)`, an entitlement consumption keyed `addon:{id}` with a fresh `uuidv7` id) before the order row is inserted. Two creates with the same Idempotency-Key both pass the `byKey` check and both consume; the loser's insert hits the unique violation, returns the winner's order, and its own `addon:{loserId}` consumption stays for good: the member loses plan credit for an order that does not exist. Re-read `create`, `restoreCredit` and `credit.ts` first.
Test first: TST-MKT-001. A member with eSIM credit in their plan sends two `create` calls with one key at once (`Promise.all`): one order row, one charge journal, but the entitlement usage is two orders' units on main.
- When the order insert fails (the unique violation, or any other error), the credit applied for that attempt is handed back: the same negative consumption row `restoreCredit` writes (`addon:{id}:refund`, idempotent on conflict), for the attempt's own id. Factor `restoreCredit` to take an order id and the credit amount so the refund path and this one share it.
- The winner's credit stays consumed once; a replay of the key later (the `existing` path) consumes nothing.
- Known window left open and named here: a crash between `credit.apply` and the insert still strands one consumption. Closing it means moving the consumption after the row (the quote is stored on the row); only do that if it fits the 400 lines, else leave it in the card's As-built as a follow-up.
**Tests.** the concurrent same-key create above: one order, one journal, usage equals one order's units, the loser's consumption net zero; an insert that fails for another reason hands the credit back; a sequential replay consumes nothing; a refunded order still restores its credit once (existing behaviour unchanged). Use the same race setup as T-0548's unique-violation test.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: the funds pre-check race between different keys (it is a pre-check, not a lock; its own card); the crash window above unless it fits. Stop and ask on conflict with the spec.

## As-built
- `AddonOrderService.create`: when the order insert fails for any reason, the credit that attempt consumed is handed back before the error is handled, so the loser of a same-key race no longer keeps a consumption for an order that never exists. Then the unique violation still returns (and charges if still `created`) the winner's order. `restoreCredit` now takes `(orderId, credit)`; `refund` and the insert-failure path share it, and the refund row `addon:{id}:refund` is idempotent on conflict. The winner's `addon:{id}` consumption is untouched, so it is consumed once and a later replay consumes nothing.
- One addition the race needs in practice: `consume` re-checks the limit, so on a plan whose credit the winner used up entirely, the loser's own `consume` threw `LIMIT_EXCEEDED` instead of reaching the insert. `create` now looks the key up on that error and returns the winner's order (same-request check applies); with no winner the `LIMIT_EXCEEDED` stands.
- Tests (`orders.test.ts`): concurrent same-key create via `Promise.all` on a 20 GB plan (one order, one charge journal, usage and net consumption equal one order's 5 units, one refund row); the same race on the 5 GB plan returns the winner's order, not `LIMIT_EXCEEDED`; an insert failing for another reason hands the credit back and a retry starts clean; a sequential replay adds no consumption row; a refunded order restores its credit once. The first three failed on main (usage `10` instead of `5`; `LIMIT_EXCEEDED`; the consumption left at `5`).
- Crash window left open, as the card allows: a crash (process death) between `credit.apply` and the insert still strands one consumption, since no code runs to give it back and its id is never reused by a retry. Closing it means inserting the row first (the quote is on the row) and consuming after, which also needs a state for "row without consumption" and a reconciliation of a failed consume against a row that already promises the credit; that is more than this card and is a follow-up. A failure of the refund write itself in the catch path has the same effect and also surfaces as the error.
- `specs/tasks/README.md` already has the T-0557 row, so it is unchanged. The funds pre-check race between different keys is untouched (out of scope).

### Review follow-up (REQUEST CHANGES on 27db95f)
- The insert-failure path no longer refunds blindly: it first reads the row under this attempt's own id. An insert that committed but whose reply was lost leaves a real order, so its consumption is kept and `create` carries on to `charge` (the member gets one order, charged once, credit consumed once). Only with no row under the id is the credit handed back. Test added (`commit-then-error`, fails on 27db95f: the credit was refunded and the error rethrown). If that read itself fails, nothing is refunded and the error propagates (a stranded credit is the safe side of the open window, never free data).
- `restoreCredit(orderId)` now gates on the `addon:{id}` consumption row alone, not on `credit.minor`. This also changes `refund` for the one case it was wrong: a consumed credit worth zero money (integer division on a tiny price) now gets its units back; orders with no consumption row behave as before.
- Residual race, left as is: if the winner has consumed but not yet inserted, `byKey` is empty for a loser whose own consume is refused, and the loser gets a spurious `LIMIT_EXCEEDED`. No money or credit is lost and a retry with the key returns the order. The `LIMIT_EXCEEDED` race test depends on scheduling (the winner's row being there when the loser looks); a deterministic version needs a stale quote injected between quote and consume, which is not cheap, so it stays a `Promise.all` test.
