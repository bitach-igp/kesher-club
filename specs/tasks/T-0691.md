Source: gap audit 2026-11-09, item 10. ADR-004 lists social sign-in as optional; the API has no route. Needs the owner's Apple and Google client ids before it can run for real; the simulator stands in until then.
Test first: `GET /v1/auth/social/providers` lists Apple and Google together or neither (flag `auth.social` off lists none, and the sign-in route answers `FEATURE_OFF`); a verified identity token for a known member signs in; for an unknown identity it answers `NOT_FOUND` and creates no member (passkeys stay the primary path); a token for the wrong audience is rejected.
- Verification goes through the port (extend with `verifyIdentityToken` and its contract suite); the flag defaults `false`. As built the port is `FederatedIdPPort` (T-0117), not `AuthPort` (which is passkeys and OTP), and the flag is the existing `auth.social.enabled`.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: account linking from settings; Apple revoke (T-0692).

## As-built
- Port: `FederatedIdPPort.verifyIdentityToken(provider, { idToken, nonce })` (T-0117's Apple/Google port, not `AuthPort`, which is passkeys and OTP). The OIDC base adapter runs the same `jose` verification as the code exchange (signature against the cached JWKS, issuer, audience = our client id, expiry, then the nonce) and returns a `FederatedIdentity` without a refresh token; `FederatedIdPRouter` routes by provider; the simulator takes the code grammar `ok:<subject>[:relay][:nonce=<n>]` plus `badaud`, `expired`, `badsig`, `outage`. Contract suite: a good token per provider with a stable subject and a nonce check; wrong audience, expired, bad signature and garbage all `INVALID_CODE` (the adapters mint these with `FakeIdP.mintIdToken`). No JWT check lives in `apps/api`.
- API (`apps/api/src/auth/social.ts`): `GET /v1/auth/social/providers` (`listSocialProviders`, public) answers `["apple","google"]` while `auth.social.enabled` is on and `[]` while off; `POST /v1/auth/social/sign-in` (`signInWithSocial`, public) takes `{ provider, idToken, nonce, deviceId }`. Off: 404 `FEATURE_OFF`. Failed token (bad signature, expired, wrong audience, wrong nonce): 401 `UNAUTHENTICATED`. Provider down: 503 `PROVIDER_UNAVAILABLE`. Bad input: 422 `VALIDATION_FAILED`. Verified but nobody linked: 404 `NOT_FOUND`, no member created. Linked: the same `tokens.issue` pair as a passkey sign-in, device upserted, `new_device_sign_in` pushed to the passkey service's event list when the device is new. A closed account is 401.
- Link storage needs no migration: a member is linked by an `ops.external_ref` row (`entity_type 'member'`, `entity_id` the party id, `provider` `apple` or `google`, `external_id` the IdP subject), the repo's vendor-id map. The unique keys give one subject per member per provider and one member per subject. Nothing writes these rows yet (linking from settings is out of scope); tests insert them.
- No Idempotency-Key and no step-up on the sign-in, as for the passkey sign-in; no new error codes, no new flag, no migration. Shared plumbing touched: `apps/api/src/app.ts` (builds `SocialSignIn` and adds its handlers) and `apps/api/src/routes.ts`; `HEADER_OPS` unchanged.
- The card's `auth.social` is the flag `auth.social.enabled`; `config/flags.json` is unchanged. Real Apple and Google client ids (`PROVIDER_FEDERATED_IDP=oidc`) are still the owner's; the simulator is the default binding. Not covered: a real Apple or Google token, and the real-Postgres read of `ops.external_ref` (PGlite only).
