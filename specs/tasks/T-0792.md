This card is the behaviour only: `startStaffSso`, `startStaffSsoLink`, `completeStaffSso` (302, not tokens) and `exchangeStaffSso`; the path parameter is `{id}`, not `{institutionId}`. Design the behaviour PR must follow:
- State: stored hashed in `ops.workflow_marker` (kind `sso_state`, SHA-256 in `claim`, value = institution, mode, party for a link, invite id if any, device id, session id, browser-binding hash, expiry); ONE row per start. A `link` state lives 5 minutes (the step-up's window), a `sign_in` state 10. The browser binding is an `HttpOnly; Secure; SameSite=Lax` `__Host-` cookie; use a per-state cookie name, or document the one-flow-per-browser limit. Cookie hashes are compared with `timingSafeEqual`. There is no PKCE or nonce in the port: the cookie binding plus the single-use state carry the CSRF defence.
- Order at the callback: flag, shape, state lookup, cookie check, expiry, THEN claim the write-once `sso_state_used` marker (after the cookie check so an attacker holding the state cannot burn it; before the IdP exchange so a replay or concurrent double submit has one winner), then the port. Every refusal is the same 302 `#error=refused` with the same headers, and the same reads padded to one latency class, including unknown, expired and unbound state. Nothing is written on a refusal.
- Identity: the institution comes from the stored state; `identity.orgId` must equal it and the institution's per-org record must exist. Sign-in needs a live link to an ACTIVE staff row of that institution. Link completion re-verifies that the session is not revoked, the party is still active staff of the institution (or the invite is still valid and is CONSUMED here through `InstitutionTeam.accept`, never at start), and no live link exists; then `StaffIdpLinks.link` (its 409 and 404 become the uniform refusal). Never `team.accept` at start.
- Success: write a one-time exchange code (hashed, 60 seconds, one row plus the write-once used marker at redemption) and redirect to the fixed console URL (`AppOptions.orgIdp`, never caller-controlled) with `#code=`; `exchangeStaffSso` redeems it once and issues the normal token with the user's stored roles (never an IdP group).
- PKCE-style verifier (login CSRF): `challenge` (base64url SHA-256, 43 characters) is required at both starts, stored in the state row and copied into the exchange-code row; `exchangeStaffSso` requires the `verifier` and compares SHA-256(verifier) with the stored challenge by `timingSafeEqual`. A wrong or missing verifier is the same uniform 401, does NOT consume the code, and counts toward a cap of 5 attempts per code after which the code is dead. Count only for codes that exist (no counter row for an unknown, attacker-chosen code: its growth would be attacker-controlled; the edge rate rule covers those). Do not reuse the cookie (cleared at the callback; the console may be on another origin).
- Exchange: claim the write-once used marker for the code, issue the token only to the winner, and a failed token issue must not leave a replayable code (claim after the issue succeeds, or release through a marker the retry reads, never a state where the code is claimed and no token exists AND the winner cannot retry).
- Callback timing: call the IdP regardless of state validity, or equalise the latency, so unknown, expired and unbound states are not distinguishable by timing. Every query parameter is optional: a missing or malformed `code` or `state`, or an IdP `error` redirect, is the same 302 `#error=refused`, never a 422.
- `link/start` order: the global flag-off 404 first (same for everyone); then bearer, step-up, body; THEN the membership-or-invite check, and every non-member (including a malformed or unknown institution) gets the one 404 NOT_FOUND whether or not the institution has SSO; only a member sees FEATURE_OFF for a missing SSO record, the 409 for an existing live link, or 429. For an invite holder the invite is re-checked at the callback, and `accept`'s IDEMPOTENCY_CONFLICT and NOT_FOUND map to the uniform refusal.
- Limits: no application counter on the public start (edge rate rule is a requirement, T-1120); `RATE_LIMITED` per party on the link start and per code on the exchange. A purge or TTL for the state and exchange rows is a follow-up card.
- GATE before `auth.orgSso` turns on (also in T-1116 and the README checklist): the WorkOS adapter keeps its SSO state, deactivations and seen events in per-process memory, so a start on one API instance and a callback on another fails; the real flow works only on one process until that moves out. The adapter's own `orgId` check is a tautology in the callback, so the institution and record checks live here.
