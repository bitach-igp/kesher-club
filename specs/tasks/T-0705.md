# T-0705 [WAL] A load credits the vendor wallet before its release journal, a member with a refused account cannot load, and a return after release opens a case
REQ: REQ-WAL-003, REQ-WAL-002 (after T-0698, T-0703, T-0704) · Sprint: later (ADR-018, proposed)
Files: apps/api/src/wallet/loads.ts, apps/api/src/wallet/loads.test.ts, apps/worker/src/wallet/release-holds.ts, apps/worker/src/wallet/release-holds.test.ts, specs/tasks/T-0705.md, specs/tasks/README.md
Source: ADR-018 and `LoadService` (`settle`, `release`, `applyVendorState`). Today `release()` asks the vendor, then posts `pending -> wallet`. With a vendor that holds the money, the vendor step (T-0704) must come first and the journal only after it is `credited`, or our wallet shows money the vendor never moved. A return after release today throws: `applyVendorState` calls `fail()` on a settled transfer, which the state machine refuses.
Assumption: A4 (credit at the vendor, then post the release; a card credits at once), A5 (a return after release is a platform loss, an ops case, no debit), A1 and A2 (the member's account must exist and be `open`).
Test first: TST-WAL-003. A held hosted load whose hold date passes: the sweep reads the payment, calls `creditWallet` once, then posts one release journal `{workflowId}:release`; a `pending` answer from `creditWallet` posts nothing and the next cycle retries with the same key; a `refused` answer posts nothing and opens one `load_credit_refused` case per load (dedupe key `load-credit:{transferId}`, severity high), the hold stays; a crash between the vendor call and the journal is finished by the next sweep without a second vendor movement (the keys are the same) and one journal; a card load credits at the vendor before its single settle journal; a vendor with no `creditWallet` (Stripe, the simulator) skips the step and posts exactly the journals it posts today (every existing test passes unchanged); a `Returned` read of a load that has been released does not throw: it opens one `load_returned_after_release` case (dedupe key `load-returned:{transferId}`, payload: loadId, amount, member, the failure code), posts no journal and leaves the wallet alone; a return that arrives before release still reverses the hold once (unchanged); a hosted load for a member whose `ensureAccount` answers `rejected` or `frozen` is refused before any vendor call with `FEATURE_OFF` naming the status, and no transfer is created for it (the gate runs before `begin`).
- `LoadService` takes an optional `credit` dependency (the `FundingCreditPort` and `FundingAccountPort` found on the funding binding) and calls `ensureAccount` in `request()` for hosted loads, storing `funding_contract` and `funding_account` in `ops.external_ref`; the account ref is read back by the release path.
- `ReleaseHoldsJob.run()` reports `credited` and `refused` counts beside `released`, and the existing SLA (`lagMs`) is unchanged.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: a debit or reversing journal for a return after release (a person decides, case first); the float alert for the chapter checking account; the funder (non-member) contact; the closure refund (T-0706); the app.
