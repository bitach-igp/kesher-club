CLAIM RE-VERIFIED, TRUE, and wider than stated. `standardWebhooksVerifier` (`apps/api/src/webhooks/verify.ts:67-77`) and `stripeVerifier` (`:80-90`) are referenced only by `apps/api/src/webhooks/handler.test.ts:17,51,52,165,166,190` and by two quoted review notes (`review/CODEBASE-REVIEW.md` F26). Both are thin wrappers over `hmacVerifier` (`:34-64`), and `hmacVerifier` has no other caller either, so the generic HMAC verifier is test-only as a whole; only `simulatorVerifier` (`:92`, used by `cards/provisioning.ts:130` and `app.ts:295`) and the `Verified`/`WebhookVerifier` types are live. Built under T-0204 ("Inbound webhook store, verify, dedupe, replay", REQ-LED-003, sprint 4; squashed in `be6a86a`, #142) before the vendor adapters existed, to give each vendor a header-based verifier.
How the real receivers verify today (read in code, `app.ts` bindings `:233-295`): Crowded: `POST /webhooks/crowded` is `CrowdedWebhook` (`webhooks/crowded.ts:129`, `handler()`), which verifies the raw bytes with `verifyCrowdedSignature` and several secrets before parsing anything; the generic `/hooks/crowded` route is bound to `refuseAllVerifier` (`crowded.ts:102`, `app.ts:233`). Stripe funding: `webhooks.bind('funding', { verifier: loads.webhookVerifier() })` (`app.ts:261`), whose verifier calls `StripeFundingAdapter.parseWebhook` and so `verifyStripeSignature` (`packages/adapters/src/stripe/signature.ts:31-52`: parses `t` and every `v1`, constant-time compare, 5-minute tolerance), with the previous-secret rotation wrapped in `registry.ts:255-266`. Payouts, KYC, bank and card token events verify through their own ports the same way. Stripe BILLING has no receiver at all (see T-0780). So the generic verifiers are not a duplicate of something unwired; they are a duplicate of what the adapters do correctly, and the missing wiring is the billing receiver, which should use the adapter, not these.
Defects (each re-read on main; F26 in `review/CODEBASE-REVIEW.md` flagged them as low, never fixed): (1) `stripeVerifier` sets no `timestampHeader` or tolerance (the timestamp is inside the `stripe-signature` header), so a bound `stripeVerifier` has NO replay window: a captured valid delivery verifies forever; (2) its `parseSignature` returns `[fields(v)['v1']]`, built from `Object.fromEntries`, so only the LAST `v1` survives, which fails closed during a Stripe secret roll (Stripe sends several); (3) `standardWebhooksVerifier` decodes `whsec_` with `Buffer.toString('latin1')` and hands the string to `createHmac`, which re-encodes it as UTF-8, corrupting any key byte above 0x7f: every real signature would fail closed; (4) `hmacVerifier` parses JSON and extracts the event id before checking the signature (`:43-46`) and the router falls back to `JSON.stringify(req.body)` when `rawBody` is missing (`webhooks/handler.ts:35`), which can never match a real signature. (1) is the only one that fails OPEN (replay); it is a security matter the day someone binds `stripeVerifier` to `/hooks/stripe` for billing, which is the natural next step for T-0780.
RECOMMENDATION: DELETE `hmacVerifier`, `standardWebhooksVerifier` and `stripeVerifier` (keep `simulatorVerifier` and the two types), and rewrite the `handler.test.ts` cases that use them with a small in-test verifier so the router's own behaviour (store, dedupe, forged signature recorded and refused, replay) stays covered. Standard Webhooks is OUTBOUND in this product (ADR-008, T-0803, we sign); no inbound vendor uses it. If the owner wants a generic verifier kept, fix defects 1 to 3 first and add the replay-window test.
