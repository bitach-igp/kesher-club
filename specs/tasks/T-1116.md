Files: packages/adapters/src/workos/workos.ts, packages/adapters/src/workos/workos.test.ts, packages/adapters/src/workos/fake-workos.ts, packages/ports/src/org-idp.ts (the directory entry gains the raw `state`), packages/ports/src/org-idp.simulator.ts, packages/ports/src/org-idp.contract.ts, apps/api/src/institutions/staff-deprovision.ts (the verifier's timestamp read, shared with the adapter), apps/api/src/institutions/staff-deprovision.test.ts, apps/worker/src/institutions/directory-drift.ts, apps/worker/src/institutions/directory-drift.test.ts, specs/tasks/T-1116.md, specs/tasks/README.md
Source: the T-0790 and T-0791 reviews. Each item below is a way a real removal is silently missed once WorkOS is live; the simulator hides all of them.
Behaviour:
1. Signature timestamp unit. `verifyWebhookSignature` (`workos.ts`) and the verifier in `staff-deprovision.ts` (`Math.abs(now - t * 1000)`) read `t=` of `WorkOS-Signature` as SECONDS. It is suspected to be MILLISECONDS, in which case every real delivery is refused as stale and no webhook ever deprovisions anyone. Verify against the current WorkOS documentation and SDK for webhook signatures (open the page, quote the unit and the signed string `${t}.${body}` in the PR), not from memory. Fix both readers to one shared helper. A header of the wrong unit must be refused, not widened to accept both.
2. A removal needs no email. `normaliseEvent` returns `undefined` for a `dsync.user.*` event with no primary email, so `dsync.user.deleted` or a deactivation for such a user is refused as `SCIM_MALFORMED` and the removal never completes. For `deleted` and a deactivation only the subject (`idp_id`), the directory and the event id are required; the email is required only for `created` and `updated`-active. The email is never used to find the link (the subject is).
3. `listDirectory` must fail closed: a page cap (named constant, refuses with `PROVIDER_UNAVAILABLE` past it), a fetch timeout per page (injected clock or abort signal; a hung read is a failed read), a page that answers 200 without `data` or with a non-array `data` is a FAILED read (today it is read as an empty page, so linked users beyond page 1 look absent and the sweep can remove them), a repeating `after` cursor is detected and fails the read, and a `list_metadata.after` of the wrong type fails the read.
4. Raw directory state. Each directory entry exposes the raw `state` string beside `active`. The sweep (`directory-drift.ts`) treats a state that is not exactly `active` or `inactive` (missing, unrecognised, any new WorkOS value) as SUSPECT: counted as `staff.drift_refused{reason=unrecognised_state}` and never as inactive, never a removal reason. A positive `inactive` still always counts.
5. Adapter state out of process (a GATE on `auth.orgSso`, from the T-0792 review). `WorkOsOrgIdPAdapter` holds the SSO `states`, the `deactivated` set and `seenEvents` in per-process memory: with more than one API process (or a restart between start and callback) a callback answers `STATE_MISMATCH`, and a deactivation learned by one process is unknown to the next. Either the adapter takes an injected store (Postgres-backed, no new vendor SDK) or the deployment is pinned to one process for SSO; the card decides and says which. Its own organisation check in `handleCallback` is the connection's, not ours: T-0792 checks the institution itself.
Test first: TST-AUTH-008 (sign with REAL-FORMAT headers built the way WorkOS builds them, not with the helper under test; a unit-confusion test fails on the wrong unit): (1) a delivery signed with the documented unit is accepted, the other unit and a 5-minute-old one are 401; (2) a `dsync.user.deleted` and a deactivation with no emails array and with an empty one both deprovision the linked member (one audit row), and a `created` with no email is still refused; (3) a page with no `data`, a page with `data: null` or an object, a cursor that repeats, a never-ending cursor chain past the cap and a hung page each reject with `PROVIDER_UNAVAILABLE` and the sweep removes nobody; (4) a directory user in an unrecognised or missing state is counted as suspect and not removed; a linked user on page 2 is never read as absent when page 2 failed.
