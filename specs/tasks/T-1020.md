Migration `0008_member_theme.sql` (header `-- T-1020 appearance preference (REQ-UX-002)`), extends the table from `0002_member_preference.sql` (`identity.member_preference`, one row per member who set ANY preference): `alter table identity.member_preference add column theme text not null default 'system';` then `alter table identity.member_preference add constraint member_preference_theme_check check (theme in ('system','light','dark')) not valid;`. The default makes the add safe: Postgres 11 and later adds a column with a constant default as a metadata change, no table rewrite, so the NOT NULL needs no backfill. The constraint goes on `NOT VALID` per CLAUDE.md because every existing row already satisfies it (the column just got `'system'`), so Squawk (the default is what keeps the not-null add safe; Squawk's rule names vary by version, so `pnpm db:lint` is the real gate, not a rule name) and no table scan; a follow-up `validate constraint` is NOT needed before launch (no live rows) but is written as a comment for the first live migration. `club_app` already has `select, insert, update` on the table; no new grant. One concern per migration, so the receive-currency column is untouched. Existing rows read `system`. NOTE the table's `receive_currency` is `not null` and a theme-only first PATCH has no receive currency: the upsert must insert `receive_currency = 'as_sent'` (the documented default) when it creates the row, and a later receive-currency PATCH must not reset the theme. The API default for a member with no row is `theme: 'system'`, `receiveCurrency: 'as_sent'`.
