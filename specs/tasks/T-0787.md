Design (NARROW on purpose): the owner's intent is clearing failed-owner markers. A bare `grant delete` would let any app code delete the credit (`credit_began`, `credit_outcome`), lost-key (`membership_lost_key`), payee (`payout_payee`) and purpose (`subaccount_purpose:{provider}`) markers, which must stay write-once: a deleted `credit_began` or outcome row erases the evidence the double-credit guard reads (T-0742), a deleted lost-key or payee row lets the same key or payee be taken twice. Postgres cannot grant delete per row, so migration `0034` does both: `grant delete on ops.workflow_marker to club_app` AND a BEFORE DELETE row trigger `ops.workflow_marker_delete_guard` (SECURITY INVOKER, `search_path = pg_catalog`) that raises unless `left(old.kind, 17) = 'subaccount_owner:'` (`left`, not `like`, so the underscore needs no escape). The trigger fires for every role including the owner and the superuser; the message names no kind, subject or value. No update grant and no truncate grant (a truncate does not fire row triggers, which is why it must stay ungranted). The TS side repeats the rule: `clearMarker(db, { kind, subjectId, seq? }): Promise<boolean>` throws before any query for a kind without the `subaccount_owner:` prefix, deletes with parameterised SQL, and returns whether a row was deleted (false: nothing was there; clearing twice is safe). The first clear after the owner is fixed is followed by the credit, because the sweep re-reads the marker every cycle (T-0763 design).
Test cleanup as a superuser: a test or desktop step that must remove a write-once marker uses `set local session_replication_role = replica` inside a transaction (row triggers do not fire); the one existing caller, the `drop` helper in `apps/api/src/payouts/service.test.ts`, is changed that way. The owner-marker deletes in `loads.test.ts` and `crowded.test.ts` need no change (owner kind).
