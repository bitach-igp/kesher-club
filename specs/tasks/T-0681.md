# T-0681 [WAL] Sweeps report how many times they asked the vendor

Source: T-0547's open gap ("the sweep asks the vendor about every held load each cycle") and the owner's choice, 2026-11-09, to measure before building a "last asked" marker.
Test first: no sweep report or log line carries a vendor-read count on main (`vendorReads` does not exist), so the three new cases fail.
- `LoadService.vendorReads` counts the vendor reads the release step makes (one per held load asked about). `ReleaseHoldsJob.run` reports the difference over its run as `vendorReads`; `LoadWorkflow.sweep` reports its own reads (a failed read counts) plus the release step's reads during the sweep, as `vendorReads`: a `pending` load resumed by the sweep is read once by the sweep and once inside `release`.
- The scheduler's `job_ran` log line carries `vendorReads` when the job's result has a numeric one, so the cost of a sweep is in the logs with no extra plumbing; a job that reports none logs exactly as before.
**Tests.** nothing due: 0 reads; a due hold: the report equals the reads the vendor saw; the load sweep's count equals the vendor's; a `job_ran` line carries `vendorReads`, and a job without one logs `{ job, ms }` only.

## As-built
- As above. Read the numbers in the worker logs: `ach-release-holds` and `load-sweep` lines now end with `vendorReads`. Held loads are asked about every cycle (5 minutes for the release job, 60 seconds for the load sweep), so the cost per day is roughly `vendorReads x cycles`; build the marker only if that is high or the vendor rate-limits.
- Review caught that a first version counted one read for a resumed `pending` load; it now counts both. The release job's count is the process's reads during the run (a counter delta), not a per-job count: `LoadService.release` is also reached from a request's own load run, so a request that releases during a sweep adds to that sweep's number. It is a measurement, not an invoice.
