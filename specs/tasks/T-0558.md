- `LoadService` records `last_asked_at` (upsert) after every vendor read of a held load, including an `UNKNOWN_LOAD` answer, in `release()` and in the worker's `resume()`.
- `stale()` returns a `pending_hold` load only when it has no marker, its marker is older than `HELD_RECHECK_MS` (6 hours, a named constant), or its hold is due (`holdReleasesAt` passed: asked every cycle until it releases). `submitted` and `pending` loads are unchanged.
- The trade-off is stated in the code comment: a return with no webhook is found within `HELD_RECHECK_MS` instead of within 10 minutes; a webhook still fails the load at once.

## As-built
- Migration `0032_load_last_asked.sql`: `ops.load_check (transfer_id uuid primary key references ops.transfer(id), last_asked_at timestamptz not null)`, `grant select, insert, update to club_app` (no delete). `atlas` is not installed in the cloud session, so `atlas.sum` was recomputed with a small script (cumulative sha256 over each file's name and bytes in order, then the sha256 of every name and per-file hash for the header); it reproduced all 31 existing lines and the header byte for byte before the 0032 line was added. The real Postgres apply is requested in `handoff/desktop/T-0558-load-last-asked.md`.
- `LoadService`: exported `HELD_RECHECK_MS` (6 hours) with the trade-off in its comment; `recordAsked(transferId, now)` upserts the marker. `release()` records it after a vendor read of a `pending_hold` load, including an `UNKNOWN_LOAD` answer; the worker's `resume()` records it after its own read of a held load. A read that throws any other error records nothing, so the next cycle retries. A `failed` answer records nothing either, so if `fail()` then throws transiently the load is asked again next cycle instead of being hidden for the interval (review S1); the worker's `resume()` does the same. `recordAsked` is monotonic (`where last_asked_at < excluded.last_asked_at`): an older clock reading never moves the marker back (N1). The worker's `resume()` also handles `UNKNOWN_LOAD` for a held load the way `release()` does, through `LoadService.holdUnknown` (marker and the one case); other loads still throw (G1).
- `stale()` returns a `pending_hold` load only when it has no marker, its marker is `HELD_RECHECK_MS` old or older, or its hold is due (`hold_releases_at <= now`, or null). `submitted` and `pending` loads are unchanged. The filter is in SQL, so `limit` still counts only loads that will be asked.
- Tests: `loads.test.ts` (never-asked hold swept, waits out the interval and is swept at exactly `HELD_RECHECK_MS`, due hold swept despite a fresh marker, one upserted row, a submitted load with a marker still swept, `UNKNOWN_LOAD` hold records its marker and one case and is not swept inside the interval); `load-workflow.test.ts` (a not-due hold swept three times in an hour is read once, which reads three times on main; a return during the hold is found by the first sweep after the interval and fails the load with the hold reversed, once; a due hold is read every cycle).
- Worker test expectations changed: none. The T-0539 expectations that count held loads every pass (`attempted: 4 + baseHeld`, `2 + baseHeld`, `1 + baseHeld`, and `3 + baseHeld` in the error test) still hold: the held loads earlier tests leave belong to provider `simulator`, while those sweeps run as `scripted` workflows, so `resume()` finds no vendor link for them, reads nothing and records no marker, and they stay in `attempted` each pass exactly as before. Only the new tests exercise a marker, and they use their own provider names.
- Review follow-up tests: a return whose `fail()` throws once is asked again on the next sweep and then failed; an unknown held load swept by the worker records its marker and opens one case; the marker does not move backwards and `release()` itself writes it.
- Not done: nothing from the card; a held load of a provider this worker does not serve is still attempted (not read) each cycle, which costs a query, not a vendor call.
