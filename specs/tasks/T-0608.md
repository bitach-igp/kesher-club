As built:
- **Which institution.** Nothing told a signed-in member which institution they staff, so the contract gained `GET /me/institution` (`getMyInstitution`). It reads the same active `org.staff` row every institution handler checks. A token without an `org_*` role, or a member with no active row, answers 403, and the console shows "no institution access". `apps/api/src/admin/institutions.test.ts` covers it:
  - before the grant: 403;
  - after the next sign-in: the yeshiva as `finance`;
  - after removal: 403 on the same token.
- **Sign-in is the passkey, not OTP first.** The API's passkey sign-in is discoverable: it finds the credential by its id, whatever the device id. So staff use the passkey they already have, from the computer or with their phone across devices. OTP remains the app's enrolment and recovery path; sign-in would only add a step.
- **Session handling:**
  - The console's server relays the ceremony through server actions and writes the pair into httpOnly, same-site-strict cookies (Secure outside `local`); page script sees no cookie.
  - `proxy.ts` resolves the session on every page request with `src/session.ts`: a 401 refreshes once with the console's device id, a second 401 or a failed refresh clears the cookies and goes to `/sign-in`, and a 403 lands on "no institution access".
  - The landing reaches the pages URI-encoded on a header only the proxy sets.
- **Step-up** arrives with the first money action (T-0610), through `@kesher/ui`'s `StepUp`; this card has no money action. The layout uses `@kesher/tokens` only, since nothing yet needs a `@kesher/ui` component.
- **Local demo.** With `CONSOLE_ENVIRONMENT=local`, the sign-in page lists the seeded finance staff (T-0034), whose passkeys the persona module derives. The import sits behind a `NODE_ENV` literal: a `next build` output holds no persona or seeded-passkey code (checked with grep on `.next/static` and `.next/server`), and the build needs no settings.
