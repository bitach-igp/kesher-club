CORRECTION TO THE T-0757 NOTE (money-state flag). T-0757 says "the sweep through `getLoad` still sees the load" once the owner is fixed. It does see it, and it CREDITS it: `LoadService.creditStep` (`loads.ts:549-592`) checks only the vendor status, the account ref and `accountBlock` (the vendor's account status, `:600-610`), never the owner marker; `grep owner apps/api/src/wallet/loads.ts` finds nothing. The worker sweep (`apps/worker/src/wallet/load-workflow.ts:52-77`: `stale` then `getLoad` then `applyVendorState` then `settle` then `creditStep`) therefore credits a failed-owner sub-account's load on its next cycle. The rule exists only on the webhook path, which the sweep bypasses. Latent today (sub-accounts are behind `wallet.subAccounts`, off, and not wired into `LoadService` until T-0709), but it must be fixed before either turns on.
Design: `creditStep` gains `ownerBlock(transfer)` beside `accountBlock`: for a `load` whose `toPartyId` has a `funding_subaccount_owner` marker equal to `ownerFailedMarker(party)` (`o:{party}:failed`, written at `sub-accounts.ts:125`; use the literal until T-0762 lands), the step opens the owner case through `openCase` with the SAME key `subaccount-owner:{party}` (`ownerCaseKey`, kind `OWNER_FAILED_CASE`, medium, payload `{ partyId }`) and returns false. Unlike `accountBlock` it does NOT open a `load_credit_refused` case and does NOT write the `began` marker, so no attempt number is burned and nothing waits for people to resolve a credit case: the load stays where it is, and every sweep cycle re-reads one marker row and credits (same `{wf}:credit:{n}` key) the first cycle after the marker is gone. The webhook drops `ownerFailed` from `CrowdedWebhookDeps`, `subAccountChapters` returns only `isMemberChapter`, and `process` stores and dispatches a failed-owner event like any other (the funding handler calls `applyVendorLoad`, which now refuses on its own and returns the unmoved transfer).
Replay and sweep behaviour after the change: (1) event arrives for a failed-owner chapter: stored, dispatched, `applyVendorLoad` leaves the load unsettled, one owner case, event marked processed (as before, but now harmless because the credit path owns the retry). (2) The same event replayed: no second case (`openCase` dedupes), no vendor credit call, no journal. (3) `stale()` returns `submitted` and `pending` loads every cycle and a held `pending_hold` ACH load when its hold is due (`loads.ts:680-695`), so the refused load is retried by the sweep without any webhook. (4) Once the owner marker is cleared the next sweep credits once and posts the one journal. Open question for the owner (DECIDED 2026-11-23: a delete grant, T-0787; text below as scoped): NOTHING clears `o:{party}:failed` today (it is written once, `on conflict do nothing`, and no code deletes or updates it), so "the owner is fixed" has no code path; the test clears the row with SQL. Either T-0770's `workflow_marker` gets a delete, or the block reads the live `ownerStatus` from `MemberSubAccountPort.subAccount(ref)` instead of the stored snapshot. Also: `openCase` does not reopen a resolved or dismissed case (the three load cases do), so a dismissed owner case with the marker still failed leaves the load waiting with no open case; T-0765 (cases module) is the place to give the owner case the reopen variant if the owner wants it.
