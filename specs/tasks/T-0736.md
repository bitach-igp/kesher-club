# T-0736 [SETUP] Production boots with Crowded funding while membership billing is waived: the three Stripe billing flags default off, the T-0043 guard is left exactly as it is

STATUS: NOT BUILD-READY until the owner answers the items marked OWNER DECISION. Changing `defaultProd` is owner territory (AGENTS.md: flag defaults, and the `billing.*` exceptions are listed there). Nothing in this scout changes a flag.
Files: config/flags.json (three `defaultProd` values and their `turnOnTrigger` text, nothing else), AGENTS.md (the one sentence listing the `defaultProd: true` exceptions), apps/api/src/main.test.ts (the T-0043 describe), apps/admin/src/providers/release-gates.test.ts, specs/tasks/T-0736.md, specs/tasks/README.md
Source: verified 2026-11-12 at 90fe882.
- The problem. `PORT_FLAGS.billing = ['billing.stripe','billing.applePay','billing.googlePay']` (`apps/api/src/config.ts:363`) and all three are `defaultProd: true` in `config/flags.json`. `PROVIDER_FUNDING=crowded` (T-0709) binds funding only, so the `billing` port stays a simulator, and `assertProdSimulatorsSafe` (`apps/api/src/flags/service.ts:60`, run by `apps/api/src/main.ts:45` and `apps/worker/src/main.ts:66`) refuses to boot prod: `port billing is a simulator but flag billing.stripe is on`. `FlagService.isOn` answers the `ops.flag_state` row, else `defaultProd`.
- Why the "flip them off in the flag store" path in T-0043's as-built note does not work for a first deploy: the flip goes through the admin API (`FlagService.propose`, a second admin approves) and the API is the process that refuses to start; a hand-written `ops.flag_state` row needs a real `approval_id` and `audit_id` (the test fakes them with `session_replication_role = replica`, `main.test.ts:262`). So the clean path is the registry default.
- What the flags gate (grep, every non-test use): `billing.stripe` gates `POST /memberships` (`apps/api/src/app.ts:337`) and a funder invite's accept and start (`billing/funder-invites.ts:238`); `billing.applePay` and `billing.googlePay` only choose the wallet buttons of the card-save sheet (`funder-invites.ts:125`). No mobile or admin code reads them except the generated capabilities payload. No other port has a default-on flag, so these three are the only guard violations (`auth.passkey.primary` and `ui.hebrew` are in no `PORT_FLAGS` row).
- What "waived" means in code with the flags off: no membership exists, so `MembershipService.forMember` is undefined and every reader falls back: FX markup is `DEFAULT_FX_MARKUP_BPS` (`fx/service.ts:250`), P2P limits use the risk limit only (`p2p/limits.ts:67`), the card plan cap does not apply (`cards/jit.ts:203`), entitlement credits (eSIM) do not apply, `GET /me/capabilities` returns `membership: null`. A self top-up needs no membership: `parse()` checks one only when the payer loads someone else's purse (`wallet/loads.ts:554`).
Proposal (the card):
1. Set `defaultProd` to `false` for `billing.stripe`, `billing.applePay` and `billing.googlePay` and rewrite their `turnOnTrigger` to name T-0737 (membership fee from the wallet) and that Stripe is not used; remove the three names from the exceptions sentence of AGENTS.md (the list shrinks to `auth.passkey.primary` and `ui.hebrew`). The guard code, `PORT_FLAGS`, the catalogue row and the Stripe adapters stay as they are (ADR-018 "Reversible"): turning a billing flag on later is refused while billing is a simulator, which is exactly the protection wanted.
2. Tests that pinned the old default and must change: `apps/api/src/main.test.ts` "refuses to start while a simulator port has a flag on" (it relies on `billing.stripe` being on by default; rewrite it to put a different simulator flag on through the flag store, or keep one assertion with the flag row set true) and its `GATED_ON_BY_DEFAULT` helper; `apps/admin/src/providers/release-gates.test.ts` lines 41 to 59 (`billing.stripe` on, the kill switch from on, `billing` row `status: 'live'`, `us.flags` on). `apps/admin/src/data/http.test.ts` uses fixtures and `registry.test.ts:423` builds its own `isOn`, so neither changes. `apps/api/src/billing/memberships.test.ts` and `funder-invites.test.ts` pass overrides and do not change.
3. New test: a prod boot with the `billing` port on its simulator and the three flags at their registry defaults passes `assertProdSimulatorsSafe` (so a future edit of `flags.json` that turns one back on fails CI); with `PROVIDER_FUNDING=crowded` from T-0709 the same holds.
OWNER DECISIONS (each with the recommendation):
- W1. What "waived" means. (a) RECOMMENDED: no memberships at all; every member gets the default plan behaviour above; zero new code. (b) Complimentary memberships: an active membership at price 0 with no vendor subscription, so plan entitlements (eSIM credits, P2P and card caps) apply from day one; needs a new `MembershipService` path and a price-0 plan version, a card of its own. - W3. Accept that, with no memberships, a funder cannot load another member's purse (`loads.ts:554` requires an active membership with the funder as payer). Consistent with "self top-ups first"; funder loads return with T-0737 or W1(b).
- W4. Confirm Stripe stays in the repo, unbound (default `sim`).
