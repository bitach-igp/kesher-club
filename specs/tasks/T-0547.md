## As-built
- `fail()` reverses the hold journal whenever it exists, also when the row still says `submitted` (a hold journal posted a moment before the row moved). `hold()` covers the other order: if the row turned out `failed` or `cancelled` by the time its journal posted, `hold()` reverses that journal itself (`{key}:hold:reversal`, once) and rethrows.
- A held load the vendor does not know (`UNKNOWN_LOAD` from `getLoad`) opens one `ops.case` (`load_unknown`, deduped per transfer) and `release()` stops asking the vendor about it until people act. The card said "marks the load `needs_review`", but the transfer state machine has no such state and adding one is outside this card's files, so the case is the marker: `unknownLoadOpen` checks it before the vendor call. The load stays `pending_hold` and nothing is credited.
- The stale sweep (`stale()`) asks about a held load only when its hold is due. A return during a hold that no webhook announced is still found at release time (`release()` asks the vendor first, T-0539). The sweep's own file `apps/worker/src/wallet/load-workflow.ts` needed no change: it calls `stale()`.
- Tests (`loads.test.ts`): both orders of the fail/hold race leave no hold standing; an unknown load opens one case and is asked once; a not-yet-due hold is not swept. All three fail on the old code.
