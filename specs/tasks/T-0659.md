## As built
- **Config** (`apps/api/src/config.ts`, shared by the API and the worker): `PROVIDER_INSTITUTION_BANKING` (`sim` default | `crowded`), `CROWDED_BASE_URL` (https), `CROWDED_API_TOKEN` (a `Secret`), `CROWDED_WEBHOOK_SECRETS` (one or two, comma-separated, distinct, non-empty; parsed to `Secret[]`). `CROWDED_BINDING` (`sandbox` default | `live`) is a fourth key outside the all-or-nothing set; see Registry. `PROVIDER_MODE_DEFAULT` is still `sim`-only. A partial set is refused, and I went one step past the card: also while the port stays on `sim`, because half a credential is a mistake and not a choice. A complete set under `sim` is accepted and ignored. Errors name keys and rules only; no value is quoted (tested for the token and both secrets).
- **Registry** (`apps/api/src/registry.ts`): `createRegistry(mode, clock, overrides)` keeps `(mode, clock)` first, so `dev.ts` and the demo are untouched. `overrides.institutionBanking` registers one `CrowdedInstitutionBankingAdapter` and binds `institution-banking` to it for both markets (binding mode `sandbox` for any base URL, `live` only when `CROWDED_BINDING=live` is set explicitly; the URL is never used to guess it); every other port stays on the `SimulatorHost`. It also returns `providers` for the start-up log. Two helpers sit beside it so the API and the worker do not repeat themselves: `overridesFromConfig(config, db, warn?)` and `crowdedWebhookSecrets(config)`. With `CROWDED_BINDING=live` the process logs a `warning` event (`LIVE_BINDING_WARNING`): the `provider_binding` approval in `ops.approval_request` is not applied by an env switch.
  - **Decided by Zvi (2026-11-04): option (a)**, keep `CROWDED_BINDING=live` as a label plus the warning; routing it through the `provider_binding` approval is a later card. Original options: `CROWDED_BINDING=live` only changes the binding label the registry holds in memory; it does not create, check or apply the `provider_binding` approval. Choose one: (a) keep it as a label plus the warning, and treat the approval as a manual step before the key is set; (b) have start-up refuse `live` unless an approved `provider_binding` row for `crowded` exists; (c) drop the key and bind `live` only through the approval flow. Until then nothing reads the mode for this port, so the label has no effect on behaviour.
- **The adapter's clock.** The card says the adapter's clock is the registry's, but the adapter takes no clock. The registry's clock goes to what does carry time: the key ledger is built by a `keys(now)` factory on that clock (its `created_at`).
- **Webhook verifier.** The adapter refuses every webhook unless `verifyWebhookSignature` is set, and the card does not mention it. The registry sets it to the same HMAC check the `/webhooks/crowded` receiver uses (`verifyCrowdedSignature`, both rotation secrets).
- **`crowdedHandlers` is not passed.** `app.ts` already binds the real `application`, `ach` and `collected` handlers (T-0650, T-0652, T-0653) and only spreads `AppOptions.crowdedHandlers` on top of them, so an empty object would add nothing. Only `crowdedWebhookSecrets` is passed, from `main.ts` (API and worker). On `sim` it is `[]`, as today: the simulator signs with the literal `sha256=sim`, not an HMAC, so it has no secret to hand over and the receiver refuses every delivery.
- **Keys** (`apps/api/src/institutions/crowded-keys.ts`): `PostgresVendorKeyLedger(db, provider, clock)` over `ops.vendor_idempotency (provider, key, body_hash, result jsonb, created_at)`, primary key `(provider, key)`, `select, insert` for `club_app` only (migration `ledger/0026_vendor_idempotency.sql`). First write wins; a put for the same key with another hash throws `IDEMPOTENCY_CONFLICT`, the same hash is a no-op (also under a race: insert, then compare). Results are stored bigint-safe: a bigint is written as `{"$bigint":"123"}` and read back as a bigint (`encodeResult` / `decodeResult`; `toWire` only covers `Money`), and a stored `null` reads back as `null`, an `undefined` result (SQL NULL) as `undefined`. Both are tested. **Overlap with T-0650:** `PostgresKeyLedger` in `us-banking.ts` already stores the same thing in `org.us_banking_key`, and T-0650 says it is "not yet handed to the real adapter". The card names a second table and class, and `us-banking.ts` is outside its files, so I built what it says; the two should be merged in a later card (point `us-banking.ts` at this ledger and drop `org.us_banking_key`), which needs a decision.
