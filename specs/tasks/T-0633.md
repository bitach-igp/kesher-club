## As built
- **Where I01 lives.** `/apply`, reached from the landing. A signed-in person with no institution sees "Apply for
  your organisation" while `institutions.selfServe` is on (read from `/me/capabilities`), or "Continue your
  application" once they have one. The page itself refuses a new application when the flag is off, and sends
  existing staff with no application home.
- **The token.** Applying needs only the person's own member token. `src/session.ts` now passes that token to the
  pages on the "no institution access" landing too, with no institution in the landing (the session test pins it).
  Every staff page and action still checks for the dashboard landing, so nothing institutional is reachable.
- **Steps.** The entity is done once the application exists, and shows read-only after that. People need at least
  one with the signatory role. The account is IL IBAN with a mod-97 check, or US routing (ABA checksum) and account
  number. Each step's fields are checked in `src/apply.ts` with the API's own rules before the call.
- **Dropped fields.** The card's ownership share and date of birth are not collected, matching T-0632: the API
  has no such fields.
- **Writes.** The server actions in `app/apply/actions.ts` call the API as the person (`memberApi` in
  `src/api.ts`) and return the problem's `problems`/`missing` list, so an account refusal names its cause. A retry
  keeps its key (`keyFor`); a landed write drops it.
- **Status.** A sentence for each status, in both languages; "needs more info" lists the reviewer's reasons and
  reopens the steps. "Approved" says to sign in again: the `org_admin` role reaches the token at the next sign-in,
  as for admin-created staff (T-0924).
- **Outside the card's list:** `src/session.ts` and `src/session.test.ts`.
