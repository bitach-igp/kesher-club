# T-1013 [AGT] Mount the MCP gateway on the API: an assistant can reach /mcp
REQ: REQ-AGT-001, REQ-AGT-002, REQ-AGT-006 (after T-1001 to T-1008, and T-1014 to T-1017: ADR-009's authorization server, which the card first assumed existed) · Sprint: 12
Files: apps/api/src/mcp/http.ts, apps/api/src/mcp/http.test.ts, apps/api/src/server.ts, apps/api/src/intents/service.ts, apps/demo/src/record/stack.ts, docs/setup/demo.md, specs/tasks/T-1013.md, specs/tasks/README.md; shared plumbing: apps/api/src/app.ts
Test first: TST-AGT-001, TST-AGT-002 (HTTP rows). Found while recording REC-09 (T-0921): `McpGateway` (`apps/api/src/mcp/gateway.ts`) is built and passes `agentGatewayContract`, but no running process serves it, and no card ever planned that. The API serves:
- `POST /mcp` (Streamable HTTP, JSON-RPC);
- `GET /.well-known/oauth-protected-resource` with the gateway's metadata.

Both are behind `mcp.enabled`, with writes behind `mcp.write.enabled` and money proposals behind `mcp.money.propose`, as the gateway already enforces. The tests cover:
- an unauthenticated call answers 401 with the `WWW-Authenticate` challenge naming the metadata URL;
- a token for another audience is refused;
- `tools/list` with a read-scoped token lists only read tools;
- `propose_p2p` over HTTP creates a pending intent and no transfer;
- with `mcp.enabled` off, `/mcp` answers 404.

The demo stack mounts it too, and REC-09 can then propose through it instead of the stack helper.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace` green; only listed files touched
Out of scope: OAuth authorization-server changes (the grant flow exists), SSE streaming beyond what the transport requires. Stop and ask on conflict with the spec.

As built:
- **The transport.** `apps/api/src/mcp/http.ts` speaks Streamable HTTP: one JSON-RPC 2.0 message per POST, no sessions, no server-sent stream.
  - Methods: `initialize` (protocol `2025-06-18`), `ping`, `tools/list` and `tools/call`. A notification answers 202.
  - `dispatch` hands `/mcp` and `/.well-known/oauth-protected-resource[/mcp]` to it before the route table, which must equal the contract. JSON-RPC is not a REST operation.
- **What the gateway already enforced, and what this adds.** `McpGateway` still enforces the audience, scope tiers, 60 calls a minute and the audit row. The transport adds the switches the gateway left to its host: `mcp.enabled` for everything (off answers 404), `mcp.write.enabled` for T1 tools and `mcp.money.propose` for T2 tools. A switched-off tool is neither listed nor callable.
- **Auth answers.** 401 and 403 carry the WWW-Authenticate challenge naming the metadata. The validator checks tokens against the signing key's public half and this API's issuer (ADR-009).
- **The production tool context.**
  - Accounts come from the ledger. Card status and freeze use the member's live card.
  - Proposals go through `IntentService.propose`. `unfreeze_card` was already a proposal, never a direct unfreeze, so it stays one.
  - The API has no transaction feed or eSIM usage endpoint, so `list_transactions`, `spending_summary` and `get_esim_usage` answer a tool error ("not available to assistants yet") rather than an empty list an assistant would read as "nothing happened".
- **A tightening outside the card.** `IntentService.propose` now refuses a p2p `toPartyId` that is not a member id. The end-to-end check found a phone number accepted there, which would only have failed at the member's passkey.
- **`config.ts` and `dev.ts` needed no change.** The resource and issuer come from T-1014's settings, and the demo mounts /mcp because the app does. The recording stack instead gains `POST /mcp` on its readiness port, which forwards a message with the demo assistant's token, so REC-09 can propose through the gateway.
