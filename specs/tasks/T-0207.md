# T-0207 [LED] A forged webhook never claims a genuine event's id
REQ: REQ-LED-005 · Sprint: 12
Files: apps/api/src/webhooks/store.ts, apps/api/src/webhooks/handler.ts, apps/api/src/webhooks/handler.test.ts, db/migrations/ledger/0023_inbound_event_signed_unique.sql, db/migrations/ledger/atlas.sum, handoff/desktop/T-0207-inbound-event.md, specs/tasks/T-0207.md, specs/tasks/README.md
Test first: TST-LED-005.
**Why.** `ops.inbound_event` is unique on the provider and event id, and the first delivery wins. So a forged delivery that arrives first is stored with `signature_ok = false`. The provider's genuine delivery of the same id then finds it and is answered 401 for good. Found while building T-0618; the bank feed is covered by its statement, the other providers are not.
**Change.**
- A refused delivery is kept for forensics but claims nothing: the uniqueness covers verified deliveries only (a partial unique index, `NOT VALID`-safe, with a desktop handoff).
- A genuine delivery after a forged one is verified, stored and processed once.
- A repeat of the genuine one is a duplicate.
**Tests.**
- forged, then genuine, then genuine again: 401, 200 processed once, duplicate;
- two forged deliveries do not block a genuine one;
- a verified duplicate still answers as before.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace`, `pnpm db:lint` green; only listed files touched
Out of scope: rate-limiting forged traffic. Stop and ask on conflict with the spec.
