# T-0207 [LED] A forged webhook never claims a genuine event's id
REQ: REQ-LED-005 · Sprint: 12
Files: apps/api/src/webhooks/store.ts, apps/api/src/webhooks/handler.ts, apps/api/src/webhooks/handler.test.ts, db/migrations/ledger/0023_inbound_rejected.sql, db/migrations/ledger/atlas.sum, handoff/desktop/T-0207-inbound-rejected.md, specs/tasks/T-0207.md, specs/tasks/README.md
Test first: TST-LED-005.
**Why.** `ops.inbound_event` is unique on the provider and event id, and the first delivery wins. So a forged delivery that arrives first is stored with `signature_ok = false`. The provider's genuine delivery of the same id then finds it and is answered 401 for good. Found while building T-0618; the bank feed is covered by its statement, the other providers are not.
**Change.**
- A refused delivery is kept for forensics but claims nothing: the uniqueness covers verified deliveries only (a partial unique index, `NOT VALID`-safe, with a desktop handoff).
- A genuine delivery after a forged one is verified, stored and processed once.
- A repeat of the genuine one is a duplicate.
**Tests.**
- forged, then genuine, then genuine again: 401, 200 processed once, duplicate;
- two forged deliveries do not block a genuine one;
- a verified duplicate still answers as before.
Done when: listed tests pass; `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm trace`, `pnpm db:lint` green; only listed files touched
Out of scope: rate-limiting forged traffic. Stop and ask on conflict with the spec.

## As built
- A forensic table instead of a partial index: `ops.inbound_event`'s primary key is the provider and event id, and
  changing a primary key is heavier than moving refused rows out. So a refused delivery goes to
  `ops.inbound_rejected`, with an id of ours and the app allowed only to add rows. It is answered 401 as before.
  `ops.inbound_event` holds verified deliveries only; refused rows already stored move across in the migration.
- `handler.test.ts` pinned the old behaviour on purpose ("a later, correctly signed delivery of the same id is
  still refused"). REQ-LED-005 reverses it, so that case now asserts the forensic copy, and a new case covers
  forged, forged, genuine, genuine.
- Extra files: `apps/api/src/kyc/service.test.ts`, whose two cases checked that refused deliveries were stored in
  `ops.inbound_event` and now check `ops.inbound_rejected`; and `apps/api/src/institutions/deposits.test.ts`. T-0618's test re-sent a fresh notification to get round
  this; it now re-sends the very notification the forger copied.
