# ADR-001: Modular monolith vs services

Status: Accepted · Decided: 2026-10-30 (Zvi, approving the next-phase plan; the draft recommendation below stands) · Decide by: Sprint 1

## Context
See the live spec, Tab 3 §4.

## Options
- Modular monolith, NestJS

## Recommendation (draft, 2026-10-18, for Zvi to accept or amend)
Keep the modular monolith, and keep it as it is built: one `apps/api` process with modules behind a
routes table that must equal the OpenAPI operations, a composition root (`app.ts`) that wires services,
and plain TypeScript handlers. The NestJS binding named in the README is not needed for the code that
exists: dependency injection is the composition root, module boundaries are the directory layout and
the ports, and every handler is already tested through `dispatch()`. Bind NestJS only if a concrete
need appears (a second process sharing modules, decorators the team wants, a vendor SDK that assumes
it). Services split out, if ever, along the port boundaries, starting with the JIT decision service
(REQ-CRD-003), which has its own latency budget.
