# ADR-009: MCP authorization server

Status: Accepted · Decided: 2026-10-30 (Zvi: build the authorization server before mounting /mcp) · Requirements REQ-AGT-010, REQ-AGT-011

## Context
The MCP resource server is built (T-1001 to T-1006): it validates audience-bound tokens against `agent.grant`, and enforces scope tiers, a 60 calls a minute limit and an audit row per call. Nothing issued those tokens: grants existed only as test fixtures. ADR-004 settled that the authorization server is in-house, so a member has one identity, their passkey, and not a second one at a vendor. T-1013 (mounting /mcp) found the gap.

## Decision
The API is the authorization server, with the same issuer as member tokens and a separate audience: the MCP URL. It follows OAuth 2.1 with the MCP authorization profile:

1. **Discovery.** `GET /.well-known/oauth-authorization-server` (RFC 8414) names the endpoints. It also states `code_challenge_methods_supported: ["S256"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `client_id_metadata_document_supported: true` and the scopes of REQ-AGT-005. `GET /oauth/jwks` publishes the signing key, which the member token service already holds.
2. **Clients.**
   - A client is its Client ID Metadata Document URL. It is fetched through the existing SSRF-guarded registry (T-1003).
   - There is no dynamic registration and no client secret: every client is public.
   - `redirect_uri` must exactly match one the document lists.
3. **Authorization: code flow with PKCE (S256 only).**
   - `GET /oauth/authorize` checks the client, redirect URI, PKCE challenge, `resource` (it must be the MCP URL) and scopes. It stores the request and sends the browser to the member app's consent screen.
   - A request the redirect URI can be trusted with fails back to the client with an RFC 6749 error. Any other failure stops at Kesher with a 400.
4. **Consent.**
   - In the member app, signed in, with a fresh passkey step-up.
   - The member sees the client's name and each scope in plain words, and may untick any scope.
   - Approving creates the grant, or replaces the scopes of the member's active grant for that client, so the grants screen (T-1006) shows one row per assistant.
   - The approval then issues a one-time code, valid for 60 seconds, bound to the client, redirect URI, PKCE challenge and resource.
   - Denying sends `access_denied` back to the client.
5. **Tokens.**
   - Access tokens are ES256 JWTs valid for 10 minutes. They carry `aud` set to the MCP URL, `sub`, `scope`, `grant_id`, `client_id` and `jti`.
   - Refresh tokens are opaque, stored only as SHA-256 hashes, and rotate on every use for up to 30 days.
   - Presenting a refresh token that was already rotated revokes the whole grant, which is how theft is detected.
   - Revoking a grant (T-1006) ends its refresh tokens, and the resource server already refuses its access tokens within 60 seconds.
6. **Separation.** The member API keeps refusing any token whose audience is not its own, and /mcp refuses any token whose audience is not the MCP URL (REQ-AGT-002). Downstream providers never see either (REQ-AGT-004).

## Consequences
- Tables `agent.authorization_request` and `agent.refresh_token` (migration agent/0002), both written only by the API.
- Cards: T-1014 (discovery, JWKS, authorization request), T-1015 (consent API), T-1016 (token endpoint and refresh rotation), T-1017 (the app's consent screen and a demo assistant client). T-1013 then mounts /mcp and REC-09 proposes through it.
- `mcp.enabled` gates the authorization endpoints as well as /mcp, and stays off in production until ADR-004's provider binding and the bank's agent review are done.
- A vendor authorization server can replace this later behind the same metadata, since clients discover the endpoints rather than hard-code them.
