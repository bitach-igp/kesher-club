# Codebase review

Reviewer: senior review pass. Read-only: no code changed. Findings cite file:line as read; anything not read is marked "unverified".

## Summary

1. Scope: I read about 55 files in full (domain, the ledger, transfers, P2P, payouts, loads, add-ons, JIT, auth, webhooks, the Stripe and Crowded adapters, the worker job table and workflow hosts, key migrations). Institutions, FX, intents, admin, MCP gateway, console and mobile were sampled by grep only and are marked unverified.
2. 39 findings: 5 high, 18 medium, 16 low. No code changed; this file is the only write.
3. The foundations hold: money is bigint everywhere I looked, the ledger is insert-only for the app role with a deferred balance trigger, reversals happen once, signatures are checked over raw bytes in constant time (Stripe adapter, Crowded), no PUT routes, the 171 OpenAPI operations equal the 171 routes, flags found in code exist in `config/flags.json`, and the only `console` call in non-UI source is the simulator start-up line (no logger calls found, so nothing logs PAN, tokens or OTPs; other logging libraries were not searched for).
4. The weak point is replay and concurrency. Workflows are built to be re-run, but the replay guards differ per workflow (F09, F10, F23), `TransferService.apply` is not idempotent despite its docs, and no balance, limit or entitlement check holds a lock (F13, F17).
5. Money-in has one serious hole: a failed or returned ACH load is never marked failed, and the release job credits the wallet without asking the vendor (F05). The fake used by every test models failure differently from Stripe, so the suite is green.
6. Money-out has two: payout funds are not reserved while it waits for cool-off or approval (F11), and a payout hit by a rail outage is stranded debited and unsent (F10).
7. Add-on purchases are the one money route with no step-up and no funds check (F12).
8. Auth and webhooks are generally careful (step-up on money routes, refresh rotation with reuse detection, rejected webhooks never claim an event id). Gaps: step-up and passkey ceremony state in process memory (F20), device add without step-up and no notification (F21), SSRF guard open to DNS rebinding (F22), an audit table lock the app role probably cannot take (F34, unverified).
9. Tests: the concurrency and crash tests run on single-connection PGlite and below every threshold, so none of F09, F13, F16, F17 or F23 can fail them (F36, F37).
10. Maintainability: three near-identical workflow skeletons and an inline-handler-heavy `app.ts` explain most of the drift; fix the skeleton, not the findings one by one (F38, F39).

## Top 5

1. **F05 (high)** Failed ACH loads are never failed and the hold release credits uncollected money. Real loss, test fake hides it. Fix: map `requires_payment_method` with a payment error to `failed`, re-check the vendor in `release`, sweep `pending_hold`.
2. **F11 (high)** A payout's funds are checked at request time only. A member can queue a payout to a new payee, spend the money during the 24 h cool-off, and the payout still goes out with the wallet negative. Fix: reserve at request time or re-check under lock at `submit`.
3. **F13 (medium, systemic)** No balance, limit or velocity check holds a lock (P2P, card JIT, entitlements): parallel requests overdraw the wallet and exceed caps. Fix: `for update` on `ops.account_balance` inside the posting transaction; add a real-Postgres concurrency test.
4. **F12 (high)** `createAddonOrder` debits the wallet with no funds check and no step-up, and passes `quantity` unvalidated. Fix: shared funds check, `requireStepUp`, integer bounds.
5. **F09 (high)** A P2P send left in `pending` (between `release_hold` and `settle`) is posted a second time when the client retries, and no sweep finishes it; the same shape exists for loads. Fix: explicit per-state branches in `runSend`, one transaction for release plus settle, add `pending` to the sweep.

Next in line: F10 (payout stranded after a rail outage), F15 (idempotency keys are global and only P2P checks the owner), F14 (a second card clearing is dropped).

## Findings

### packages/domain

Read in full: `money.ts`, `ledger.ts`, `ids.ts`, `config.ts`, `errors.ts`. Money is bigint end to end, `applyBps` rounds correctly, `Secret` never prints, config has no secret defaults. Nothing high here.

**F01 (low) `packages/domain/src/money.ts:45`, `apps/api/src/wallet/loads.ts:398-402`.** `fromWire` accepts an integer string of any length. Callers only check `> 0`. Scenario: `POST /loads` with `minor: "1" + 30 zeros` passes `parse`, then `transfers.create` binds it to `bigint` (`transfers/service.ts:100`) and Postgres raises 22003, which surfaces as a 500 `INTERNAL`, not a 422. Fix: cap in `fromWire` at the int64 maximum and answer VALIDATION_FAILED.

**F02 (low) `packages/domain/src/errors.ts:39-48`.** `toProblem` spreads `...this.extra` last, so an `extra` carrying `status`, `code`, `detail` or `type` overrides the real values. No call site does this today (all verified extras are `remaining`, `available`, `currency`, `problems`, `limitedBy`), so this is a trap, not a bug. Fix: spread `extra` first.

### packages/ports

Read: `base.ts`, `funding.simulator.ts`. Other simulators and contract suites were only listed and sized (unverified).

**F03 (medium) `packages/ports/src/base.ts:40-52`, `packages/adapters/src/stripe/funding.ts:33-37,119-126`.** `IdempotencyStore.run` has no in-flight guard, lives in process memory, and returns the first result for a key without comparing the input. The Stripe adapter also keeps webhook dedupe (`events`) and the amount cross-check source (`known`) in per-instance Maps. Scenario: two API tasks, a webhook lands on a task that did not create the load, `known` is empty, so the amount cross-check at line 126 silently does not run. After a restart the same applies. Stripe's own Idempotency-Key and `ops.inbound_event` primary key remain the real backstops, so this is defence-in-depth lost, not a double charge. Fix: drop the cross-check from the adapter and do it in `LoadService.applyWebhook` (it already does, `loads.ts:292`), or persist; document that `IdempotencyStore` is test-only.

**F04 (low) `packages/ports/src/funding.simulator.ts:14-23` (used by `stripe/funding.ts:57`).** `addBusinessDays` counts Mon-Fri using UTC day boundaries with no bank holidays, and it is the production ACH hold calculation (a simulator file exporting production logic). A load made at 21:00 New York time on a Sunday is Monday in UTC, so the hold ends a day later than the same load made at 15:00; a US bank holiday is counted as a business day, so the hold ends a day short around holidays (which matters given F05). Fix: move it out of a simulator file and decide the zone and holiday calendar explicitly.

### packages/adapters

Read in full: `stripe/client.ts`, `stripe/signature.ts`, `stripe/funding.ts`, `crowded/signature.ts`, `crowded/map.ts`, `crowded/institution-banking.ts`, both `money.ts` files. Not read: `stripe/billing.ts`, `airalo/*`, `cover-genius/*`, `workos`, `twilio`, `postmark`, `expo-push`, `apple`, `google` (unverified). Signature checks in both Stripe and Crowded run over raw bytes before parsing, in constant time, and Crowded has no re-serialised fallback. Money conversion at the adapter edge is exact (`decimalToMinor`, `fromCents`, `toCents` all refuse non-integers and unsafe ranges).

**F05 (high) `packages/adapters/src/stripe/funding.ts:214-228`, `apps/api/src/wallet/loads.ts:140-141,313-315`, `apps/worker/src/wallet/release-holds.ts:40-44`.** A failed ACH load is never marked failed, and the hold release credits money Stripe never collected.
- `mapPaymentIntent` maps `requires_payment_method` to `requires_action` (214-219), and computes `failureCode` from `last_payment_error` (226-228) but never turns that into `failed`. Per Stripe's documented behaviour, an ACH debit that fails or is returned leaves the PaymentIntent in `requires_payment_method` with `last_payment_error`, and emits `payment_intent.payment_failed`.
- `applyVendorState` treats `requires_action` as "wait for the member" and returns without change (`loads.ts:140-141`).
- The 5-minute `ReleaseHoldsJob` moves every `pending_hold` load past `hold_releases_at` from pending to wallet without asking the vendor (`release-holds.ts:40-44`), and the vendor sweep only looks at `state = 'submitted'` (`loads.ts:313-315`), never `pending_hold`.
- The fake hides this: `fake-stripe.ts:118` models a failed intent as `canceled`, which does map to `failed`, so the contract and load tests pass (`loads.test.ts:203` and `release-holds.test.ts:87` both drive failure through that fake).
Scenario: member loads $500 by ACH, the transfer goes `pending_hold` with the money in `pending`. On day 2 the bank returns the debit. Stripe sends `payment_failed`, the load stays `pending_hold`. On day 3 the release job posts pending to wallet and the member spends or pays out $500 that does not exist. Fix: map `requires_payment_method` with a `last_payment_error` (or any intent that was previously `processing`) to `failed`; have `LoadService.release` call `port.getLoad` and refuse unless `succeeded`; extend the stale sweep to `pending_hold`; make the fake follow real Stripe.

**F06 (medium) `packages/adapters/src/stripe/client.ts:99` and every other vendor client.** Only the Crowded client sets a timeout (`crowded/client.ts:122`). A grep for `AbortSignal` across `packages/adapters` and `apps` finds nothing else. Scenario: Stripe stalls a connection during `createLoad`; the HTTP request or workflow activity hangs until the socket dies, holding a DB-backed request open. Fix: one shared fetch wrapper with `AbortSignal.timeout`, retryable `PROVIDER_UNAVAILABLE` on abort.

**F07 (medium) `packages/adapters/src/crowded/institution-banking.ts:165-178,247-250`.** Crowded has no idempotency on creates, so the adapter reuses an existing organization and chapter by exact name match (`o['name'] === name`), and a collection by title plus amount. The EIN is validated at line 167 but never sent or used in the lookup. Scenario: two different institutions with the same legal name (common for chapters of one network) get the same `entityRef`, so one bank account and one set of collected payments serves both. Likewise two fee items with the same title and amount share one collection. Fix: put the institution id in the created object's name or metadata and match on that; use the EIN.

**F08 (low, forward-looking) `packages/adapters/src/crowded/institution-banking.ts:281-285`.** `collectPayments` filters Crowded by `createdAt >= since` and skips `pending`/`processing` payments. A payment created before `since` that succeeds after it is never returned. There is no production caller yet (grep: only the port, simulator and contract), so this is unverified in practice; the caller card (T-0652) must use an overlapping window or filter on `updatedAt`.

### apps/api

Read in full: `app.ts`, `http.ts`, `server.ts`, `routes.ts`, `transfers/*`, `ledger/post.ts`, `ledger/accounts.ts`, `p2p/{send,holds,limits,handlers}.ts`, `payouts/service.ts`, `wallet/loads.ts`, `addons/{orders,credit}.ts`, `billing/entitlements.ts`, `cards/jit.ts`, `cards/settlement.ts` (first 130 lines), `auth/{step-up,otp,passkeys,tokens,handlers}.ts`, `webhooks/*`, `mcp/cimd.ts`, `oauth/token.ts`, `audit/service.ts`. Not read (unverified): `institutions/*` (us-funding, deposits, kyb, credit beyond a grep), `fx/*`, `intents/*`, `admin/*`, `mcp/gateway.ts`, `billing/memberships.ts`, `wallet/{closure,auto-reload}` beyond grep, `p2p/requests.ts`. Every money handler I read except add-on orders and memberships calls `requireStepUp`; `requireRole` use is consistent in what I read.

**F09 (high) `apps/api/src/p2p/send.ts:79-95,259-274`, `apps/api/src/p2p/holds.ts:68-87`, `apps/worker/src/p2p/send-workflow.ts:39`.** A P2P send found in state `pending` is posted a second time, and nothing sweeps a send left in that state.
- Releasing a held send is two separate transactions: `apply('release_hold')` moves `pending_hold` to `pending`, then `apply('settle')` moves it to `settled` (`holds.ts:85-86`, and `send.ts:272-273` for converted sends). A failure between them leaves the transfer `pending`, with the release journal `{key}:release` (sender's pending to recipient's wallet) already posted.
- `runSend` has branches for `pending_hold` and for `created`/`submitted`, but a `pending` transfer falls into the same `else` block (lines 86-91): it skips both ifs, calls `post`, which posts a new `{key}:settle` journal from the sender's wallet to the recipient, then `settle`.
- `P2pReleaseHoldsJob` selects only `pending_hold` (`expiredHolds`, `transfers/service.ts:146`) and `SendWorkflow.stale` only `submitted` (`send.ts:282`), so a `pending` send is never finished by the system. The only thing that re-enters `runSend` for it is the client retrying `POST /transfers` with the same key (`send.ts:124-127`), and that is exactly what a mobile client does after an error.
Scenario: 800 ILS to a new payee, held two hours; the release job's second transaction fails (DB failover, deploy kill). The recipient already has 800. The member's app shows an error, they retry with the same key: `runSend` posts a second 800 from their wallet to the recipient, the transfer settles, and the recipient has 1,600 for one send. A rarer variant of the same shape: a crash between the hold journal and the hold transition (`holds.ts:53-64`) followed by `isNewPair` turning false (another send to the payee settled meanwhile) posts a settle journal on top of the hold, because `shouldHold` is re-evaluated on the replay (`send.ts:88`). Fix: make `runSend` switch on the state explicitly (a `pending` transfer finishes with `settle` only, using the release journal id); do release_hold and settle in one transaction; add `pending` to the sweep. The same two-step shape exists in `LoadService.release` (`loads.ts:254-255`), where a `pending` load replayed by webhook or sweep reaches `settle`, which posts `{key}:settle` on top of the release journal and credits the wallet twice (`loads.ts:210-220`); I did not run it, so that part is unverified.

**F10 (high) `apps/api/src/payouts/service.ts:102,266-270,451-456`.** A payout that hits a rail outage is stranded `submitted` with the money already debited.
- `submit` posts the debit journal, calls the vendor, and on `PROVIDER_UNAVAILABLE` moves a fresh transfer to `submitted` with the journal id, then throws (267-270; the comment says "the same key retries the pull").
- A retry runs `runPayout`, which returns immediately for `state === 'submitted'` (line 102), never calling the vendor again.
- The sweep's `resumable` selects only `pending_hold`, or `created`/`pending` with `journal_id is null` (451-456), so a `submitted` payout is not picked up either. No webhook can arrive because no payout was created.
Scenario: Nium is down for ten minutes when a member pays out 500 ILS (below the cool-off threshold, below the approval threshold). Their wallet is debited, the app shows "processing" forever, no vendor payout exists. Fix: let `runPayout` retry `submit` when the transfer is `submitted` with no `external_ref` for the transfer; or have the sweep pick those up; alert on `submitted` payouts without a vendor ref older than N minutes.

**F11 (high) `apps/api/src/payouts/service.ts:178-179,251-262`.** The balance is checked at request time, not when the money is posted, and nothing is reserved while a payout waits.
- The funds check is at 178-179. A new payee over 2,000 ILS cools off for 24 h (`coolOff`, 226-229, "nothing has moved"), and an amount over the two-person threshold waits for approval for as long as the approver takes. `submit` then posts wallet to partner_settlement (251-262) with no balance check, and `ledger.post` has no non-negative guard (`ledger/post.ts:62-75`).
Scenario: member with 3,000 ILS requests a 3,000 ILS payout to a new payee, then during the 24 h spends the 3,000 on the card or P2P. At release the journal posts, the wallet goes to -3,000, and Nium pays out 3,000. The same holds for institution payouts across an approval wait. Compare P2P holds, which do reserve (`holds.ts:49-65`). Fix: reserve at request time (wallet to pending under `{key}:reserve`), or re-check `available` inside `submit` under a lock and fail the transfer with INSUFFICIENT_FUNDS.

**F12 (high) `apps/api/src/addons/orders.ts:135-152`, `apps/api/src/app.ts:325-331`.** Add-on purchases debit the wallet with no funds check and no step-up.
- `charge` posts wallet +price, addon_payable -cost, fee_income -commission (142-150) with no `available >= price` test; a grep for `INSUFFICIENT_FUNDS` in `apps/api/src` shows it in p2p, fx, payouts, collections and institution credit, not add-ons. The handler `createAddonOrder` calls only `requirePrincipal` (app.ts:326), unlike every other money route.
- `quantity` is taken as-is from the body (app.ts:327-329): `1.5` makes `BigInt(quantity)` throw (500), `-1` is caught only by the table check `quantity >= 1` after entitlement credit has been computed, and a large value multiplies cost and price with no cap.
Scenario: a member with an empty wallet orders an eSIM; the order is charged (wallet negative), fulfilment proceeds through the vendor, which costs real money (Airalo cost), and the overdraft is only visible to the reconciliation job. Anyone holding a stolen access token can also spend the wallet to the vendor without a passkey. Fix: funds check inside the charge transaction (shared helper with p2p), `requireStepUp`, validate `quantity` as an integer 1..N.

**F13 (medium) `apps/api/src/p2p/send.ts:130-133,92`, `apps/api/src/cards/jit.ts:118-134,166-198`, `apps/api/src/ledger/post.ts:62-75`.** Every balance, limit and velocity check is a read followed by a later write with no lock.
- P2P: `limits.check` and the purse check happen at 130-132; usage is recorded only after settle (92, `recordUsage`); the ledger post has no guard. JIT: balance is read in one query (118-132), the hold is posted at 198; daily and monthly sums (`heldSince`) and the velocity count are separate reads.
- The only advisory locks in `apps/api/src` are in institution credit (`credit.ts:113`); `for update` appears on transfer, order and approval rows but never on `ops.account_balance`.
Scenario: two simultaneous 100 ILS card authorisations on a wallet holding 100 both pass `available >= amount` and both post, leaving -100; two concurrent P2P sends of the full balance do the same, and both pass the monthly limit that is computed from transfers not yet settled. Fix: `select ... from ops.account_balance where account_id = $1 for update` (or a per-wallet advisory lock) and re-check inside the posting transaction; for JIT a conditional update on the cache row. No test covers this (see Test gaps).

**F14 (medium) `apps/api/src/cards/settlement.ts:84-85`.** A second clearing for one authorisation is swallowed. `applyClearing` posts under `endKey(authId)`; if that journal exists it is returned (`ended.kind === CLEARING_JOURNAL_KIND`) without comparing `eventId` or amount to the first clearing. Scenario: a merchant captures a hotel hold in two parts, or a fuel pre-auth with an incremental capture; the processor sends two `authorization.cleared` events with different `eventId`s; the second is marked processed and nothing is charged to the member. Fix: key clearings by `eventId`, track cumulative cleared against held, and alert when a repeat has a different amount.

**F15 (medium) `apps/api/src/wallet/loads.ts:184-191`, `apps/api/src/addons/orders.ts:108-109`, `apps/api/src/transfers/service.ts:92-93`, `apps/api/src/ledger/post.ts:48-49`.** `Idempotency-Key` is one global namespace, and owner and payload are checked in only one place. P2P send checks `kind` and `fromPartyId` (`send.ts:124-126`) and has a test for it (`send.test.ts:122`). `LoadService.begin` checks only `kind`; `AddonOrderService.create` checks nothing. `TransferService.create` and `PostgresLedger.post` return the first result for a key even if the amount differs. Scenario: member B sends `POST /addon-orders` with a key member A used (keys are client-chosen, 8-128 chars, so a weak scheme like a timestamp or counter is guessable) and gets A's order back (sku, price, fulfilment including the eSIM install URL), nothing charged to B. On loads, B replaying A's key for a finished load gets A's transfer id and amount back (`runLoad` returns early for a settled transfer, `loads.ts:115`). Same key with a different amount for the same member silently replays the old amount instead of answering a conflict. Fix: scope keys by principal (`{partyId}:{key}` for the transfer key and journal prefix) or store a request hash and answer IDEMPOTENCY_CONFLICT on mismatch.

**F16 (medium) `apps/api/src/addons/orders.ts:114-131`.** Entitlement credit is consumed before the order exists, under a fresh order id. `credit.apply(..., id, now)` consumes units with key `addon:{id}` (credit.ts:44) outside the order transaction. If two requests with one key race, both consume, one insert loses on the unique key (128), and the loser's units are never restored (`restoreCredit` only runs for an order that exists). A crash between consume and insert does the same. Scenario: a member double-taps "Buy 5 GB" with their monthly 5 GB credit: the credit is consumed twice for one order and the second 5 GB is gone for the month. Fix: insert the order first, apply credit keyed by the order id after.

**F17 (medium) `apps/api/src/billing/entitlements.ts:66-82`.** `consume` reads usage via `can()` then upserts `used = used + excluded.used` in the same READ COMMITTED transaction with no row lock. Two concurrent consumes with different idempotency keys both see the old `used`, both pass, and the upsert adds both: usage exceeds the plan limit. This guards P2P monthly caps, card spend caps and eSIM credit. Fix: `select ... for update` on the usage row, or make the upsert conditional (`where used + amount <= limit`) and check `rowCount`.

**F18 (medium) `apps/api/src/cards/jit.ts:97-110,171-177,288-294`.** Three JIT correctness gaps.
- `decide` races `evaluate` against a 250 ms timer but does not cancel `evaluate`. If the budget fires first the processor gets a TIMEOUT decline while `evaluate` carries on and may still post the hold (line 198) and consume the entitlement. The member's money is held for a declined authorisation until `releaseExpired` frees it 7 days later (`settlement.ts:26,92-99`); a processor retry of the same `authId` finds the journal and approves (134).
- `heldSince` sums every `auth_hold` journal for the card (290-293), including holds already released or cleared, because it filters only on `kind = 'auth_hold'`. A card with a 100 ILS daily limit that makes three 40 ILS purchases that all clear still reads as 120 held until the day rolls over, and a released hold counts for up to 7 days towards the monthly limit.
- `decide` swallows all errors into TIMEOUT with no log, so a genuine failure (bad data, DB error) is indistinguishable from a slow request.
Fix: check an `aborted` flag before posting; exclude holds with an `:end` journal from `heldSince`; log the swallowed error class (not content).

**F19 (medium) `apps/api/src/cards/jit.ts:315-316`, `apps/api/src/p2p/limits.ts:106`, `apps/api/src/billing/entitlements.ts:27,33`.** "Day" and "month" for limits and entitlement periods are UTC. The business zone is Asia/Jerusalem (used only by the worker scheduler, `recon.ts`, and notification quiet hours). A member's daily card limit resets at 02:00 or 03:00 local, the monthly P2P cap and monthly eSIM credit reset at 02:00-03:00 on the 1st instead of midnight, and a purchase at 01:30 on the 1st local still counts to last month. Fix: compute period boundaries with `Intl.DateTimeFormat` in `Asia/Jerusalem` in one shared helper; cover with DST-edge tests.

**F20 (medium) `apps/api/src/auth/step-up.ts:14-17`, `apps/api/src/auth/passkeys.ts:53-54,80-84,123-127`.** Step-up and passkey ceremony state lives in process memory.
- `StepUpService` keeps `pending`, `issued` and a random per-instance HMAC `secret`; `PasskeyService` keeps `pendingRegistrations` and `pendingAuthentications`.
- With more than one API task a ceremony begun on one task fails on another ("ceremony missing"), a step-up token minted on task A is `STEP_UP_REQUIRED` on task B, and a deploy invalidates every live step-up.
- The two maps are fed by unauthenticated routes (`registerPasskey` options step needs only any `Bearer x`, `authenticatePasskey` takes any `deviceId`) and entries are removed only when a ceremony completes, so a client looping with random device ids grows the heap without bound.
Fix: move to `identity.*` tables or Redis with a TTL; cap and expire the maps in the meantime.

**F21 (medium) `apps/api/src/auth/passkeys.ts:102-103,115`, `apps/api/src/auth/handlers.ts:64-66`.** Adding a passkey to an existing account needs only a valid access token, no step-up. Scenario: a stolen 10-minute access token (or an XSS on web) registers the attacker's authenticator and gets a permanent, independent sign-in that survives token expiry and refresh-token revocation. The only signal is `this.events.push(...)` (115, and `new_device_sign_in` at 142), an in-memory array that is read only by `passkeys.test.ts:117` (grep of `passkeys.events` and `AuthEvent` across `apps` and `packages`). So no "new device" or "passkey added" notification is ever sent, and the array grows by one entry per sign-in for the life of the process. Fix: `requireStepUp` on the add-device path and write both events through the outbox instead of an array.

**F22 (medium) `apps/api/src/mcp/cimd.ts:70-80`, `apps/api/src/app.ts:237`.** The SSRF guard resolves the hostname, checks the addresses, then `fetch` resolves it again: a DNS rebinding attacker answers a public address to the guard and `127.0.0.1` or `169.254.169.254` to the fetch. `isPublicAddress` also misses 198.18.0.0/15, 192.0.0.0/24, documentation ranges, 6to4 and NAT64 (`64:ff9b::/96`) embedding private IPv4, and an IPv4-mapped address in hex form (`::ffff:7f00:1`) passes (`cimd.ts:41` slices 7 characters and recurses on `7f00:1`, which falls to the hex test at line 43). `client_id` is attacker-supplied through `/oauth/authorize` (public route). Fix: connect to the vetted IP with a custom agent (pin the lookup) and send `Host`/SNI for the name; widen the range list.

**F23 (medium) `apps/api/src/transfers/service.ts:112-132`, `apps/api/src/transfers/state-machine.ts:25-28`.** `apply` is documented as "Idempotent for an already applied event when `expectFrom` is omitted and the row is already in the target state" but there is no such code: `next()` throws IDEMPOTENCY_CONFLICT for any event the current state does not allow, including a repeat of the one just applied. Every workflow (`runSend`, `runLoad`, `runPayout`) relies on replays being safe. Scenario: a client retries a send while the first request is between `post` and `settle`: the second request's `settle` or `submit` throws 409 although the transfer is fine, and the client is told the send conflicts. Webhook processing hits the same path and is stored as an error until replayed. Fix: treat "already in the target state" as success inside `apply`, or return the row.

**F24 (low) `apps/api/src/transfers/outbox.ts:35-50`.** `publishBatch` has no `FOR UPDATE SKIP LOCKED` and publishes in id order but continues past a failed row. Two publishers deliver the same row twice, and a later event for the same aggregate (for example `transfer.settled`) can be delivered before an earlier failed one (`transfer.submitted`). At-least-once is documented; ordering is not, and consumers are unverified. Fix: `skip locked`, and stop the batch for an aggregate after its first failure.

**F25 (low) `apps/api/src/ledger/post.ts:62-75`, `db/migrations/ledger/0001_init.sql:30-37,47-56`.** Postings are inserted and the balance cache upserted in input order, so two concurrent journals touching the same two accounts in opposite order can deadlock (Postgres aborts one with 40P01, which is not retried here). Sort postings by account id. At the database level nothing ties `ledger.posting.currency` to `ledger.account.currency` (the cache upsert ignores currency too), and a journal with zero postings passes the deferred trigger. Both are caught only by the application. Fix: composite FK `(account_id, currency)` to `ledger.account`, and a minimum-postings check in the trigger.

**F26 (low) `apps/api/src/webhooks/verify.ts:43,69,81-88`, `apps/api/src/server.ts:34-40`, `apps/api/src/webhooks/handler.ts:35-39`.** Three smaller webhook points.
- `hmacVerifier` parses JSON and extracts the event id before it checks the signature (43 vs 53-60), and `server.ts` JSON-parses every non-Crowded webhook body before the handler runs, answering 422 for malformed JSON before authentication. Harmless today, but the rule is verify first.
- `stripeVerifier` sets no `timestampHeader` or tolerance (the timestamp sits inside the header), so the generic Stripe verifier has no replay window (the Stripe adapter's own `verifyStripeSignature` does), and `parseSignature` returns only the last `v1`, which breaks during a Stripe secret roll.
- `standardWebhooksVerifier` turns `whsec_` into `Buffer.toString('latin1')` and hands that string to `createHmac`, which encodes it as UTF-8, so any key byte above 0x7f corrupts the key and every real signature fails closed.
`handler.ts:35` also falls back to `JSON.stringify(req.body)` when `rawBody` is absent, which could never verify a real signature. Fix: pass key bytes as a Buffer, verify before parse, tolerance in `stripeVerifier`.

**F27 (low) `apps/api/src/webhooks/store.ts:46-48`, `apps/api/src/webhooks/handler.ts:36-38`.** Every unsigned or forged request to `/hooks/{provider}` inserts a row with the full payload into `ops.inbound_rejected` (public route, 2 MB body limit, no rate limit). Scenario: a loop of 2 MB posts fills the table. The Crowded route stores only a hash (`webhooks/crowded.ts:70`) and is the better model. Fix: store a hash and size, and rate-limit per IP.

**F28 (low) `apps/api/src/auth/tokens.ts:59,105`.** `TokenService` defaults its clock to `fixedClock(new Date().toISOString())`, a frozen clock: if any caller omits `opts.clock`, access tokens never expire and refresh checks use boot time. `app.ts:158` passes a clock, so this is latent. Separately `refresh` rebuilds the pair from `session.roles` captured at sign-in (105), so a role removed after sign-in survives refresh for up to 30 days; institution handlers recheck `org.staff` in the database (`app.ts:270-271`), other role gates do not (unverified). Fix: make `clock` required; reload roles on refresh.

**F29 (low) `apps/api/src/auth/otp.ts:34`.** `startOtp` is public and limited only per phone number (3 per 10 minutes, counted by a read then a later write, so a burst can exceed it). No per-IP or per-device limit. Scenario: SMS pumping against premium numbers, each a distinct phone that passes the per-phone check. Fix: per-IP and global send budget, and an atomic counter.

**F30 (low) `apps/api/src/routes.ts:201`, `apps/api/src/server.ts:29,72-74`.** `decodeURIComponent` throws `URIError` on a path like `/accounts/%E0%A4%A/transactions`; `match` is called outside the request try/catch in `dispatch`, so the server's outer catch answers a 500 `INTERNAL` instead of a 404 or 422. Fix: catch in `match`.
